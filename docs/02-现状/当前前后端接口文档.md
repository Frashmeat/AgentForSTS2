# 当前前后端接口文档

更新时间：2026-05-05

本文基于当前仓库实现整理，目标是给前端明确后端已暴露的 API 接口、WebSocket 协议、事件流和运行角色边界。本文覆盖“前端当前已使用接口”和“按 `workstation` / `web` 角色暴露的后端接口”。

## 1. 总览

### 1.1 基础约定

- 后端框架：FastAPI
- 工作站入口：`backend/main_workstation.py`、`backend/main.py`
- Web 入口：`backend/main_web.py`
- 默认 API 前缀：`/api`
- 当前 CORS 白名单：
  - `http://localhost:5173`
  - `http://localhost:7860`
- 认证链路已补 `/api/auth/*` 与 `/api/me/*`
- 新增用户中心链路默认不再由前端直传裸 `user_id`
- 旧 `/api/platform/*` 兼容接口仍保留显式 `user_id` 查询参数
- 当前后端运行角色为 `workstation` 与 `web` 两类；`full` 不再是当前代码中的有效运行角色
- WebSocket 地址由前端按运行时配置或当前 workstation 地址拼接

### 1.3 运行角色启用说明

当前接口可用性由后端运行角色决定：

- `workstation` 角色注册工作站路由：`/api/config/*`、`/api/knowledge/*`、`/api/plan`、`/api/project/*`、`/api/approvals/*`、`/api/workstation/platform/*` 与 `/api/ws/*`
- `web` 角色注册 Web 路由：`/api/auth/*`、`/api/me/*`、`/api/platform/*` 与 `/api/admin/*`
- `GET /api/platform/execution-profiles` 与 `GET/PUT /api/me/server-preferences` 还要求当前会话用户已登录并具备平台访问资格

当前 `config.migration` 会被标准化为空对象；旧 `platform_jobs_api_enabled`、`platform_service_split_enabled` 等迁移开关只属于历史阶段口径，不再控制当前路由挂载。

当前部署主线中的 Web 执行节点：

- 人工配置唯一真实源为 `runtime/agentthespire.config.json`。
- `tools.ps1 deploy app` 会生成 `runtime/generated/web.config.json` 与 `runtime/generated/web-workstation.config.json`，并通过 Docker env 注入容器。
- `web` 角色不再在同一容器内自动托管 Workstation 子进程；它通过 Docker 内网 `http://web-workstation:7860` 调度独立 `web-workstation` 容器。
- `web-workstation` 继续运行 `workstation` 路由集合中的内部执行接口，并通过 `ATS_WORKSTATION_CONTROL_TOKEN` 鉴权。
- `web` Docker 镜像会把仓库根目录 `mod_template/` 复制到容器内 `/app/mod_template`；`POST /api/me/server-workspaces` 创建服务器工作区时依赖该模板目录，缺失时返回 `503` 配置错误。
- 前端 runtime config 只包含本机 `local-workstation` 与 `web` 地址，不包含 `web-workstation` 地址。

### 1.4 当前执行链路边界

当前存在两条执行链路，必须按执行面、凭据来源、项目目录来源和产物归属区分。

#### Web 托管 Workstation 执行链路

Web 平台任务的服务器执行链路为：

```text
用户浏览器
-> Web 后端 same-origin /api/me/jobs
-> 平台任务、任务子项、ai_execution 入库
-> ExecutionOrchestrator 按 execution profile 选择 runner_type / model / server credential
-> Web 后端解密服务器凭据并派发给 web-workstation
-> web-workstation 调用 /api/workstation/platform/executions 执行 workflow step
-> step 内按 runner_type 调用 Codex CLI / Claude CLI / API
-> 写入服务器工作区并登记 artifact
-> 用户中心任务历史下载 source_project 或 plan_markdown
```

该链路的事实边界：

- 凭据来源：服务器凭据与用户默认服务器配置，不读取用户本机 Workstation 的 LLM 配置。
- CLI 来源：`web-workstation` 容器内安装的 Codex CLI / Claude CLI，不使用用户电脑上的 CLI 登录态或本机 PATH。
- 项目目录来源：服务器工作区；生成任务由前端先调用 `/api/me/server-workspaces` 获取 `server_project_ref`，再创建平台任务。
- 产物归属：平台任务历史；有服务器工作区的生成任务输出 `source_project` 源码 zip，纯方案链路输出 `plan_markdown`。
- 错误归因：Web 后端派发失败归为 `web_workstation`，Web 托管 Workstation 内部执行失败归为 `web_workstation`，模型网关或 CLI 调上游失败归为 `upstream` 并保留上游错误摘要。

#### 用户本机 Workstation 执行链路

用户本机执行链路为：

```text
用户浏览器
-> runtime-config.js 中配置的 workstation 地址
-> 用户本机 local-workstation 后端
-> 用户本机 project_root
-> 本机配置中的 LLM / Agent 后端
-> 用户本机 Codex CLI / Claude CLI / API
-> 直接修改用户本机项目或返回本机 workflow 结果
```

该链路的事实边界：

- 凭据来源：用户本机 Workstation 配置。
- CLI 来源：用户电脑上可执行的 Codex CLI / Claude CLI。
- 项目目录来源：用户本机 `project_root`。
- 产物归属：默认不进入 Web 平台任务历史；若需要进入平台历史，必须通过上传、导入或后续显式归档链路完成。
- 错误归因：浏览器或 Web 页面连接本机 Workstation 失败归为 `local_workstation`；本机执行阶段的错误也应显示为本机 Workstation 错误。

因此，“本机 Workstation / 本机 CLI 健康”不代表“Web 托管 Workstation / 服务器执行配置健康”。服务器执行是否可用至少取决于：服务器凭据健康、execution profile 与凭据协议匹配、Web 托管 Workstation 可达、容器内 CLI 可用，以及第三方网关是否支持对应 CLI 实际调用的协议。

## 2. 通用约定

### 2.1 HTTP 返回风格

当前项目已安装全局 HTTP 错误处理器。成功响应仍以 FastAPI 原生对象为主，失败响应分三类：

- 直接返回 JSON 对象
- 直接返回 JSON 数组
- 可预期失败由路由抛出 `HTTPException`，全局 handler 返回 `{"error":{"code":"http_<status>","message":"...","detail":"..."}}`
- 未处理异常由全局 handler 记录日志并返回安全兜底：`{"error":{"code":"internal_server_error","message":"服务端发生异常，请稍后重试","detail":null}}`

少数旧接口在参数不合法时不会返回 4xx，而是返回 200 + 业务错误对象，例如：

```json
{
  "error": "..."
}
```

前端 HTTP 错误处理当前统一经 `frontend/src/shared/api/http.ts` 与 `frontend/src/shared/error.ts`：

- JSON 请求使用 `requestJson()`。
- `multipart/form-data` 上传使用 `requestFormData()`。
- Blob / 文件下载使用 `requestBlob()`。
- 后端返回 4xx / 5xx 时，前端会解析 JSON `detail/message/error` 或纯文本，展示为 `请求失败（HTTP <status>）：<message>`。
- 浏览器网络层失败不再直接展示 `Failed to fetch`；会转换为 `无法连接 Web 后端（<url>）...` 或 `无法连接 Workstation 后端（<url>）...`，并提示检查服务是否启动和 `runtime-config.js` 地址。
- 管理端页面应通过 `AdminLayout` 注入的全局 `StatusNoticeStack` 展示成功、失败和警告；需要二次确认的危险操作使用项目通用 `ConfirmDialog`，不直接调用 `window.confirm`。

### 2.2 WebSocket 事件公共格式

所有 WebSocket 消息都是 JSON 文本。大多数消息带有 `event` 字段，例如：

```json
{
  "event": "progress",
  "message": "..."
}
```

公共事件：

| 事件名 | 说明 |
| --- | --- |
| `stage_update` | 阶段状态更新，通常用于页面顶部阶段条 |
| `error` | 全局错误 |
| `cancelled` | 用户主动取消或服务端确认取消；`code` 通常为 `user_cancelled` |
| `done` | 单流程完成 |

`stage_update` 通用结构：

```json
{
  "event": "stage_update",
  "scope": "project | text | image | agent | build",
  "stage": "内部阶段标识",
  "message": "给前端显示的阶段文案",
  "item_id": "可选，批量模式下用于标识具体 item"
}
```

客户端主动取消当前工作流时，向支持取消的工作流连接发送：

```json
{
  "action": "cancel"
}
```

服务端收到后应停止当前协程、关闭仍在运行的子进程或后台任务，并返回 `cancelled` 事件。若客户端直接断开连接，服务端按 `client_disconnected` 做本地清理；前端不应把 `user_cancelled` 或 `client_disconnected` 展示为系统失败。

## 3. 配置接口

### 3.1 `GET /api/config`

用途：获取当前配置，供独立设置页中的配置表单回显。

前端调用位置：

- `frontend/src/components/SettingsPanel.tsx`
- `frontend/src/shared/api/config.ts`

返回特点：

- 后端会对 `llm.api_key`、`image_gen.api_key`、`image_gen.api_secret` 做脱敏
- 脱敏格式通常为 `****xxxx`
- 返回对象是“标准化后配置”，会带默认值
- `llm.custom_prompt` 是后端运行时全局提示词来源，会追加到 agent / text prompt；仓库根目录不再保留或自动注入 `AGENTS_CODEX.md`

```json
{
  "llm": {
    "mode": "agent_cli",
    "agent_backend": "claude",
    "provider": "",
    "model": "",
    "api_key": "****abcd",
```

- 当前仍保留后端兜底：如果请求未显式传 `selected_execution_profile_id / selected_runner_type / selected_model`，后端会优先尝试继承当前用户“可用的默认服务器配置”
- 当确认开始平台任务时，后端会尝试基于任务快照里的 `selected_execution_profile_id` 创建 `ai_execution`，并写入实际命中的 `runner_type / model / credential_ref`。Web 派发到 `web-workstation` 时会把解密后的健康服务器凭据写入 `StepExecutionBinding`，Workstation 再按 `runner_type` 调用对应 CLI；若 `runner_type` 与 `api_protocol` 不匹配，会在路由或 runner 配置构造阶段直接失败，不进入 CLI 子进程。
- `runner_type=codex_cli` 时，Workstation 不依赖全局 `~/.codex/config.toml` 或 `OPENAI_BASE_URL`。它会对本次 `codex exec` 注入独立 `model_provider` 覆盖项，把 `api_base_url` 写入 `model_providers.platform_openai_compatible.base_url`，并通过 `OPENAI_API_KEY` 环境变量传入密钥。当前 Codex CLI 执行面使用 OpenAI Responses API；因此第三方 OpenAI-compatible 网关即使通过了 Chat Completions 健康检查，也还必须支持 `/responses` 才能被 Codex CLI 正常调用。若日志仍出现 `api.openai.com/v1/responses`，说明执行子进程没有吃到本次 provider 覆盖配置，应检查 Web Workstation 版本和启动配置。

认证接口常见失败仍以 `HTTPException` 风格返回，例如：

- `401 {"detail":"invalid credentials"}`
- `404 {"detail":"verification code not found"}`
- `400 {"detail":"verification code expired"}`

### 6.4 服务端事件

| 事件 | 结构 | 说明 |
| --- | --- | --- |
| `stage_update` | `scope/stage/message` | 阶段状态 |
| `progress` | `message` | 普通文本进度 |
| `prompt_preview` | `prompt/negative_prompt/fallback_warning?` | 提示词预览 |
| `image_ready` | `image/index/prompt` | 单张候选图已生成，`image` 为 base64 PNG |
| `approval_pending` | `summary/requests` | 审批模式下动作预览 |
| `agent_stream` | `chunk` | Code Agent 流式输出 |
| `done` | `success/image_paths?/agent_output?` | 完成 |
| `cancelled` | `message/code/traceback?` | 已取消，`code = user_cancelled` |
| `error` | `message/code?/traceback?` | 失败 |

### 6.5 典型事件流

#### 普通单资产流程

1. 客户端连接并发送 `start`
2. 服务端多次发送 `stage_update`、`progress`
3. 服务端发送 `prompt_preview`
4. 客户端发送 `confirm`
5. 服务端循环发送：
   - `stage_update`
   - `progress`
   - `image_ready`
6. 客户端发送 `select` 或 `generate_more`
7. 选定后，服务端进入后处理和代码生成
8. 服务端发送若干 `agent_stream`
9. 服务端发送 `done`

#### 自定义图片流程

如果首包带 `provided_image_b64`：

- 跳过 `prompt_preview`
- 跳过 `image_ready`
- 直接进入后处理和代码生成

#### 纯代码流程

如果 `asset_type = custom_code`：

- 跳过生图
- `image_paths` 为空数组
- 单资产页当前已暴露 `custom_code` 入口，并会隐藏图片来源、上传图片与自动选图相关 UI
- 本地直连模式会直接进入 Code Agent；服务器模式会直接创建文本实现方案任务

### 6.6 `done` 事件

典型结构：

```json
{
  "event": "done",
  "success": true,
  "image_paths": [
    "E:/STS2mod/MyMod/Resources/..."
  ],
  "agent_output": "Code Agent 最终输出"
}
```

### 11.2 `POST /api/platform/jobs/{job_id}/start`

用途：确认开始平台任务，并把当前任务子项正式接入执行调度真源；对已注册的最小服务器任务，还会直接进入内部 runner 执行。

当前行为：

- 路由会先把任务从 `draft` 推到 `queued`
- 若任务子项可调度，会继续创建对应的 `ai_execution`
- 默认会先把 `ai_execution.status` 推到 `dispatching`
- 当前 `web` runtime 已挂最小 `workflow_registry / execution_adapter / workflow_runner`
- 若命中已注册的最小服务器任务，会继续把 `ai_execution` 推到 `running/succeeded`，并同步回写 `job_item / job` 完成态
- 当前第一版已注册两条最小文本类链路：
  - `("log_analysis", "log_analysis") -> log.analyze`
  - `("batch_generate", "custom_code") -> batch.custom_code.plan`
  - `("single_generate", "custom_code") -> batch.custom_code.plan`
- 其他尚未注册的任务类型，开始后仍停留在记录层 / 运行中口径
- 对这类尚未进入最小 runner 的任务，后端现在会追加 `ai_execution.deferred` 事件，并在 payload 中写明 `reason_code / reason_message`
- 这类 deferred 任务当前会即时返还本次预留额度，避免“未真实执行但已净消耗 1 次”
- 对应的 `ai_execution.status` 当前会收口为 `completed_with_refund`，并追加一条 `ai_execution.finished` 事件
- 对应的 `job.status` / `job_item.status` 当前也会直接返回 `deferred`，不再继续伪装成 `running`

查询参数：

- `user_id`

请求体：

```json

  "triggered_by": "user"
}
```

成功响应：

```json

}
```

说明：

- 返回状态取决于任务类型是否命中已注册 workflow
- 若命中写型 workflow 且同一 `server_project_ref` 已被占用，当前会返回 `queued`
- 对当前最小闭环 `log_analysis`、`batch_generate/custom_code`、`batch_generate/card`、`batch_generate/relic`、`batch_generate/card_fullscreen`、`single_generate/custom_code`、`single_generate/relic`、`single_generate/card`、`single_generate/card_fullscreen`、`single_generate/power` 与 `single_generate/character`，开始后可能直接返回 `succeeded`

- `400 {"detail":"job selected_execution_profile_id is required"}`
- `400 {"detail":"execution profile is disabled: 1"}`
- `400 {"detail":"too many active server jobs for user: limit 2"}`

- 若额度不足，当前会把任务推进到 `quota_exhausted`
- 当前服务器任务开始前还会做第一版单用户并发保护：同一用户同时处于 `queued / running / cancelling` 的服务器任务数最多 `2`
- 当前开始任务接口还会做第一版轻量限流：同一用户 60 秒内最多开始 `5` 次平台任务，超限返回 `429`
- 若命中写型 workflow 且同一 `server_project_ref` 已被占用，当前不会创建 `ai_execution`，而是保持 `job=queued`、`item=ready`

- 若 `build.project` 进入服务器部署阶段且同名 `Mods/{project_name}` 当前正被另一条部署链占用，当前也会把该次执行回收到 `queued`

  - `queued_reason_message = "server deploy target is busy"`
- 当前还补了一条同进程内最小自动续跑：

### 12.18 管理端知识库包接口

本组接口用于服务器生成知识库的热更新。Web 后端 `runtime/knowledge/` 是服务器知识库唯一真实源：知识库包保存在 `runtime/knowledge/packs/{pack_id}`，当前激活指针保存在 `runtime/knowledge/active-knowledge-pack.json`。

管理端前端支持两种上传方式：

- 手动选择 zip 后上传到 Web。
- 从管理员本机 Workstation 调用 `GET /api/knowledge/export-pack` 导出当前知识库 zip，再由浏览器上传到 Web。该链路默认只上传，不自动激活；勾选“上传后立即激活”时才会继续调用 activate 接口。
- 上传、激活、回滚、删除的阶段、成功和失败提示通过全局 `StatusNoticeStack` 展示；删除知识库包通过通用 `ConfirmDialog` 二次确认。
- 当 Web 后端或本机 Workstation 不可达时，管理端展示明确的目标后端与 URL，不再只显示浏览器原始 `Failed to fetch`。

运行时读取规则：

- Web 后端 `runtime/knowledge/` 是服务器知识库唯一真实源，管理端列表、激活状态与运行状态页的“服务器知识库包”都以 Web 真源为准。
- Web 托管 Workstation 只是服务器生成执行面；由 Web 启动时会注入同一个 `SPIREFORGE_RUNTIME_DIR`，使托管 Workstation 读取同一份 runtime。若 Workstation 回报的 runtime 或 active pack 与 Web 真源不一致，`GET /api/admin/platform/workstation-runtime-status` 会返回 `knowledge_runtime_consistent = false` 和不一致原因。
- 手动启动或外部注册的 Workstation 若没有使用同一 `SPIREFORGE_RUNTIME_DIR`，不再按旧口径兼容；管理端会把它显示为运行时不一致，需要修正启动配置。
- 激活知识库包时，Web 会先校验包完整性，再把包内 `game/`、`baselib/`、`resources/sts2/` 安装到 Web 真源 `runtime/knowledge/`，后续服务器知识读取仍走这一个目录。
- `game/` 下只有 `sts2_api_reference.md` 或旧式单文件 `sts2.decompiled.cs` 不再算完整游戏知识库；只有通过 `ilspycmd --project --outputdir` 生成源码树并存在足量 `game/**/*.cs` 时才视为 `runtime_decompiled`。
- 知识库包必须是完整迁移包：`game/**/*.cs` 数量达到完整性门槛，`baselib/BaseLib.decompiled.cs` 存在，且必需 `resources/sts2/*.md` 全部存在。
- 上传、从本机 Workstation 导出上传、激活、回滚、删除等长耗时操作会在管理端显示阶段反馈，例如“导出本机知识库”“上传到 Web”“安装并激活”“刷新服务器状态”。
- 上传、激活、回滚会写运行时审计事件，但不会记录包内完整内容
- 上传后 `pack-meta.json` 会保存 zip 内相对文件清单 `files`，用于管理端校对包结构；接口不返回服务器绝对内容路径下的逐文件路径，也不返回文件内容
- 新包 metadata 会额外保存 `resource_md_count / game_cs_count / baselib_cs_count / required_resource_count / required_resource_total / missing_resource_files / has_required_resources / has_baselib_file`，用于快速判断资源 md、游戏反编译 `.cs`、BaseLib `.cs` 和必需资源文档是否齐全；旧包可能缺少这些字段

#### `POST /api/admin/platform/knowledge-packs`

请求类型：`multipart/form-data`

字段：

- `file`：知识库 zip 包
- `label`：可选显示名

成功响应：返回新建包 metadata，字段同列表项，包含 `pack_id / label / file_name / file_count / files / has_resources / has_game / has_baselib / has_required_resources / has_baselib_file / missing_resource_files`。其中 `files` 为 zip 内相对路径列表，可用于上传后人工校对。

源码统计字段：

- `resource_md_count`：`resources/sts2/*.md` 数量。
- `game_cs_count`：`game/**/*.cs` 数量。小于完整性门槛时上传、导出或激活会失败。
- `baselib_cs_count`：`baselib/**/*.cs` 数量。
- `has_baselib_file`：是否包含 `baselib/BaseLib.decompiled.cs`。
- `has_required_resources`：必需资源文档是否齐全。
- `missing_resource_files`：缺失的必需资源文档相对路径列表。

必需 zip 结构：

```text
resources/sts2/common.md
resources/sts2/card.md
resources/sts2/power.md
resources/sts2/relic.md
resources/sts2/custom_code.md
resources/sts2/character.md
resources/sts2/potion.md
resources/sts2/planner_guidance.md
game/...
baselib/BaseLib.decompiled.cs
```

失败：

- `400 {"detail":"knowledge pack file is empty"}`
- `400 {"detail":"knowledge pack must be a zip file"}`
- `400 {"detail":"unsafe knowledge pack path: ..."}`
- `400 {"detail":"知识库包不完整；..."}`

#### `POST /api/admin/platform/knowledge-packs/{pack_id}/activate`

激活指定包。成功后 Web 会把该包内容安装到 Web 真源 `runtime/knowledge/`，后续服务器 prompt 知识读取使用这份 runtime 内容；托管 Workstation 通过注入的 `SPIREFORGE_RUNTIME_DIR` 读取同一份 runtime。

失败：

- `404 {"detail":"knowledge pack not found"}`
- `400 {"detail":"知识库包不完整；..."}`

#### `POST /api/admin/platform/knowledge-packs/rollback`

回滚到上一激活包；如果没有上一包，则清空激活指针并清空当前 Web runtime 知识库内容。

### 12.4 `GET /api/admin/audit/events`

查询参数：

- `job_id` 可选
- `event_type_prefix` 可选；当前可用于只读取 `runtime.queue_worker.*` 等前缀事件
- `after_id` 可选；仅返回 `event_id > after_id` 的事件
- `limit` 可选；默认 50

成功响应：

- 当前返回对象来自 `AdminQueryService.list_audit_events`
- 当 `job_id` 为空时，当前还会并入运行时审计事件，例如：
  - `runtime.queue_worker.leader_acquired`
  - `runtime.queue_worker.leader_taken_over`
  - `runtime.queue_worker.leader_observed_other`
  - `runtime.queue_worker.leader_released`
- 当前运行时审计事件已优先走数据库真源；仅在未配置数据库时才回退文件存储
- 运行时审计事件当前不绑定真实平台 job，因此会以 `job_id = 0` 返回

## 15. 已知注意事项

- 当前很多旧接口直接使用 `dict` 作为请求体，没有严格的 OpenAPI schema，前端联调时应以本文档和具体实现为准。
- WebSocket 协议是项目自定义事件流，不是标准订阅模型；前端要按事件名驱动状态机。
- `/api/platform/*` 和 `/api/admin/*` 虽已实现，但默认不开启，前端不要假定线上必然存在。
- `/api/plan` 在需求为空时返回 200 + `{"error": ...}`，不是标准 4xx。
- 当前前端组件层已经不再直接 `fetch("/api/...")`，HTTP 调用统一经 `frontend/src/shared/api/*` 进入。
- 当前前端消费层已进一步补充共享 helper：`runApprovalAction()`、`useDefaultProjectRoot()`、`createBatchPlanningController()`、`createBuildDeployController()`、`resolveErrorMessage()`，用于减少页面重复逻辑。
- 审批对象后端字段比当前前端 TypeScript 类型更多，前端如果要完整展示，可补充：
  - `source_backend`
  - `source_workflow`
  - `created_at`
  - `result`
  - `error`
