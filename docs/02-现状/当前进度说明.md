## 3. Pack、Item 与 Resource 事实

STS2 Pack 正式注册六种 Item type：

```text
custom_code
relic
card
potion
power
character
```

Pack v4 顶层 `itemTypes` 是类型、canonical/localization fields、required locales、Evidence Queries、typed reference slots 和 conditional Resource profiles 的唯一真源。`compositionProfiles` 声明 preset/custom 参数、交叉约束和 128-node 上限。

```text
Pack SHA-256:
90b72f51911317e166802517329be5a5848b17b79961498953c5dfa72ee85df4

Character identity master SHA-256:
ec1b4f15aeb864166e0ec60936acfa390de9a0e9f2e06e41c5dc5a729a34c393
```

Character 合同包含 7 个 canonical fields、14 个 localization fields、6 个 typed reference slots 和 8 组 Truth Queries。

- `placeholder` 不要求 Character Resource binding。
- `branded_placeholder` 要求五个静态身份 roles。
- 512x512 `character.identity_master` 确定性派生顶栏 icon/outline、select/locked icon 和 map marker。
- Pack default 只按精确 Pack ID/SHA、asset ID 和 asset SHA 解析，不接受调用方路径。
- Upload、AI 和 Pack default 都先产生不可变 candidate；只有显式 select 才更新 selected pointer。

`character_suite` 默认 Standard；Prototype 为 11 nodes，Standard 为 35 nodes，当 Custom 在 Standard 上增加 8 个 Power 时为 43 nodes。数量、类型、依赖和 reference quantity 均来自 Pack，Feature 不写死 STS2 数量。

## 4. Composition 与恢复事实

CompositionDraft v2 保存 Pack/profile/root/nodes/revision、`sourceExecutionGraphId` 和 `validatedContentDigest`。审阅修订使用 revision CAS；内部 pinned DAG 在每次修订时自底向上重算 definition hashes；最终提交使用 `createOrMatch`实现精确创建或幂等匹配。

ExecutionGraphRecord v1 保存 owner/request/Blueprint identity、有序 nodes、logical attempts、已验证 checkpoint、active/previous Run、commit intent 和 final result reference。状态修改使用 revision CAS，Run 创建前必须先获得 graph claim。

```text
composition.plan
  Pack-driven Blueprint
  -> Suite Brief
  -> serial bounded nodes
  -> local reference binding
  -> whole-graph validation
  -> atomic Draft createOrMatch

composition.generate
  item.000.plan
  -> item.000.single
  -> ...
  -> item.NNN.single
  -> composition.finalize
  -> one validation/build/package/publication transaction
  -> one composition Artifact
```

模型或 typed validation 失败时，当前节点失败、graph 暂停、已成功 checkpoint 保留。用户显式 Resume 后创建新父 Run，只执行未成功节点。Feature 不实施第二层自动语义 retry，也不自动换 model、endpoint 或 response format。

definition-bound Plan 接收完整已验证 `StoredItemDefinition`，而不是仅依赖 behavior prose。Recipe 必须把 canonical fields、localizations、Resource/reference bindings 视为权威；typed decode 后 Feature 本地回填 `itemId`、`itemType` 和 `behaviorIntent`。Single 遇到 Plan prose 冲突时采用 definition，不通过文本启发式重建事实。

## 5. Prompt 与 Provider 事实

```text
Feature Recipe
+ Pack Contribution / selected Item descriptor
+ bounded Truth Evidence
+ selected Resource versions
+ Project Context
+ llm.custom_prompt
+ Typed Output Contract
= ModelRequestSnapshot v1
```

跨游戏任务语言属于 Feature Recipe；游戏类型知识属于 Pack；当前 API 事实属于 Truth；资源版本属于 Workspace；用户补充指令属于 `llm.custom_prompt`。

所有桌面 HTTP model 任务共享一个 FIFO 单飞队列。一个逻辑请求在全部 HTTP attempts 期间始终占用一个席位；排队取消不发请求。OpenAI-compatible output format 由 typed `json_schema`/`json_object` 配置在 Run 前固定，失败后不降级重发。

Single multi-file Recipe 输出上限为 16,384 tokens。invalid/truncated output 只持久化 `feature.mod-generate-single-failure-details` v1 的闭集 `reasonCode`，不保存 raw completion、parser text、Provider body 或未知 role 文本。
