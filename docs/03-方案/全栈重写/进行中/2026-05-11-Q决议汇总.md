## A. 架构最终方案 — new-api 中转站 + 全本地任务

### A.1 拓扑图

```
┌─────────────────────────────────────────────────┐
│ 创建者的服务器                                    │
│  ┌─────────────────┐  ┌──────────────────────┐  │
│  │ ats-web         │  │ new-api 中转站       │  │
│  │ - 用户管理       │◄─┤ - LLM key 池        │  │
│  │ - JWT token 分发 │  │ - 额度/扣费          │  │
│  │ - admin 控制台   │  │ - OpenAI/Anthropic   │  │
│  │ - 不跑用户任务！  │  │   双协议代理         │  │
│  └─────────────────┘  └──────────────────────┘  │
└─────────────────────┬───────────────────────────┘
                      │ HTTPS
                      ▼  ① 登录拿 JWT  ② LLM 调用走中转站
┌─────────────────────────────────────────────────┐
│ 用户桌面端 Tauri                                  │
│  - 所有任务在本地跑：                              │
│    * codegen / build_project / package_project   │
│    * knowledge_refresh（ilspycmd 本地）           │
│    * image_proc（rembg ONNX 本地）                │
│  - LLM 调用（每任务可选）：                        │
│    * 自带 key 模式 → 直连 Anthropic               │
│    * 平台模式 → endpoint 指向中转站，token 从       │
│                  ats-web 登录获取                  │
│  - 工程文件夹永远在本地（Q1）                       │
└─────────────────────────────────────────────────┘
```

### A.2 关键设计取向

- **计算分散到用户本地**：创建者服务器只负责"用户/token 管理 + admin"，不跑用户任务。Web 服务器压力可控。
- **LLM key 不暴露给桌面端**：中转站持真 key，桌面端只持"用户专属 JWT token"。token 撤销在中转站统一管理。
- **现有桌面端代码完全可用**：AnthropicClient 已有 `base_url` 参数，只需指向中转站；FileJobRepository / ilspycmd / 全部 handler 不变。
- **工程文件夹模式 (Q1) 天然契合**：用户工程本地存，无同步问题；任务产物直接落本地工程目录。

### A.3 N4（每任务可选 provider）的实现思路

每个涉及 LLM 的请求新增 `llm_provider` 字段（可选）：

```rust
pub enum LlmProviderChoice {
    AnthropicDirect,  // 用 settings.llm.anthropic_direct.api_key
    Platform,         // 用 settings.llm.platform.token + endpoint
    InheritDefault,   // 走 settings.llm.default_provider
}

pub struct SubmitTextGenerateRequest {
    // ... 现有字段
    pub llm_provider: Option<LlmProviderChoice>,
}
```

Tauri command 收到请求 → 根据 `llm_provider` 字段从 config 取对应配置 → 构造 LlmClient（同一个 trait，不同实例）→ 注入 service。

Settings schema（Q5 对齐 Python 风格，snake_case）：
```toml
[llm]
default_provider = "platform"   # 或 "anthropic_direct"

[llm.anthropic_direct]
api_key = ""                    # 留空则该 provider 不可用
endpoint = "https://api.anthropic.com"
model = "claude-sonnet-4-6"

[llm.platform]
token = ""                      # ats-web 登录后写入
endpoint = ""                   # 由 ats-web 登录返回（中转站 base url）
model = "claude-sonnet-4-6"
```

## 2. Q2 — 桌面端是否暴露 admin 路由？

### 状态
✅ **已决：按登录用户的 role 动态显示**（2026-05-11，经 new-api 方案讨论澄清）

> **决策路径**：
> 1. Claude 初版推荐"否"（基于"桌面端 = 单用户"假设）
> 2. 用户批注"是，需要暴露"
> 3. 经讨论暴露用户真实意图：桌面端是面向"创建者 + 普通用户"的多角色客户端
> 4. **最终方案**：admin 入口对所有桌面端用户暴露，但**根据登录用户的 role 决定是否显示**
>    - role=admin（创建者本人）→ 看到 11 个 admin 子页 + user-center
>    - role=user（普通用户）→ 只看到 user-center
>    - 未登录 / 本地模式 → 都不显示 admin

### 选项对比（历史）
| 选项 | 含义 |
| --- | --- |
| A | 桌面端也挂 admin 路由 |
| B | 桌面端隐藏 admin（Claude 初推） |
| **C** | **按 role 动态显示**（最终） |

### 理由
1. 桌面端是单用户场景。admin 概念（多用户管理、退款审计、credential 健康）在 Tauri 桌面环境下没有对应业务。
2. 减少 IPC 表面积。当前 Tauri command 已经 21 个，admin 加进来要 25+ 个，性价比低。
3. 前端代码：`__IS_TAURI__` 在 `App.tsx` 路由层就分流，桌面端根本不挂载 `pages/admin/*`。
4. 未来若桌面端要做"团队版"再加。

### 影响面
- Stage 3.6 routes/commands：admin 系列只在 ats-web 落地，src-tauri/commands 不出现
- Stage 6 前端：`pages/admin/*` 11 个页面只在 Web 模式编译进入（vite `define` 配合 `__IS_TAURI__`）
- 减少 Tauri 端 invoke_handler 列表项数

### 何时决/可回炒
Stage 3.6 启动前决；可回炒成本低（只需要把 Tauri command 加回来）。

## 3. Q3 — 远端 workstation HTTP 模式是否保留？

### 状态
✅ **已决：C 删除概念**（2026-05-11，经新-api 方案讨论后确认）

> **决策路径**：
> 1. Claude 初版决 C（基于"Tauri 桌面端已覆盖本地化"假设）
> 2. 用户批注"需要讨论"，提出真实诉求："用户任务在我的 web 服务器上跑，但不暴露 key"
> 3. Claude 转向 C 模式（双模式可配置）
> 4. 用户回提"new-api 中转站方案"：Web 不跑任务，只做用户/token 管理；任务永远本地跑；LLM 通过中转站
> 5. **最终方案**：仍然是 C（删除 workstation HTTP 概念），但**理由不同**——不是"任务都桌面端本地跑"而已，而是"创建者服务器只做用户管理 + 中转站，全部任务下放用户本地"
>
> 详见 §A 架构最终方案。

### 背景
Python 现状：Web 主服务在本地 spawn 一个 `workstation` 子进程，通过 HTTP 自己跟自己说话，让长任务（编译/打包/资产生成）在子进程跑。

### 选项对比
| 选项 | 含义 | 取舍 |
| --- | --- | --- |
| A | Web 端不再依赖 workstation runtime，自己装齐 LLM/ONNX | 失去"工作站本地化"动机；要求 Web 服务器有 GPU |
| B | 保留 headless 模式：`ats-web --mode workstation` 启 worker 子模式，Web 主服务 HTTP 调它 | 双进程协调复杂度（HTTP + ticket auth + 进程生命周期），与 Tauri 双壳设计冲突 |
| **C** | **删掉远端 workstation 概念，所有任务在本进程内的 tokio task 跑** | 最简，与 Tauri 双壳对偶；未来若真需要分布式可加 `ats-worker` crate |

### 选 C 的 4 条理由
1. **Tauri 桌面端已经覆盖"用户本地跑"场景**。远端 workstation 是 Python 时代的设计妥协 —— 当时只有 Web 一种壳，需要靠 spawn 子进程让 Web 主服务"借用本地资源"。Tauri 化后这层间接性失去意义。
2. **架构对偶最干净**：Web 轨 = sqlx + Postgres + 任务在 Web 进程；桌面轨 = Tauri + file repo + 任务在 Tauri 进程。两端形状完全对称。
3. **降低 Stage 3.4 ExecutionOrchestrator 复杂度**：不再需要分流 Web/workstation、ticket auth、远端进程生命周期管理。
4. **未来若真需要分布式 worker**（云端 Web 无 GPU、用户不想用桌面端这种小众场景），可单独加 `ats-worker` crate，不需要从 day 1 背着。

### 影响面
| 项 | Before（倾向 B） | After（决 C） |
| --- | --- | --- |
| `ats-web` 启动模式 | 主服务 + `--mode workstation` 子模式 | 单一进程，无子模式 |
| `workstation_runtime_service` Rust 等价物 | 保留 | **不迁移** |
| `workstation_platform` router | Web 轨保留代理 | **不迁移** |
| `workstation_capabilities` router | 远端能力查询 | **改名"本地能力查询"**（CPU/GPU/dotnet/ilspycmd 检测） |
| `ExecutionOrchestratorService` | 分流 Web/workstation | 简化为"所有任务本进程内调度" |
| Stage 3.4 services 数量 | 11 个 | 9 个（删 ExecutionOrchestrator 分流职责 + 删 ServerWorkspaceService） |
| Stage 3.4 工期 | 1.5 周 | 0.5-1 周 |
| 风险 R3（rembg 加载） | Web 端可推给 workstation | Web 端必须自己跑 ONNX；CPU mode 可接受 |

### 何时可回炒
- 在 Stage 3.4 ExecutionOrchestratorService 设计开始前可低成本翻盘
- 一旦 Stage 3.4 完成（约 2-3 周后），翻盘成本变高（需要重写 service 层分流逻辑 + 加回 workstation 二进制壳）
- 真正不可逆点：Stage 3.6 完成时

### 风险
- **R3 升级**：Web 部署的服务器若无 GPU，rembg ONNX 必须跑 CPU mode（慢，但能用）。中长期若要支持高并发图像处理，可能需要重新引入分布式 worker。届时按 §3 末尾说的 `ats-worker` crate 路径走，不影响主架构。

## 4. Q4 — 前端 zustand store 重设计 vs 镜像？

### 状态
✅ **已决：重设计**（2026-05-11 用户确认 Claude 推荐）

### 选项对比
| 选项 | 含义 | 取舍 |
| --- | --- | --- |
| A | 完全镜像现 frontend store API | 迁移轻，但拷贝过来的形状可能不是最优 |
| **B** | **集中到 `src/stores/` 按 feature 切，重设计 API** | 一次性痛快；后续维护成本低 |

### 理由
1. 现 frontend 的 store 分散在 `features/` 和 `shared/`，没有清晰的所有权边界。
2. zustand 5 + immer + persist 的组合用法与 zustand 4 时代有变化，借迁移做一次重新规划。
3. 双适配（Tauri / Web）让 store 形状有微妙差异（如 auth state 桌面端无意义），重设计能从 day 1 把 `__IS_TAURI__` 分支收敛到 store 选择层。

### 影响面
- Stage 6.1 共享基础（3-5 天）需要先把 store 结构敲定
- 所有 feature 迁移按新结构走

### 何时决/可回炒
Stage 6.1 启动前；可回炒（store 是前端内部结构，不影响后端）。

## 10. Q10 — rembg ONNX 模型分发？（本轮新增）

### 状态
✅ **已决：内嵌进安装包**（用户翻盘 Claude 初推荐）

> 用户明确要求"内嵌进包"。桌面 Tauri 安装包 +170MB；Web 端 Docker 镜像同步内嵌（运维方一次性下载到镜像层）。
> 离线可用 ✅ / 首启 0 延迟 ✅ / 安装包体积变大是接受的代价。

### 背景
rembg 用 u2net.onnx 模型做背景去除，模型约 170MB。

### 选项对比
| 选项 | 含义 | 安装包大小 | 首启延迟 | 离线可用 |
| --- | --- | --- | --- | --- |
| A | 模型内嵌进二进制 | +170MB | 0 | ✅ |
| **B** | **首启下载到 app_data/cache** | 30MB（基础） | 首次 30s-2min（看网速） | ❌（首次需联网） |
| C | 容器化部署单独 mount volume | 30MB（容器层） | 0（提前 mount） | ✅（运维责任） |

### 选 B 的 3 条理由
1. **安装包尺寸友好**：30MB 的 Tauri 安装包是合理的，200MB 会显著拖慢分发体验。
2. **桌面 + Web 双轨复用**：Web 服务器启动期下载到容器内 cache 卷，Tauri 桌面端 setup 钩子下载到 OS app data，逻辑同一份。
3. **未来可扩展**：若以后要支持多模型（u2net / u2netp / isnet-general），首启下载策略天然支持，按需取。

### 影响面
- Stage 4 `ats-core/src/image_proc/` 加 `model_resolver.rs`：检查 cache → 下载（reqwest） → 校验 SHA256 → 加载到 `ort::Session`
- Tauri `setup` 钩子：app 启动后异步 prewarm 模型（不阻塞 GUI）
- Web `main`：启动期检查模型；缺失时阻塞启动并打日志（避免首次请求才下载导致超时）
- 配置：`Settings.image_proc.{model_cache_dir, model_url, model_sha256}`

### 何时决/可回炒
Stage 4 image-proc 启动前；可回炒（切到内嵌只需要 include_bytes! + build 配置）。

### 风险
- 用户首次离线启动失败：需要在 GUI 给清晰提示"需联网完成首次模型下载"
- 模型 URL 失效：用 GitHub Release 自己镜像一份，避免 PyPI rembg 包变更
