# 2026-05-04 服务器知识库状态唯一真源收口计划

## 适用范围

- Web 管理端知识库包上传、从本机 Workstation 上传、激活、回滚、删除。
- Web 管理端运行状态页的“服务器生成能力”和知识库状态展示。
- Web 托管 Workstation 的 runtime 注入、能力上报和一致性诊断。

## 不纳入范围

- 不保留旧口径兼容：不再把外部 Workstation 自己的知识包状态视为服务器知识库最终状态。
- 不实现旧知识库包格式兼容：残缺包继续拒绝上传和激活。
- 不在本计划内改造完整后台异步任务系统；上传/激活第一版使用前端阶段反馈和后端同步接口。

## 问题事实

当前存在两个状态来源：

1. 管理端知识库包页读取 Web 后端 `runtime/knowledge/active-knowledge-pack.json`，激活后列表可显示当前激活包。
2. 管理端运行状态页读取 Web 托管 Workstation 的 `/api/workstation/capabilities`，其中 `knowledge_pack_active` 由 Workstation 进程自己的 `knowledge_runtime.get_active_knowledge_pack()` 得出。

如果 Web 后端和托管 Workstation 没有共享同一个 runtime 根目录，就会出现知识库包页显示“当前激活”，运行状态页仍显示“激活知识库包不可用”的状态不统一。

前端反馈也存在不足：

- `AdminKnowledgePacksPage.tsx` 上传、从本机上传、激活和回滚时只显示按钮“处理中”。
- “从本机上传后立即激活”实际包含导出、上传、激活、刷新列表多个阶段，但没有阶段反馈。
- 运行状态页没有说明能力状态是否来自 Web 真源、托管 Workstation 回报还是一致性检查。

## 主线决策

服务器知识库状态以 Web 后端 runtime 为唯一真实源：

```text
Web runtime/knowledge/
  active-knowledge-pack.json
  game/
  baselib/
  resources/sts2/
  packs/
```

Web 托管 Workstation 是执行面，不拥有独立服务器知识库状态。Web 启动托管 Workstation 时必须注入同一个 `SPIREFORGE_RUNTIME_DIR`，使 Workstation 读取 Web 的 runtime。运行状态页展示 Web 聚合后的服务器知识库状态，并把 Workstation 回报作为一致性诊断，而不是最终结论。

## 目标架构

```text
管理端知识库包页
  -> Web 管理端知识库包接口
  -> Web runtime/knowledge/active-knowledge-pack.json
  -> Web runtime/knowledge/{game,baselib,resources}

Web 托管 Workstation
  <- Web 启动时注入 SPIREFORGE_RUNTIME_DIR=<Web runtime 根>
  -> /api/workstation/capabilities 回报 runtime 与 active pack

管理端运行状态页
  -> /api/admin/platform/workstation-runtime-status
  -> Web 聚合：
       - Web active pack 真源
       - Workstation capabilities 回报
       - runtime root / active pack 一致性
```

## 实施计划

### Phase 1：后端状态真源收口

1. `WorkstationRuntimeManager` 启动托管 Workstation 时注入 `SPIREFORGE_RUNTIME_DIR`。
2. `workstation-runtime-status` 返回 Web 后端真源知识库状态：
   - `web_knowledge.active_pack_id`
   - `web_knowledge.active_pack_label`
   - `web_knowledge.knowledge_root`
3. `workstation/capabilities` 增加执行面回报：
   - `runtime_root`
   - `knowledge_root`
   - `active_knowledge_pack_id`
4. Web 聚合一致性字段：
   - `knowledge_runtime_consistent: boolean`
   - `knowledge_runtime_mismatch_reason: string`
5. 不一致时不做兼容兜底，直接作为异常状态暴露给管理端。

### Phase 2：前端状态展示收口

1. 运行状态页把“激活知识库包”改为“服务器知识库包”，展示 Web 真源 active pack。
2. 运行状态页单独展示 Workstation 一致性：
   - 一致：执行面已读取同一知识库。
   - 不一致：显示 runtime root 或 active pack 不一致原因。
3. 知识库包页激活、回滚、删除成功后刷新列表，并提示运行状态页会读取同一 Web 真源。
4. 前端类型更新为新字段，不保留旧字段作为主判断。

### Phase 3：长耗时操作反馈

1. 知识库包页增加操作阶段状态：
   - `导出本机知识库`
   - `上传到 Web`
   - `安装并激活`
   - `刷新服务器状态`
2. 全局 `StatusNoticeStack` 展示进行中、成功和失败。
3. 按钮文案显示当前阶段，而不是统一“处理中”。
4. 普通 zip 上传如需百分比，改为可上报进度的上传请求；第一版至少保证阶段反馈。

### Phase 4：文档与测试

1. 更新 `docs/02-现状/当前前后端接口文档.md`：
   - 说明 Web runtime 是服务器知识库唯一真源。
   - 说明 `workstation-runtime-status` 的 Web 真源字段与一致性字段。
   - 说明管理端知识库包操作的阶段反馈。
2. 补后端局部测试：
   - 托管 Workstation 启动注入 `SPIREFORGE_RUNTIME_DIR`。
   - runtime status 返回 Web active pack。
   - Workstation 与 Web active pack 不一致时暴露 mismatch。
3. 补前端局部类型检查与关键状态展示验证。

## 风险与约束

- 如果部署脚本没有为 Web 和托管 Workstation 挂载同一个 runtime 目录，后端一致性检查会暴露异常；这是预期行为，不再隐藏。
- `fetch` + `FormData` 没有原生上传进度事件；精确上传百分比需要换 `XMLHttpRequest` 或封装可追踪上传客户端。
- 当前接口仍是同步上传/激活，大包和安装过程可能占用请求时间；第一版通过阶段反馈改善可见性，后续如需要再引入后台任务。

## 验收标准

- 激活知识库包后，知识库包页和运行状态页显示同一个 active pack id。
- Web 托管 Workstation 的 capabilities 回报与 Web active pack 不一致时，运行状态页明确显示不一致原因。
- 从本机上传并激活期间，管理端能看到导出、上传、激活、刷新状态等阶段反馈。
- 知识库包上传、激活、回滚、删除成功和失败均走全局通知。
- 接口文档同步说明新的真源和一致性字段。

## 实施结果

### 已落地

- `WorkstationRuntimeManager` 启动托管 Workstation 时注入 `SPIREFORGE_RUNTIME_DIR=<Web runtime 根>`，并在运行状态中返回 `workstation_config_path` 与 `runtime_root`。
- `/api/workstation/capabilities` 返回 `runtime_root`、`knowledge_root` 与当前执行面 active pack。
- `/api/admin/platform/workstation-runtime-status` 返回 `web_knowledge`、`knowledge_runtime_consistent`、`knowledge_runtime_mismatch_reason`，并对缺失 `runtime_root`、`knowledge_root` 或 knowledge 状态的旧式 capabilities 直接判定为不一致。
- 管理端运行状态页把知识库状态改为展示 Web 真源“服务器知识库包”，并展示 Web runtime、Workstation runtime 与一致性诊断。
- 管理端知识库包页增加阶段反馈，覆盖手动上传、从本机 Workstation 导出上传、激活、回滚、删除与刷新服务器状态。
- 接口文档已同步更新 `workstation-runtime-status` 与管理端知识库包接口口径。
