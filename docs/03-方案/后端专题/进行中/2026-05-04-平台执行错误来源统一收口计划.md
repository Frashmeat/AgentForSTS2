## 1. 问题结论

当前系统已经有局部错误分类，但还不能稳定回答“到底是谁报错”。

主要问题：

1. `ExecutionAdapter` 目前只在异常对象提供 `to_error_payload()` 时才保留结构化错误；其它异常会落成 `failed_system + error_summary=str(exc) + error_payload={}`。
2. Web 到 Workstation 的边界只粗分为 `workstation_dispatch_failed`，没有进一步区分 Workstation 不可达、token 错、轮询超时、Workstation 已接单但 step 失败。
3. 上游错误分类只在文本生成链路存在，且当前主要依赖异常字符串判断。
4. “错误在哪个运行面触发”和“根因属于谁”没有拆开，导致 Web 托管 Workstation 内触发的上游错误容易被误判为 Workstation 自身错误。
5. 前端和管理端只能靠 `reason_code` / `error_summary` 猜测错误来源，不能稳定引导管理员查看 Web 日志、Web Workstation 日志、本机 Workstation 或上游配置。
6. 前端多个页面各自拼错误提示，缺少统一解析函数和通用展示组件，后端即使分清来源，展示层仍可能混淆。
7. `agent_backend=claude` 容易被理解为“Claude 协议”，但实际代码中它可能只是非 Codex CLI 的文本执行路径；`provider=openai` 实际表示 OpenAI-compatible 协议，不表示任意第三方网站供应商。
8. `base_url` 当前语义不够明确，用户可能填入第三方网站首页；当 `provider=openai` 时系统会按 OpenAI-compatible 拼 `/chat/completions`，若该地址实际是 Claude/Anthropic 入口或网页入口，就会返回 HTML 并触发 `upstream_invalid_response`。
9. LiteLLM 初始异常与 direct HTTP fallback 最终异常目前主要散落在日志中，结构化错误 payload 不一定同时保留完整错误链，管理端排障仍需要翻日志猜测。

## 2. 目标

每一次平台任务失败最终都必须能回答：

1. 错误发生在哪个运行面。
2. 根因属于 Web、本机 Workstation、Web 托管 Workstation 还是上游。
3. 具体组件和操作是什么。
4. 错误是否可重试。
5. 管理员下一步应该查看哪类日志或配置。
6. 前端所有任务失败入口使用同一套解析函数和组件展示，不再按页面各自解析字符串。
7. 执行配置必须清楚区分“运行器类型”和“API 协议”，从源头阻止混合协议配置。
8. 上游错误 payload 必须保留脱敏、截断后的错误链，管理端能看到初始错误与最终错误摘要。

## 3. 核心概念

### 3.1 runtime_surface

`runtime_surface` 表示错误在哪个运行面被触发。

取值：

- `web`：Web 后端进程。
- `web_workstation`：Web 托管 Workstation 进程。
- `local_workstation`：用户本机 Workstation 进程。
- `browser`：浏览器侧发起的本机 Workstation 调用或网络请求。

### 3.2 origin

`origin` 表示根因属于谁。

取值：

- `web`：Web 后端自身逻辑、数据库、队列、配置、路由等问题。
- `web_workstation`：Web 托管 Workstation 自身执行环境、文件、CLI、构建、runtime 等问题。
- `local_workstation`：本机 Workstation 自身执行环境、导出、文件、CLI 等问题。
- `upstream`：外部模型、第三方网关、OpenAI-compatible 代理、Claude/OpenAI/Codex 服务等问题。

示例：

| 场景 | runtime_surface | origin |
| ---- | ---- | ---- |
| Web 连接不上托管 Workstation | `web` | `web_workstation` |
| 托管 Workstation 内 Codex CLI 缺失 | `web_workstation` | `web_workstation` |
| 托管 Workstation 调模型 429 | `web_workstation` | `upstream` |
| Web 自己写数据库失败 | `web` | `web` |
| 浏览器直连本机 Workstation 失败 | `browser` | `local_workstation` |

### 3.3 runner_type

`runner_type` 表示文本或代码生成由哪个执行器发起，不表达上游 API 协议。

取值：

- `codex_cli`：通过 Codex CLI 执行，凭据注入为 `OPENAI_API_KEY` / `OPENAI_BASE_URL`。
- `claude_cli`：通过 Claude CLI 执行，凭据注入为 `ANTHROPIC_API_KEY` / `ANTHROPIC_BASE_URL`。
- `api`：通过后端 HTTP API 客户端执行，此时必须显式选择 `api_protocol`。

旧 `agent_backend` 不再作为正式字段保留。管理端 UI、后端 contract、数据库字段、文档统一使用 `runner_type`。

### 3.4 api_protocol 与 api_base_url

`api_protocol` 表示上游 API 协议，不表示第三方网站品牌名。

取值：

- `openai_compatible`：OpenAI-compatible Chat Completions 协议。只有此协议可以拼接 `/chat/completions`。
- `anthropic_compatible`：Anthropic / Claude-compatible 协议。必须使用 Anthropic 请求路径与 header。

`api_base_url` 表示协议对应的 API base URL，不是网页入口、控制台入口或文档页。

配置规则：

| runner_type | api_protocol | api_base_url 要求 |
| ---- | ---- | ---- |
| `codex_cli` | 可为空或 `openai_compatible` | 注入给 Codex CLI；若填写，必须是 OpenAI-compatible API base URL |
| `claude_cli` | 可为空或 `anthropic_compatible` | 注入给 Claude CLI；若填写，必须是 Anthropic-compatible API base URL |
| `api` | 必填 | 后端按协议直接发 HTTP 请求，必须通过健康检查 |

禁止规则：

- `api_protocol=openai_compatible` 不得请求返回 HTML 的网页入口。
- `api_protocol=anthropic_compatible` 不得走 `/chat/completions`。
- `runner_type=api` 时不得省略 `api_protocol`。
- 不再保留 `provider=openai`、`provider=anthropic` 这种混合“供应商”和“协议”的旧命名。

## 4. 统一错误结构

新增统一错误 envelope，建议命名为 `PlatformErrorEnvelope` 或 `ExecutionErrorEnvelope`。

目标结构：

```json
{
  "schema_version": "platform_error.v1",
  "origin": "upstream",
  "runtime_surface": "web_workstation",
  "component": "text_generate",
  "operation": "openai_compatible_chat_completion",
  "category": "invalid_response",
  "reason_code": "upstream_invalid_response",
  "message": "上游 OpenAI-compatible 网关返回了非 JSON 响应",
  "developer_message": "HTTP status 200 content_type=text/plain body_tail=...",
  "retryable": true,
  "step_id": "single.relic.plan.text",
  "step_type": "text.generate",
  "job_id": 2,
  "job_item_id": 2,
  "execution_id": 2,
  "runner_type": "api",
  "api_protocol": "openai_compatible",
  "model": "deepseek-v4-pro",
  "http_status": 200,
  "provider_error_code": "invalid_json_response",
  "log_hint": {
    "primary": "web_workstation_stderr",
    "secondary": "web_backend_log"
  },
  "diagnostic": {
    "endpoint": "https://e-flowcode.cc/chat/completions",
    "initial_error": "litellm openai-compatible response parsing failed...",
    "final_error": "OpenAI-compatible direct response was not valid JSON...",
    "upstream_attempts": "litellm,direct_http",
    "content_type": "text/plain",
    "body_tail": "..."
  }
}
```

字段规则：

- `message`：面向用户和普通管理员的短说明。
- `developer_message`：面向排障人员的短诊断，可包含截断后的响应尾部、退出码、stderr tail，但不得包含 API Key、完整 prompt 或完整响应。
- `diagnostic`：结构化诊断字段，只放允许展示和记录的截断信息。
- `diagnostic.initial_error` / `diagnostic.final_error`：用于保留上游调用链中的初始失败和最终失败摘要。
- `diagnostic.upstream_attempts`：记录上游调用尝试链路，例如 `litellm,direct_http`。
- `diagnostic.endpoint`：只允许记录不含凭据的 URL 摘要。
- `log_hint`：管理端根据该字段引导查看 Web 日志、Web Workstation stdout/stderr、本机 Workstation 或上游执行配置。
- `reason_code`：稳定机器码，前端和测试应依赖它，不依赖自然语言。

## 5. 分类矩阵

### 5.1 category

| category | 含义 |
| ---- | ---- |
| `config_error` | 配置缺失、base_url 错、token env 缺失、模型配置不合法 |
| `network_error` | 连接失败、DNS、拒绝连接、Workstation 不可达 |
| `auth_error` | 401/403、token 错、凭据无效、模型权限不足 |
| `rate_limited` | 429、额度不足、限流 |
| `content_policy` | content filter、safety policy、内容策略拒绝 |
| `invalid_request` | 400、参数不支持、模型不支持字段 |
| `invalid_response` | 200 但非 JSON、空响应、响应结构不符合协议 |
| `timeout` | CLI 超时、HTTP 超时、poll 超时 |
| `process_error` | CLI 退出码非 0、构建进程失败 |
| `filesystem_error` | 路径不存在、权限、文件读写失败 |
| `internal_error` | 未分类异常，后续应持续减少 |

### 5.2 reason_code 首批清单

| reason_code | origin | category | 典型场景 |
| ---- | ---- | ---- | ---- |
| `web_internal_error` | `web` | `internal_error` | Web 未分类异常 |
| `web_database_error` | `web` | `internal_error` | 数据库读写失败 |
| `web_workstation_unreachable` | `web_workstation` | `network_error` | Web 连不上托管 Workstation |
| `web_workstation_control_token_missing` | `web_workstation` | `config_error` | 控制 token 环境变量缺失 |
| `web_workstation_control_token_invalid` | `web_workstation` | `auth_error` | 控制 token 不匹配 |
| `web_workstation_dispatch_timeout` | `web_workstation` | `timeout` | 派发或轮询超时 |
| `web_workstation_execution_failed` | `web_workstation` | `internal_error` | 托管 Workstation 执行入口未分类失败 |
| `local_workstation_unreachable` | `local_workstation` | `network_error` | 浏览器或 Web 连接不上本机 Workstation |
| `local_workstation_export_failed` | `local_workstation` | `process_error` | 本机知识库导出失败 |
| `upstream_content_policy_blocked` | `upstream` | `content_policy` | 内容策略拒绝 |
| `upstream_rate_limited` | `upstream` | `rate_limited` | 429 或额度不足 |
| `upstream_auth_or_region_blocked` | `upstream` | `auth_error` | 401/403、区域或模型权限不可用 |
| `upstream_bad_request` | `upstream` | `invalid_request` | 400、模型或参数不兼容 |
| `upstream_gateway_blocked` | `upstream` | `auth_error` | 网关 blocked、账号策略拒绝 |
| `upstream_invalid_response` | `upstream` | `invalid_response` | 空响应、非 JSON、响应结构不合法 |
| `upstream_protocol_mismatch` | `upstream` | `config_error` | `api_protocol` 与 `api_base_url` 实际协议不匹配，例如 OpenAI-compatible 请求返回 HTML 页面 |
| `llm_cli_timeout` | `upstream` | `timeout` | Codex / Claude CLI 超时 |
| `codex_cli_not_found` | `web_workstation` 或 `local_workstation` | `config_error` | Codex CLI 未安装 |
| `claude_cli_not_found` | `web_workstation` 或 `local_workstation` | `config_error` | Claude CLI 未安装 |
| `build_project_failed` | `web_workstation` 或 `local_workstation` | `process_error` | 构建失败 |

## 6. 前端统一展示方案

前端必须与后端统一错误 envelope 一次性收口。后端提供 `platform_error.v1`，前端只负责解析和展示，不再从 `error_summary` 中猜测错误来源。

### 6.1 统一解析函数

新增共享解析函数，建议位置：

```text
frontend/src/shared/platform/errors.ts
```

核心 API：

```ts
toPlatformErrorView(errorPayload: unknown, errorSummary?: string): PlatformErrorView
```

目标类型：

```ts
type PlatformErrorView = {
  schemaVersion: string
  title: string
  badgeLabel: string
  badgeTone: "danger" | "warning" | "info"
  message: string
  developerMessage: string
  origin: "web" | "web_workstation" | "local_workstation" | "upstream" | "unknown"
  runtimeSurface: "web" | "web_workstation" | "local_workstation" | "browser" | "unknown"
  component: string
  operation: string
  category: string
  reasonCode: string
  retryable: boolean | null
  stepId: string
  stepType: string
  runnerType: string
  apiProtocol: string
  model: string
  httpStatus: number | null
  logHint: {
    primary: string
    secondary: string
  }
  diagnosticRows: Array<{ label: string; value: string }>
}
```

解析规则：

- 优先读取 `errorPayload.schema_version === "platform_error.v1"`。
- 旧字段只允许作为实施期内部临时 fallback；正式完成后所有平台任务失败都应有 `platform_error.v1`。
- 前端不能依赖 `message` 文案判断类型，只能依赖 `origin/category/reason_code`。
- `diagnosticRows` 必须由白名单字段生成，不直接渲染任意对象，避免泄露敏感字段或展示过长内容。

### 6.2 用户侧短卡片

新增组件：

```text
frontend/src/shared/platform/PlatformErrorSummary.tsx
```

展示内容：

- 固定标题：
  - `upstream`：上游模型错误
  - `web`：Web 服务错误
  - `web_workstation`：Web 工作站错误
  - `local_workstation`：本机工作站错误
  - `unknown`：任务执行失败
- `message`
- `reasonCode`
- `stepId / stepType`
- `retryable`
- 主要操作按钮：
  - 可重试时显示“重试”
  - 上游错误可显示“切换执行配置”
  - 本机 Workstation 错误可显示“检查本机 Workstation”

用户侧不展示：

- traceback
- 完整 prompt
- 完整响应正文
- API Key / Authorization
- 未清洗的 `diagnostic`

### 6.3 管理端诊断面板

新增组件：

```text
frontend/src/shared/platform/PlatformErrorDiagnostics.tsx
```

展示内容：

- 错误来源：`origin`
- 发生位置：`runtimeSurface`
- 组件：`component`
- 操作：`operation`
- 分类：`category`
- 诊断码：`reasonCode`
- 是否可重试：`retryable`
- 失败步骤：`stepId / stepType`
- 模型：`model`
- HTTP 状态：`httpStatus`
- 运行器：`runnerType`
- API 协议：`apiProtocol`
- 建议查看：`logHint.primary / logHint.secondary`
- 开发诊断：`developerMessage`
- 折叠诊断表：`diagnosticRows`

诊断面板默认折叠详细诊断，只展开摘要字段。

### 6.4 全局通知展示

新增或改造组件：

```text
frontend/src/shared/platform/PlatformErrorNotice.tsx
```

展示内容：

- 第一行：`生成失败：{title}`
- 第二行：`message`
- 可点击时跳转任务详情或运行状态诊断页。

全局通知不展示长诊断。

### 6.5 首批接入页面

一次性收口时必须接入以下入口：

| 入口 | 改造目标 |
| ---- | ---- |
| 用户中心任务历史/详情 | 使用 `PlatformErrorSummary` 展示失败原因 |
| 管理端任务/执行详情 | 使用 `PlatformErrorDiagnostics` 展示完整诊断 |
| 管理端运行状态页 | Workstation / Web Workstation 相关错误使用统一来源标签 |
| 管理端知识库包页 | 本机 Workstation 导出、Web 上传/激活失败使用统一解析 |
| 全局通知 `StatusNoticeStack` | 使用 `PlatformErrorNotice` 展示平台任务失败 |

## 7. 改造范围

### 7.1 后端共享错误模型

新增模块建议：

```text
backend/app/modules/platform/errors/
  execution_error.py
```

职责：

- 定义 `PlatformErrorEnvelope`。
- 定义 `PlatformExecutionError` 异常类型。
- 提供 `to_error_payload()`、`from_exception()`、`with_step_context()` helper。
- 提供敏感信息截断和清洗 helper。

### 7.1.1 执行配置模型收口

项目未上线，本项不做旧字段兼容迁移，直接收口正式概念：

- 后端 contract、数据库模型、repository、service、前端表单统一把 `agent_backend` 改为 `runner_type`。
- 后端 contract、数据库模型、repository、service、前端表单统一把 `provider` 改为 `api_protocol`。
- 后端 contract、数据库模型、repository、service、前端表单统一把 `base_url` 改为 `api_base_url`。
- 当前本地开发库和测试库可以通过重建或一次性迁移脚本处理，不保留双字段读写。
- 文档和 UI 必须明确：第三方地址可以使用，但必须填写对应协议的 API base URL。

健康检查规则：

- `api_protocol=openai_compatible`：至少确认目标不是 HTML 页面；若网关支持 `/models`，优先检查 `/models` JSON；若不支持 `/models`，返回明确的“无法确认，但不是 HTML”的降级诊断。
- `api_protocol=anthropic_compatible`：按 Anthropic-compatible 请求规则检查，不复用 OpenAI-compatible 路径。
- `runner_type=api`：健康检查失败时不得作为 healthy routable target。
- `runner_type=codex_cli` / `claude_cli`：健康检查同时检查 CLI 环境可用性与凭据协议提示。

### 7.2 ExecutionAdapter

改造目标：

- 所有失败都必须返回非空 `error_payload`。
- 已经是 `PlatformExecutionError` 的异常原样转 envelope。
- 普通异常统一包装为当前运行面的 `internal_error`。
- 自动补充 `step_id`、`step_type`、`job_id`、`job_item_id`、`execution_id`。

当前运行面来源：

- Web 本地执行：`runtime_surface=web`。
- Web 托管 Workstation 内执行：`runtime_surface=web_workstation`。
- 本机 Workstation 内执行：`runtime_surface=local_workstation`。

### 7.3 WorkstationExecutionClient

改造目标：

- 仅负责 Web 到 Workstation 的通信边界错误。
- 派发失败、轮询失败、token 错、响应非 JSON 均归为 `origin=web_workstation`，`runtime_surface=web`。
- Workstation 返回的执行失败不重包为 `workstation_dispatch_failed`，应保留原 envelope，仅补 Web 侧可见的 dispatch / poll 诊断字段。

### 7.4 WorkstationPlatformExecutor

改造目标：

- 托管 Workstation 执行入口注入 `runtime_surface=web_workstation`。
- 内部 step 产生的上游错误保留 `origin=upstream`。
- 执行器自身异常包装为 `origin=web_workstation`。
- `events` 中也携带当前 step 的错误摘要和 `reason_code`，便于任务进度流定位失败点。

### 7.5 text_generate_handler 与上游分类

改造目标：

- `upstream_error_classifier.py` 输出统一 envelope 或统一分类对象。
- `text_generate_handler` 将 LiteLLM、OpenAI-compatible direct、Codex CLI、Claude CLI 错误全部转为 `origin=upstream`。
- 调用方注入 `runtime_surface`，避免把 Web Workstation 内触发的上游错误误判成 Workstation 自身错误。
- 保留 `runner_type/api_protocol/model/http_status/provider_error_code/retryable` 等诊断字段。
- LiteLLM 初始失败后进入 direct HTTP fallback 时，若 fallback 也失败，最终异常必须保留初始错误和最终错误，写入 `diagnostic.initial_error`、`diagnostic.final_error` 与 `diagnostic.upstream_attempts`。
- direct HTTP fallback 的 endpoint 摘要可以记录，但必须剥离凭据、token、query secret。

协议不匹配判定：

- `api_protocol=openai_compatible` 请求返回 `text/html`，优先归类为 `upstream_protocol_mismatch`。
- OpenAI-compatible 请求返回非 HTML 但不是 JSON，归类为 `upstream_invalid_response`。
- Anthropic-compatible 请求走到了 OpenAI-compatible 路径属于代码配置错误，开发期应由测试阻断。

### 7.6 前端与管理端

改造目标：

- 任务失败展示按 `origin` 分组：
  - 上游模型错误
  - Web 服务错误
  - Web 工作站错误
  - 本机工作站错误
- 管理端详情展示：
  - `origin`
  - `runtime_surface`
  - `component`
  - `operation`
  - `category`
  - `reason_code`
  - `step_id / step_type`
  - `retryable`
  - `log_hint`
  - `diagnostic`
- 普通用户页只展示 `message` 和可行动建议，不展示 traceback 和敏感诊断。
- 所有页面复用 `toPlatformErrorView()`，不得直接在页面里用字符串包含判断错误类型。

## 8. 一次性前后端实施计划

本项必须作为一次完整收口推进：后端 envelope、跨进程传递、前端解析与展示组件、接口文档同步应在同一任务中完成。可以分 commit 或分小步验证，但不交付“后端已分清、前端仍旧展示”的中间状态。

### 阶段零：执行配置概念重命名

目标：

- 用 `runner_type` / `api_protocol` / `api_base_url` 替换 `agent_backend` / `provider` / `base_url`。
- 更新后端 contract、数据库模型、repository、service、执行路由、文本 runner 入参。
- 更新管理端执行配置和服务器凭据表单。
- 更新本地测试数据和文档，不保留旧字段兼容层。

验收：

- 代码中平台执行配置主链路不再使用 `agent_backend` / `provider` / `base_url` 作为正式概念。
- UI 不再出现“服务器商=openai”这种容易误导的字段，改为“API 协议=OpenAI-compatible”。
- `runner_type=api` 时必须选择 `api_protocol`。
- `api_protocol=openai_compatible` 的健康检查能识别 HTML 网页入口。
- `api_protocol=anthropic_compatible` 不会拼 `/chat/completions`。

### 阶段一：错误模型和前端视图模型落地

目标：

- 新增统一错误 envelope。
- 新增 helper 和单元测试。
- 新增前端 `toPlatformErrorView()` 与类型。
- 新增 `PlatformErrorSummary`、`PlatformErrorDiagnostics`、`PlatformErrorNotice` 的基础组件。
- 不改业务流程，只建立可复用结构。

验收：

- helper 能从普通异常生成 `web_internal_error`。
- helper 能保留已有 `PlatformExecutionError`。
- 敏感字段清洗测试覆盖 API Key、Authorization、prompt。
- 前端解析函数能把 `platform_error.v1` 转为稳定 UI 模型。
- 前端组件能在最小示例数据下渲染四类来源。

### 阶段二：平台执行主链路收口

目标：

- 改 `ExecutionAdapter`。
- 改 `WorkstationExecutionClient`。
- 改 `WorkstationPlatformExecutor`。
- 保证 Web、Web Workstation、本机 Workstation 运行面可区分。

验收：

- Workstation 不可达返回 `origin=web_workstation`、`runtime_surface=web`、`reason_code=web_workstation_unreachable`。
- 托管 Workstation 内部未分类异常返回 `origin=web_workstation`、`runtime_surface=web_workstation`。
- Web 本地未分类异常返回 `origin=web`、`runtime_surface=web`。
- 前端任务失败入口能用同一组件展示以上三类错误。

### 阶段三：上游 LLM 错误统一

目标：

- 改 `text_generate_handler` 与 `upstream_error_classifier`。
- OpenAI-compatible direct 非 JSON、429、401/403、content filter、CLI timeout 全部输出统一 envelope。
- LiteLLM + direct fallback 双失败时保留完整错误链。

验收：

- 托管 Workstation 内上游 429 返回 `origin=upstream`、`runtime_surface=web_workstation`。
- Web 本地上游 429 返回 `origin=upstream`、`runtime_surface=web`。
- OpenAI-compatible 空响应返回 `upstream_invalid_response`，诊断中有 status、content-type、body tail，且无 key 和 prompt。
- OpenAI-compatible 请求返回 HTML 页面时返回 `upstream_protocol_mismatch` 或明确的 `upstream_invalid_response` 诊断，管理端能看出是协议/API base URL 不匹配。
- 同一错误 payload 中能看到 LiteLLM 初始错误和 direct fallback 最终错误摘要。
- 前端用户侧显示“上游模型错误”，管理端显示 runtime surface 与上游诊断，不把它展示为 Workstation 自身错误。

### 阶段四：页面接入、通知接入与文档同步

目标：

- 管理端任务详情按 `origin/runtime_surface` 展示。
- 用户侧失败提示收敛为可行动文案。
- `StatusNoticeStack` 接入统一 notice。
- 管理端知识库包页和运行状态页接入本机 / Web Workstation 错误来源展示。
- 更新接口文档。

验收：

- 管理端能直接看出应该查 Web 日志、Web Workstation 日志、本机 Workstation 还是上游配置。
- 旧的纯 `error_summary` 不再作为主展示来源。
- `docs/02-现状/当前前后端接口文档.md` 同步记录 `platform_error.v1`。
- 前端页面不再各自用字符串匹配判断平台任务错误类型。

## 9. 验收场景

必须覆盖：

1. Web 托管 Workstation 没启动。
2. Web 托管 Workstation token 缺失或错误。
3. Web 托管 Workstation 已接单，但内部 step 抛普通异常。
4. Web 托管 Workstation 内 Codex CLI 缺失。
5. Web 托管 Workstation 调上游模型 429。
6. Web 托管 Workstation 调 OpenAI-compatible 网关返回空 body。
7. Web 后端自身数据库或任务状态写入失败。
8. 浏览器请求本机 Workstation 失败。
9. 本机 Workstation 导出知识库失败。
10. 上游 content filter。
11. `api_protocol=openai_compatible` 但 `api_base_url` 填了第三方网页入口，返回 HTML。
12. LiteLLM 初始解析失败后 direct HTTP fallback 也失败。
13. `runner_type=api` 但未选择 `api_protocol`。

每个场景都必须断言：

- `origin`
- `runtime_surface`
- `runner_type`
- `api_protocol`
- `category`
- `reason_code`
- `step_id` 或 `component`
- `retryable`
- `log_hint`
- 前端用户侧标题
- 前端管理端诊断字段
- 全局通知短消息

## 10. 风险与约束

- 分类规则不能过宽，否则会把真实 Web Workstation 环境错误误判为上游错误。
- `developer_message` 与 `diagnostic` 必须持续清洗敏感字段。
- 前端不能依赖自然语言 `message` 判断错误类型，只能依赖 `origin/category/reason_code`。
- `internal_error` 只能作为兜底，不应成为常态；每次真实排障发现高频 `internal_error`，都应补细分 reason_code。
- 前端诊断面板不能直接渲染任意 `diagnostic` 对象，必须通过白名单转 `diagnosticRows`。
- 后端和前端必须同一轮交付；不接受只改后端不改展示，或只改前端继续猜字符串。
- 项目未上线，字段重命名不保留兼容层；风险是本地已有数据库和测试夹具需要重建或一次性调整。
- 第三方网关健康检查接口不完全统一，健康检查应以“协议明显不匹配必须失败，无法确认时给明确诊断”为原则，避免误杀合法网关。

## 11. 完成标准

- 平台执行失败统一输出 `schema_version=platform_error.v1`。
- 新失败不再出现空 `error_payload`。
- 执行配置正式字段统一为 `runner_type` / `api_protocol` / `api_base_url`。
- 用户无法在 UI 中配置出语义混乱的“Claude 运行器 + OpenAI 服务器商 + Claude base_url”组合；如果要配置第三方 OpenAI-compatible 或 Anthropic-compatible 网关，必须选择对应 API 协议。
- 管理端能明确区分：
  - 本地 Workstation 报错
  - Web 报错
  - Web 托管 Workstation 报错
  - 上游报错
- Web Workstation 内触发的上游错误能同时展示 `runtime_surface=web_workstation` 与 `origin=upstream`。
- 上游错误保留脱敏后的错误链，管理端能看到初始错误和最终错误摘要。
- 前端统一使用 `toPlatformErrorView()`、`PlatformErrorSummary`、`PlatformErrorDiagnostics`、`PlatformErrorNotice`。
- 用户侧、管理端、全局通知对同一个错误展示一致的来源判断。
- 相关局部测试覆盖并通过。
- 接口文档和后端专题索引同步更新。
