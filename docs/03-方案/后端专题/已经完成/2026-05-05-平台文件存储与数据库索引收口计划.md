# 平台文件存储与数据库索引收口计划

> 文档定位：本文规划平台上传资产、服务器工作区与任务产物的存储模型收口，不负责具体代码实现细节。
>
> 事实依据：基于 2026-05-05 对 `asset.generate` 读取上传图片失败的日志、当前代码与部署模板调查。
>
> 权威入口：上级入口为 `docs/03-方案/后端专题/README.md`。
>
> 最后更新：2026-05-06

## 当前状态

已完成。

Web 托管执行链路中，Web 容器负责创建任务、上传文件、创建服务器工作区，并在派发给 `web-workstation` 前把运行时引用解析成容器内绝对路径。

当前关键路径包括：

- 上传资产：`runtime/web/platform-upload-assets/{user_id}/{token}/content.*`
- 服务器工作区：`runtime/web/platform-workspaces/{user_id}/{token}/{project_name}`
- Workstation 产物：`runtime/web-workstation/platform-artifacts/...`
- 共享知识库：`runtime/knowledge`

数据库当前已记录任务、执行、产物等业务元数据；`artifacts` 表包含 `user_id`、`job_id`、`artifact_type`、`storage_provider`、`object_key` 等字段。但上传资产仍主要依赖文件夹中的 `metadata.json`，没有独立数据库索引表。

## 已确认问题

### 1. 跨容器传递绝对路径不可靠

Web 侧会把 `uploaded_asset_path` 解析为 `/app/runtime/platform-upload-assets/...` 后传给 `web-workstation`。但 Web 与 `web-workstation` 的 `/app/runtime` 分别挂载到不同宿主目录：

- Web：`runtime/web`
- web-workstation：`runtime/web-workstation`

因此相同的 `/app/runtime/...` 字符串在两个容器内指向不同文件系统，导致 `asset.generate` 在 Workstation 侧读取不到 Web 侧上传文件。

### 2. 同类风险不止上传资产

`server_workspace_root` 也由 Web 侧解析为 `/app/runtime/platform-workspaces/...`，随后被 `code.generate`、`asset.generate`、`build.project`、`package.project` 直接读写。若工作区目录不共享，即使修复上传资产目录，也会继续在代码生成、资源生成、打包或下载阶段暴露同类问题。

`platform-artifacts` 也存在 Web 与 Workstation 各写一份同名目录的风险。方案文档、源码 zip、构建产物等记录在数据库中，但实际文件可能只存在某一个执行面。

### 3. 文件归属与权限应由数据库表达

当前接口层下载产物时会按 `artifact_id + user_id` 查询数据库，具备用户级访问控制。但上传资产缺少同等数据库记录，仍主要靠 `{user_id}/{token}` 文件夹结构和服务层访问约束表达归属。

文件夹隔离是必要的物理组织方式，但不应成为唯一权限真源。

## 目标方案

采用“数据库做真源索引，文件存储做内容载体”的主线。

### 存储根收口

新增或收口为统一平台共享运行时根：

```text
runtime/platform/
  uploads/{user_id}/{asset_id}/content.ext
  workspaces/{user_id}/{workspace_id}/{project_name}/...
  artifacts/{user_id}/{artifact_id}/...
```

Docker 部署中，Web 与 `web-workstation` 都把该目录挂载到同一个容器路径：

```text
runtime/platform -> /app/runtime/platform
```

保留 `runtime/web` 与 `runtime/web-workstation` 作为角色私有运行目录，但不再承载需要跨 Web 与 Workstation 共同读写的平台业务文件。

### 数据库索引

上传资产新增数据库记录，建议表为 `uploaded_assets`：

```text
uploaded_assets
- id
- uploaded_asset_ref
- user_id
- file_name
- mime_type
- size_bytes
- storage_provider
- object_key
- sha256
- created_at
- deleted_at
```

`artifacts` 表继续作为任务产物索引，但 `object_key` 不再存容器绝对路径，改存相对对象键，例如：

```text
artifacts/1/123/source.zip
uploads/1/456/content.png
workspaces/1/789/mod2
```

业务层通过 `storage_provider + object_key` 解析实际文件路径。接口、runner、下载逻辑不再把 `/app/runtime/...` 绝对路径作为跨进程协议字段。

## 文件是否入库的边界

不建议把大文件内容直接放进数据库。

适合入库的内容：

- 小型 Markdown 方案文本
- 小型 JSON 元数据
- 审计摘要、hash、状态、错误信息

不适合入库的内容：

- 上传图片
- 源码 zip
- `.dll`、`.pck` 构建产物
- 服务器工作区目录
- 未来可能较大的资源包

原因：

- 执行端需要真实文件路径供 PIL、zip、Godot、dotnet 等工具读取。
- 大二进制会放大数据库备份、迁移、连接与查询压力。
- 文件系统或对象存储更适合承载大对象内容。
- 数据库存索引后，未来迁移到 MinIO、S3 或其他对象存储时更自然。

## 不保留兼容层

当前项目尚未正式上线，本计划不要求保留旧路径兼容层。

后续实现可以直接收口到新目录与新表结构：

- 不再读取旧 `runtime/web/platform-upload-assets`
- 不再读取旧 `runtime/web/platform-workspaces`
- 不再读取旧 `runtime/web-workstation/platform-artifacts`
- 不再依赖上传目录内 `metadata.json` 作为主数据源

如需保留当前本地调试数据，应在实施前做一次性人工备份或一次性迁移脚本；迁移完成后，新实现不保留双写或双读。

## 实施计划

### 阶段一：定义统一对象存储接口

- 新增平台文件对象 key 规范。
- 定义 `storage_provider` 的当前主值，例如 `platform_fs`。
- 定义从 `object_key` 到本地共享根路径的解析规则。
- 明确禁止跨进程 payload 传递容器绝对路径。

### 阶段二：上传资产入库

- 新增 `uploaded_assets` 表和仓储。
- 上传接口写入共享文件目录，同时写入数据库记录。
- `uploaded_asset_ref` 继续作为外部引用，但解析时必须查数据库并校验 `user_id`。
- `uploaded_asset_path` 只在执行端本地解析后产生，不作为 Web 到 Workstation 的协议字段。

### 阶段三：工作区与产物路径收口

- `ServerWorkspaceService` 默认根迁到 `runtime/platform/workspaces`。
- `PlanArtifactService` 默认根迁到 `runtime/platform/artifacts`。
- `package_project`、`build_project` 产物的 `object_key` 改为相对 key。
- 下载接口按数据库记录解析共享文件路径，并继续按 `user_id` 鉴权。

### 阶段四：部署模板收口

- `compose.app.yml` 新增共享平台运行时挂载。
- `deploy-app.ps1` 生成 `ATS_PLATFORM_RUNTIME_DIR`。
- 移除平台业务文件对 `ATS_WEB_RUNTIME_DIR` 与 `ATS_WEB_WORKSTATION_RUNTIME_DIR` 的依赖。
- 保留 `runtime/knowledge` 当前共享挂载策略，避免把知识库问题混入本次收口。

### 阶段五：测试与文档同步

- 补上传资产按用户隔离的测试。
- 补 Web 派发 Workstation 时只传 ref/key、不传绝对路径的测试。
- 补 source zip 与 plan markdown 下载测试。
- 补 Docker compose 共享平台运行时挂载测试。
- 同步更新当前接口文档、部署说明和后端专题索引。

## 验收标准

- 上传图片后，数据库存在 `uploaded_assets` 记录，文件存在共享平台运行时目录。
- 用户只能访问自己的上传资产和任务产物。
- Web 派发给 `web-workstation` 的 payload 不包含跨容器绝对文件路径。
- `single_generate/relic` 上传图链路能完成 `single.asset.plan -> asset.generate -> package.project`。
- 源码 zip、方案 Markdown 等产物能从 Web 端下载。
- Web 与 `web-workstation` 容器重启后，上传资产、工作区和产物仍可访问。
- `runtime/web` 与 `runtime/web-workstation` 不再出现新的 `platform-upload-assets`、`platform-workspaces`、`platform-artifacts` 业务写入。

## 风险与注意事项

- 这是跨 API、数据库、runner、部署模板和下载接口的横向收口，不能只改单点路径。
- 若只共享 `platform-upload-assets`，会留下 `server_workspace_root` 与 `platform-artifacts` 的同类问题。
- 若把大文件放入数据库，会增加数据库体积和执行端落盘转换复杂度，不推荐作为主线。
- 若继续传容器绝对路径，后续迁移到多机、多容器或对象存储会再次失败。

## 建议优先级

优先级应高于单项资产生成 bug 修补。

原因是本问题已经影响上传图驱动的服务器生成主链路，并且同类风险覆盖工作区、产物下载和后续打包交付。建议作为“平台文件存储与对象索引收口”独立任务推进，不并入普通错误处理或 UI 体验任务。
