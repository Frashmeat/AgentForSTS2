# Item 清单编辑与 AI 审查体验改造计划

> 文档定位：本文定义批量 Mod 规划中 Item 复核阶段的后续改造方案，重点解决用户无法自由调整 Item、耦合类型难懂、AI 审查入口不明确的问题。
>
> 事实依据：基于 2026-05-05 人工反馈、当前 `frontend/src/features/batch-generation/ReviewPlan.tsx`、`ReviewBundles.tsx` 与批量规划 review 流程整理。
>
> 权威入口：上级入口为 `docs/03-方案/前端稳定化/README.md`；执行策略历史口径见 `docs/90-归档/后端专题/已经完成/2026-04-12-复杂Mod执行策略决策引导升级实施计划.md`。
>
> 最后更新：2026-05-05

## 当前状态

已落地基础版，后续可继续补充更细的“AI 帮我补全单个 Item”能力。

当前已先做一轮小范围 UI 收口：

- Item 复核阶段新增显式入口 `让 AI 重新审查 Item`。
- 执行策略阶段去掉底部重复主动作，只保留顶部唯一主动作。

本文描述的是下一步更完整的 Item 清单编辑能力。

## 目标

- 让用户在 Item 复核阶段可以自由新增、删除、复制和编辑 Item。
- 把工程化的 `relationship_type` 改成用户能理解的 Item 关系表达。
- 明确 AI 在规划阶段的参与边界：AI 生成初稿、用户修改清单、用户手动触发 AI 重新审查。
- 用户手动调整 Item 后，执行策略 bundle 必须基于最新 Item 清单重新计算。

## 不纳入范围

- 不做拖拽式 bundle 编排。
- 不让用户在执行策略阶段任意手工重组 bundle。
- 不改图片生成、代码生成、审批和执行阶段主流程。
- 不保留旧字段兼容包袱；项目尚未正式上线，字段可以收口到新口径。

## 推荐产品口径

### 1. Item 清单是用户可编辑草稿

AI 生成的 Mod 计划不应被视为最终结果，而是一个可编辑草稿。

用户在 Item 复核阶段应能执行：

- 新增 Item
- 删除 Item
- 复制 Item
- 修改类型、名称、目标、描述、范围、验收说明
- 调整 Item 与其他 Item 的关系

用户编辑优先级高于 AI 建议。AI 只在用户主动触发审查时给出校验和建议，不自动覆盖用户编辑。

### 2. 用 Item 关系替代耦合类型

现有 `relationship_type` 下拉项过于工程化：

- `unknown`
- `ordered_dependency`
- `same_feature`
- `shared_mechanism`
- `independent`

建议改为用户可理解的关系选项：

| 新显示文案 | 建议内部值 | 含义 |
| --- | --- | --- |
| `不确定关系` | `unknown` | 用户还没想清楚，让 AI 在审查时判断 |
| `独立执行` | `independent` | 这个 Item 可以单独做 |
| `有先后顺序` | `ordered_dependency` | 需要某些 Item 先完成 |
| `同一功能组` | `same_feature` | 多个 Item 属于同一个功能，建议一起考虑 |
| `共享机制或资源` | `shared_mechanism` | 多个 Item 复用同一套逻辑、资源或状态 |

字段建议：

- `relationship_type` 改为 `relationship_type`
- `depends_on_item_ids` 改为 `depends_on_item_ids`
- `relationship_reason` 改为 `relationship_reason`

### 3. 关系需要选择对象

不要只让用户选一个关系类型。根据关系类型展示对应输入：

- `有先后顺序`：显示“需要先完成哪些 Item？”多选已有 Item。
- `同一功能组`：显示“它和哪些 Item 属于同一功能？”多选已有 Item。
- `共享机制或资源`：显示“共享的机制或资源是什么？”文本说明 + 可选关联 Item。
- `独立执行`：隐藏关联 Item 选择。
- `不确定关系`：提示用户可以先保留，后续让 AI 审查。

这样用户是在回答产品问题，而不是填写技术字段。

## AI 参与边界

整个规划阶段 AI 会参与，但必须是显式阶段：

1. `生成初稿`
   - 用户输入 Mod 需求后，AI 生成初始 Item 清单。

2. `用户编辑清单`
   - 用户自由新增、删除、复制、修改 Item。
   - AI 不应在用户编辑过程中自动覆盖内容。

3. `让 AI 重新审查 Item`
   - 用户点击按钮后，前端提交当前 Item 清单。
   - AI / 后端检查字段完整性、关系是否矛盾、哪些 Item 仍需补充。

4. `重新规划执行策略`
   - Item 清单通过后，AI / 后端基于最新清单生成依赖分组和执行 bundle。

5. `执行阶段`
   - 才进入图片生成、代码生成、审批和实际执行。

## 交互设计

### Item 列表顶部

增加操作区：

- `新增 Item`
- `复制当前 Item`（在展开某个 Item 时可用）
- `让 AI 重新审查 Item`

页面提示：

> 你可以先手动调整 Item 清单。调整完成后，点击“让 AI 重新审查 Item”，系统会检查描述完整性和 Item 关系。

### 单个 Item 行

每行建议增加：

- 展开 / 收起
- 复制
- 删除
- 状态徽标
- 依赖或关系摘要

删除时：

- 从清单中移除该 Item。
- 同步清理其他 Item 对它的依赖或关联。
- 提示用户重新触发 AI 审查。

### 新增 Item 默认值

新增 Item 至少需要：

- `id`
- `type`
- `name`
- `description`
- `goal`
- `relationship_type`
- `depends_on_item_ids`
- `relationship_reason`
- `acceptance_notes`

默认建议：

- `type`: `custom_code` 或让用户先选择类型
- `relationship_type`: `unknown`
- `depends_on_item_ids`: `[]`
- 文本字段为空，等待用户或 AI 补充

### 审查结果

AI 审查后应反馈：

- 哪些 Item 可继续
- 哪些 Item 缺少目标、范围、验收说明
- 哪些关系不清楚
- 是否可以进入执行策略决策

不建议在审查时直接改写用户字段。若后续要做“AI 帮我补全这个 Item”，应做成单独按钮，并在覆盖前让用户确认。

## 实施步骤

### Task 1：字段口径与类型收口

- 调整前端类型中的 Item 关系字段。
- 替换 `relationship_type` 下拉项为用户可理解选项。
- 同步后端 plan/review 相关字段口径。
- 更新测试数据与恢复快照字段。

验收：

- 页面不再出现旧关系枚举，用户只看到 `不确定关系 / 独立执行 / 有先后顺序 / 同一功能组 / 共享机制或资源`。
- 新字段名称和显示文案一致。

### Task 2：Item 新增、删除、复制

- 在 `ReviewPlan.tsx` 增加新增、删除、复制操作。
- 删除时清理关联依赖。
- 新增 Item 自动展开，并提示需要 AI 审查。

验收：

- 用户可以从空白或已有计划中新增 Item。
- 删除 Item 不会留下悬空依赖。
- 复制 Item 不会复用原 Item id。

### Task 3：关系对象选择

- 根据关系类型动态显示关联 Item 多选。
- 关系摘要显示在折叠行右侧。
- 保留文本说明字段用于解释关系原因。

验收：

- 用户不需要手写 Item id。
- 关系能被清楚读出，例如“先做 A / 同组 B、C / 共享暗影层数机制”。

### Task 4：AI 审查流程与提示收口

- 明确 `让 AI 重新审查 Item` 是 Item 阶段唯一显式审查入口。
- 用户编辑后展示“清单已修改，建议重新审查”的状态。
- 进入下一步前仍执行 gate，但文案必须提示先审查。

验收：

- 用户知道 AI 何时参与。
- 用户知道修改后为什么要重新审查。
- 审查通过后才能进入执行策略决策。

## 风险

- 字段改名会影响后端 plan 生成、review、执行 payload 和恢复快照。
- 允许新增空 Item 后，严格审查会更频繁拦截，需要文案说明清楚。
- 删除 Item 后如果关联清理不完整，执行策略可能引用不存在的 Item。
- AI 补全如果自动覆盖用户编辑，会造成信任问题；第一版不做自动覆盖。

## 完成标准

- 用户可以自由维护 Item 清单。
- Item 关系表达不再依赖工程化枚举。
- 用户能明确知道“AI 什么时候参与、审查什么、审查后怎么继续”。
- 最新 Item 清单能驱动后续执行策略 bundle 重算。
