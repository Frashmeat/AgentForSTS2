# 统一生成反馈闭环架构方案

## 1. 架构决定

本方案不是 Provider、模型、Character 或 `merge_content` 的兼容性补丁，也不允许本地猜测、转换或接受错误模型输出。

正式方向是在 `ats-features` 建立一套通用的 **Generation Feedback Controller**，把模型输出合同错误和生成文件验证错误纳入同一条 Feature-owned semantic feedback state machine：

```text
Produce
   |
   v
Decode + Output Contract Validation
   |
   +-- repairable diagnostic --------------------+
   |                                              |
   v                                              |
Materialize normalized checkpoint                 |
   |                                              |
   v                                              |
Registered Validation                             |
   |                                              |
   +-- repairable diagnostic --------------------+|
   |                                             ||
   v                                             ||
Ready for commit                                 ||
                                                 ||
             typed feedback <--------------------++
                   |
                   v
             Produce replacement
```

每次模型返回都必须重新通过同一套 strict decode、typed contract、Pack role、path/resource、Truth identity 和完整 validator suite。失败内容不会被“修好后直接采用”，只有模型重新生成且严格验证通过的候选才可以成为 checkpoint。

## 2. 当前缺口

现有系统已经分离了三类责任：

```text
HTTP Adapter
  transport / 429 / 5xx retry + 120s/300s backoff

ExecutionGraph
  node order + claim + checkpoint + pause/resume + atomic publication

Validation-guided repair
  generated files -> registered validators -> complete-role replacement
```

但当前 semantic repair 只在模型输出已经成功解码、规范化为 checkpoint，并进入 registered validation 后生效。更早的输出合同错误仍直接终止节点：

```text
model response
     |
     v
JSON / typed output validation
     |
     +-- json_decode / file_role / merge_content
             |
             v
        graph paused
```

真实 Provider 运行已经证明：HTTP 成功和外层 JSON 可解析，不等于模型一定遵守 run-scoped output contract。`compositionMerge=json_object` role 可能被返回为双重编码字符串、嵌套对象或包含非字符串值。当前 strict rejection 是正确行为；缺少的是拒绝后的确定性反馈控制，而不是更宽松的解析器。

候选、Run ID、模型和逐次失败只属于 Trellis acceptance ledger，不写入本文的稳定设计。

## 3. 目标与非目标

### 目标

- 为所有 Game Pack 和生成型 Feature 提供同一套输出反馈基础能力。
- 让可由模型纠正的 typed output failure 进入有界、可取消、可恢复的语义重调。
- 复用现有 registered-validation repair，不建立第二套平行循环。
- 保持 Provider retry、semantic feedback 和 graph resume 三层语义独立。
- 保持 Pack、Truth、ItemDefinition、Resource、模型配置和 response format 在一个父 Run 内固定。
- 只持久化 typed、bounded、redacted diagnosis 和当前有效 checkpoint。
- 对 repeated/no-progress、证据不足、配置错误和系统错误稳定停止。

### 非目标

- 不兼容或自动转换双重编码 JSON。
- 不从任意文本、Markdown code fence 或 Provider body 猜测结果。
- 不为特定模型、Provider、STS2、Character 或 localization role 写分支。
- 不降低 JSON Schema、Pack role 或 validator 要求。
- 不自动切换模型、endpoint、response format 或 repair policy。
- 不把 transport retry 迁入 Feature。
- 不让模型修复存储、锁、配置、Truth、工具链或发布事务问题。
- 不保存 raw completion、多代生成文件或完整 Prompt 作为恢复数据。

## 4. 三层控制边界

```text
+----------------------------------------------------------------+
| Layer 3: ExecutionGraph                                        |
| node claim / checkpoint / pause / resume / commit intent       |
+-------------------------------+--------------------------------+
                                |
                                v
+----------------------------------------------------------------+
| Layer 2: Generation Feedback Controller                        |
| strict validation / typed diagnosis / policy / semantic round  |
+-------------------------------+--------------------------------+
                                |
                                v
+----------------------------------------------------------------+
| Layer 1: Model Adapter + shared FIFO ModelRequestQueue          |
| HTTP attempt / timeout / Retry-After / transport backoff        |
+----------------------------------------------------------------+
```

### Layer 1：Provider reliability

- 一个模型逻辑调用持有共享 FIFO 席位，直到其 HTTP attempts 成功、耗尽或取消。
- 只重试 transport、rate limit 和受支持的 Provider server failure。
- Adapter 不理解 `merge_content`、Card、Character 或 generated file。
- Adapter 耗尽后返回 typed `ModelError`，不得自行创建 semantic round。

### Layer 2：Semantic feedback

- 接收 Feature 产生的可信 typed diagnostic。
- 判断 repairability、round budget 和 stop condition。
- 生成 versioned、bounded、redacted feedback envelope。
- 通过同一个 `ModelClient` 和共享 FIFO 发起下一次模型逻辑调用。
- 对新候选重新执行完整严格流水线。

### Layer 3：Durable execution

- graph 决定哪个节点可以运行，以及成功 checkpoint 是否可复用。
- semantic round 是一次 node attempt 内部的受控状态，不等于用户 Resume。
- semantic feedback 耗尽或安全停止时，节点回到 pending，graph paused。
- 用户显式 Resume 创建新的父 Run，只重试失败节点。

## 5. 统一状态机

每个生成节点采用同一套阶段，不按 ItemType 或模型拆分：

```text
claimed
  |
  v
producing
  |
  +-- provider failure --------------------------> paused
  |
  v
decoding
  |
  +-- repairable output diagnostic --+
  +-- non-repairable/system failure -> paused
  |                                  |
  v                                  |
normalizing                          |
  |                                  |
  v                                  |
checkpointed                         |
  |                                  |
  v                                  |
validating                           |
  |                                  |
  +-- repairable content diagnostic -+
  +-- local/system failure ----------------------> paused
  |
  v
ready_for_commit

feedback path:
  diagnostic -> policy -> feedback envelope -> producing
```

`checkpointed` 只表示候选已经通过输出合同、可以确定性恢复，不表示完整工程验证已经通过。`ready_for_commit` 才允许创建 `commit_prepared`。

## 6. Typed diagnostic

内部诊断使用闭集 enum，不通过错误字符串驱动控制流：

```text
GenerationDiagnostic
+-- Provider
|   +-- TransportExhausted
|   +-- RateLimitExhausted
|   +-- InvalidProviderResponse
|
+-- OutputContract
|   +-- Truncated
|   +-- JsonDecode
|   +-- FileCount
|   +-- AcceptanceNotes
|   +-- FileRole
|   +-- FileContent
|   +-- MergeShape
|
+-- GeneratedContent
|   +-- ValidationIssues[]
|
+-- System
    +-- Configuration
    +-- TruthInsufficient
    +-- CheckpointMismatch
    +-- Storage
    +-- Cancellation
    +-- Publication
```

这不是新的公共错误大杂烩。现有稳定 `RunFailure` code/stage 继续作为 Shell 和持久化失败边界；`GenerationDiagnostic` 是 Feature 内部的控制类型，并按需要投影成 versioned safe details。

### OutputContractDiagnostic

输出诊断只能引用 Pack 已声明并由本地验证过的 role ID：

```text
OutputContractDiagnostic
+-- code
+-- expected contract fragment
+-- optional trusted roleId
+-- observedShape
+-- diagnosticFingerprint
+-- candidateSha256
```

`observedShape` 只描述结构，不保存值：

```text
missing
string
json_encoded_string
object_with_nested_value
object_with_non_string_value
array
number
boolean
null
unparseable
```

未知的模型自造 role、原始 JSON fragment、parser message 和 completion text 不进入诊断或 Run。

`candidateSha256` 只对本次完整 completion bytes 做 SHA-256，用于区分“同一诊断下模型给出了不同候选”和“完全相同候选重复出现”。它不允许反向作为模型输入，也不替代 strict validation。原始 completion 仍不持久化。

### Repairability

| 诊断来源 | 默认处理 |
| --- | --- |
| Provider transport/rate limit/invalid response | Adapter 有界重试；耗尽后暂停，不进入 semantic feedback |
| OutputContract 可确定纠正的 shape/count/role/content 错误 | 进入 feedback controller |
| Registered validator 的 generated-content issue | 进入同一 feedback controller |
| local environment / configuration / storage / lock | 暂停，不调用模型 |
| Truth 证据不足或 ownership 不唯一 | 暂停，不调用模型 |
| checkpoint/provenance/publication mismatch | 暂停，不调用模型 |
| cancellation | 取消优先，完成清理后终态 |

## 7. Feedback envelope

反馈不是自由拼接的异常文本，而是由 Feature 使用可信合同编译出的 versioned payload：

```json
{
  "schema": {
    "id": "feature.generation-feedback",
    "version": 1
  },
  "payload": {
    "phase": "output_contract",
    "round": 1,
    "mode": "regenerate_complete_bundle",
    "diagnostics": [
      {
        "code": "merge_shape",
        "roleId": "localization.eng",
        "expectedShape": "flat_string_object",
        "observedShape": "json_encoded_string"
      }
    ]
  }
}
```

反馈请求同时复用首次生成已经固定的：

- run-scoped output schema；
- Pack contribution 和 role declarations；
- ItemDefinition、reference/resource bindings；
- Truth evidence；
- project context；
- model execution profile。

反馈只说明上次候选违反了哪条可信合同，不把上次 raw output 回灌给模型。

### 两种生成模式

统一 controller 支持两种明确模式，而不是自由格式 patch：

```text
regenerate_complete_bundle
  用于 checkpoint 前的 output-contract failure；重新返回完整 bundle。

replace_complete_roles
  用于 checkpoint 后、可唯一归因的 generated-content failure；
  返回受影响 Item 的全部声明 role，随后完整重建和复验。
```

两种模式共用 policy、round、diagnostic、FIFO、取消和停止条件。差异只来自当前流水线阶段和 Feature 编译出的 typed request。

## 8. Attempt 与策略

必须区分三个计数：

```text
Node attempt
  graph claim / 用户 Resume 维度

Semantic round
  一个 node attempt 内，严格验证失败后的反馈重调维度

HTTP attempt
  一个模型逻辑调用内，Adapter transport retry 维度
```

示例：

```text
node attempt 4
+-- semantic round 0
|   +-- HTTP attempt 1 -> valid response -> merge_shape
+-- semantic round 1
    +-- HTTP attempt 1 -> valid response -> succeeded
```

### RepairPolicy

现有 `repairPolicy` 扩展为整个 generation feedback cycle 的不可变策略，而不再只表示 post-generation validator repair：

```text
max_rounds(1..20)
until_passed
```

- 策略在父 Run request snapshot 中固定。
- 一个父 Run 内不得更换模型、endpoint、format 或 policy。
- policy 是整个 Composition Generate Graph 的 semantic-round 总预算，与当前 registered-validation repair 语义一致；不得把 `max_rounds(3)` 放大为每个节点各 3 轮。
- 不新增 `none` wire variant。直接 `mod.generate.single` 继续保持单次严格生成；只有携带现有 `repairPolicy` 的 Composition Generate 进入反馈控制器。
- `max_rounds` 耗尽后以 typed `repair_exhausted` 暂停。
- `until_passed` 仍受所有安全停止条件和 Graph 总计 20 轮绝对上限约束，不表示无限请求。

### 安全停止条件

以下任一条件成立时不得继续请求模型：

- 相同 diagnostic fingerprint 与相同 candidate SHA-256 重复；
- generated-content replacement bytes 未变化；
- 相同 checkpoint hash 上重复相同 validator fingerprint；
- Truth evidence 不足；
- 诊断不能唯一归因到一个 owning node；
- repair policy 耗尽；
- Provider retry 耗尽；
- 配置、存储、锁、工具链或 publication failure；
- cancellation、项目关闭或进程恢复冲突。

diagnostic fingerprint 只由可信 role、JSON 类型路径和诊断 code 计算；candidate SHA-256 只用于判断完整候选是否逐字节重复。两者必须同时相同才属于 checkpoint 前 no-progress。任何一项都不用于恢复模型内容。

## 9. 持久化与破坏性升版

本方案需要明确表达 checkpoint 前 feedback state，不能含糊复用当前只面向 registered validation 的字段。因此实施时直接以 `ExecutionGraphRecord v3` 替换 v2：

```text
ExecutionNodeRecord v3
+-- nodeId / roleId / dependsOn
+-- status
+-- attemptCount / activeAttempt
+-- activeCheckpoint
+-- feedbackState
|   +-- round
|   +-- phase
|   +-- latestDiagnosticFingerprint
|   +-- latestCandidateSha256
|   +-- optional activeCheckpointHash
|   +-- feedback: versioned + hashed safe envelope
+-- safeFailure
+-- requestSnapshotHash
```

持久化边界：

- 只保留当前 normalized checkpoint，不保留多代候选。
- checkpoint 前失败没有伪 checkpoint。
- feedback model call 发出前，round、phase、fingerprints 和完整 safe feedback envelope 必须先通过 revision CAS 落盘；进程恢复后 owning Feature 可以精确重建同一请求，而不是退回无反馈首轮或猜测诊断。
- 不保存 raw completion、Provider body、完整 Prompt、parser text 或绝对路径。
- feedback state 必须随 graph revision CAS 原子更新。
- semantic round 成功后更新当前 checkpoint 和 feedback state；失败暂停时保留 safe diagnostic fingerprint。
- HTTP attempt count 只进入 bounded model-call summary/本地 tracing，不参与 graph node 状态转换。
- `commit_prepared` 后不再允许进入 feedback。

### 不迁移旧 graph

用户已允许破坏性变更。v3 实施不提供：

- v2 -> v3 migration；
- dual read / dual write；
- 旧 checkpoint compatibility adapter；
- 根据旧 failure 猜测 feedback state；
- 隐式删除旧证据。

旧 graph 保留为不可恢复证据并返回稳定 incompatible-schema。新验收必须创建全新 Graph/Run/Artifact；旧 candidate 同时失效。

### 审查结论：为什么必须升 v3

当前 v2 已有 `repairRound`、diagnostic fingerprint、checkpoint hash 和 `Repairing` 状态，这些能力必须复用；但 v2 强制 diagnostic state 依附一个已存在的 checkpoint，无法表达 checkpoint 前 output-contract feedback。用 request hash、零 hash 或空 checkpoint 代替会混淆“待纠正候选”和“已验证候选”，形成恢复语义债。

因此 v3 只扩展通用 node feedback state，并沿用 v2 的 DAG、CAS、claim、checkpoint、repair、commit 和 recovery 主体。升版不是为了重写 Graph，也不允许把 Provider 或 Feature 专用 enum 下沉到 Runtime。

## 10. 模块职责与代码落点

| 模块 | 新增或调整职责 | 明确不负责 |
| --- | --- | --- |
| `ats-runtime` | ExecutionGraph v3 通用 feedback state、versioned payload/hash、取消和 provider-neutral ports | ItemType、Pack role、feedback 文案 |
| `ats-features::generation_feedback` | policy、round、repairability、stop conditions、feedback envelope 和统一 controller | HTTP retry、文件系统事务 |
| `ats-features::mod_generate_single` | strict decode、run-scoped contract validation、OutputContractDiagnostic、完整 bundle 重生成 | Provider 特判、宽松解析 |
| `ats-features::composition_generate` | graph node ownership、checkpoint CAS、finalize/validator diagnosis 接入和 commit gate | 重复实现 feedback policy |
| `ats-game-context` / Pack | 声明 generated role、merge shape、schema 和 repair guidance | retry、模型选择、错误转换 |
| `ats-adapters::model_client` | FIFO、HTTP timeout、Retry-After、transport retry、safe attempt summary | semantic retry、schema 降级 |

## 11. UI 与可观察性

UI 不显示模型原文，只显示可信执行状态：

```text
GENERATING
item.000.single
semantic round 1 / max 3
correcting output contract
```

暂停时显示稳定原因和动作：

```text
PAUSED
output contract did not converge
last reason: merge_shape
action: Resume / change configuration / inspect Run
```

运行历史至少能区分：

- node attempt；
- semantic round；
- HTTP attempts；
- diagnostic phase/code；
- stop reason；
- 使用的模型身份和 response format；
- 是否创建或替换 checkpoint。

API key、URL query、Provider body、raw completion、绝对路径和任意 parser/compiler 文本继续禁止进入 IPC 与持久化 Run details。

## 12. 实施顺序

当前落地说明：ExecutionGraph 已升为 v3，Composition Generate request 已升为 v4、Blueprint 已升为 v2；Result、Artifact extension 和节点 checkpoint 的 JSON 形状未变化，因此未做无事实依据的升版。旧非持久化 `CompositionGenerateService::execute` 路径已删除，生产与机器测试统一使用 durable staged Graph API。

### Phase 1：合同与破坏性 schema

1. 定义 closed diagnostics、feedback envelope、Graph 级 policy 和 stop reason。
2. 定义 ExecutionGraphRecord v3 / node feedback state。
3. 升版 Composition Generate request/result/blueprint/checkpoint schema。
4. 更新 Shell runtime validators 和 UI typed state。
5. 先用 contract tests 锁定 JSON wire shape、redaction 和 incompatible-schema 行为。

### Phase 2：输出合同诊断

1. 将 `GeneratedModBundle` decode/validation 从“reason enum 终止”重构为可信 typed diagnostic producer。
2. 为 JSON decode、file count/role/content、merge shape 和 truncation 建立确定性 fingerprint。
3. 保持现有 `RunFailure` code/stage 投影兼容当前 Shell 语义；不保存 raw output。
4. 建立完整 bundle feedback request，并重新走相同 strict validation。

### Phase 3：统一 controller

1. 抽取现有 registered-validation repair 的 policy、round、fingerprint 和 stop condition。
2. 让 output-contract 与 generated-content 两种 diagnosis 进入同一 controller。
3. 删除旧的平行 repair coordinator/重复判断，不保留 legacy 分支。
4. 所有模型反馈调用继续复用 composition root 的共享 FIFO。

### Phase 4：恢复与提交边界

1. 为 checkpoint 前 feedback、checkpoint 后 replacement、crash 和 Resume 建立 v3 恢复路径。
2. 验证成功 checkpoint 不重跑，失败节点只增加自己的 attempt。
3. 保证 `commit_prepared` 只能在完整 validator suite 通过后创建。
4. 保证 commit intent 后只前滚，不能回到模型或 feedback。

### Phase 5：Shell 与证据

1. UI 显示 phase/round/stop reason，不显示不可信内容。
2. CLI/GUI E2E 使用 stub 覆盖每一种可修订与不可修订分支。
3. 完成机器门禁后构建新 candidate。
4. 使用全新 Truth/Project/Draft/Graph/Run/Artifact 重新执行真实 Provider closure。

## 13. 必需验证

### 单元与属性测试

- 每个 OutputContractDiagnostic 的 exact classification。
- flat string object 成功；双重编码、嵌套、array、number/bool/null 稳定失败。
- feedback envelope 只包含 allowlisted typed fields。
- diagnostic fingerprint/candidate SHA-256 确定性和无原始值泄漏。
- `max_rounds`、`until_passed` 的 Graph 级 round 与停止语义，并证明预算不会按节点数放大。
- repeated/no-progress、unchanged replacement、Truth insufficient 和 cancellation 停止。
- 一个 semantic round 内 HTTP retry 不增加 graph node attempt。

### Graph 场景测试

```text
invalid output
-> typed diagnostic
-> feedback
-> valid output
-> checkpoint
-> full validation
-> succeeded
```

```text
invalid output
-> same redacted shape again
-> safe no-progress stop
-> graph paused
-> Resume creates new parent Run
-> successful Plan checkpoint remains attempt 1
```

```text
valid checkpoint
-> registered validator issue
-> complete-role replacement
-> checkpoint CAS replacement
-> crash
-> recover
-> full validation
-> commit once
```

还必须覆盖 Provider exhaustion、配置错误、local environment、storage conflict、cancel while queued、cancel during feedback、commit intent recovery 和 zero staging/transaction residue。

## 14. 完成条件

只有同时满足以下条件，方案才算真正落地：

- 代码中不存在模型名、Provider 名、STS2、Character 或 `merge_content` 专用 retry 分支。
- 输出合同与 generated-content diagnosis 共用一个 controller 和一套 policy/stop semantics。
- 所有错误候选仍被 strict rejection，本地没有启发式兼容解析。
- 三类 attempt 在记录和 UI 中可区分。
- 成功 checkpoint 不重跑，失败节点可恢复，publication 仍全闭包原子完成。
- repeated/no-progress 和所有系统错误能稳定停止，不依赖无限上游请求。
- stable spec 已与实现同步，旧 graph 明确 incompatible，不存在 dual-read 技术债。
- 新 candidate 的机器门禁、安装态全新 Provider closure 和真实游戏验收全部完成。

## 15. 禁止实现

- `if model == "deepseek-v4-pro"` 或 Provider-specific Prompt 分支。
- 捕获 `merge_content` 后本地 `serde_json::from_str(string)` 并继续。
- 从 Markdown/code fence/自然语言中抽取“最像 JSON”的片段。
- typed output 失败后切换 `json_schema` / `json_object`。
- 为 output contract 再写一个与 validation repair 并列的循环。
- 在 Adapter、Pack、React 或 Tauri 中决定 semantic repairability。
- feedback 请求跳过共享 FIFO，或在等待 backoff 时释放队列席位。
- 保存 raw completion 以支持恢复，或保留多代候选作为隐式 fallback。
- 命中安全停止条件后继续请求，或把 policy exhaustion 标记为成功。

本方案的最终原则是：**系统兼容模型的不确定性，但不兼容错误数据。**
