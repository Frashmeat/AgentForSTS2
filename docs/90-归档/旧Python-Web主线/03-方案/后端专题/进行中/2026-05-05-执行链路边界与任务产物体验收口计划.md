# 执行链路边界与任务产物体验收口计划

> 文档定位：本文是 Web 托管 Workstation 执行链路、用户本机 Workstation 执行链路、任务产物下载体验和健康检查语义的收口计划。
>
> 事实依据：基于当前代码、`docs/02-现状/当前前后端接口文档.md`、2026-05-05 关于“只有计划文档”“本机 CLI 健康但 Web 工作站失败”的排障讨论整理。
>
> 权威入口：上级入口为 `docs/03-方案/后端专题/README.md`；当前事实边界见 `docs/02-现状/当前前后端接口文档.md`。
>
> 最后更新：2026-05-05

## 当前状态

已完成本轮收口。

## 适用范围

- Web 平台任务创建、启动、执行、事件同步和产物登记链路。
- Web 托管 Workstation 执行面。
- 用户本机 Workstation 执行面。
- 服务器执行配置、服务器凭据、健康检查和 runner/protocol 兼容关系。
- 用户中心任务历史、任务详情、下载和导入本机 Workstation 体验。
- 执行方式弹窗、错误诊断和相关文案。

## 不纳入范围

- 不做旧线上数据兼容迁移；项目未上线，默认按当前主线口径收口。
- 不改变 Slay the Spire 2 Mod 生成业务语义。
- 不把服务器源码包改为构建包；当前下载目标是生成后的项目源码 zip。
- 不让 Web 平台任务直接读取用户本机 `project_root`。
- 不让用户本机执行结果进入 Web 平台任务历史；本机执行历史可作为后续独立能力，仅存储在用户本地。

## 已确认决策

1. 生成类平台任务缺少 `server_project_ref` 时必须硬失败，不再静默退回只生成 `plan_markdown`。
2. 健康检查需要增加“CLI 实际执行健康”层，用于验证选定 `runner_type + api_protocol + model + base_url` 能被真实 CLI 消费。
3. 用户本机执行记录不进入 Web 平台任务历史；后续可单独设计“本机历史”，数据只保存在用户本地 Workstation 或浏览器本地存储中。

## 背景问题

近期排障暴露出三类混淆：

1. 用户看到任务历史只有 `plan_markdown`，预期却是生成后的项目源码 zip。
2. 用户本机 Codex CLI 或 Claude CLI 健康，但 Web 工作站执行失败，容易被误判为同一套执行环境。
3. 服务器凭据健康检查通过，但真实 runner 执行失败，说明“凭据 HTTP 健康”和“CLI 实际执行健康”不是同一件事。

当前已经完成的局部修复包括：

- 有 `server_project_ref` 的生成链会执行 `package.project`，输出 `source_project` zip。
- 前端 `createAndStartPlatformFlow()` 会为 `single_generate` / `batch_generate` 自动创建服务器工作区并注入 `server_project_ref`。
- 用户中心任务详情可下载 `source_project` 或 `plan_markdown` artifact。
- 现状文档已补充 Web 托管 Workstation 与用户本机 Workstation 的执行链路边界。

## 目标

1. 明确 Web 托管 Workstation 执行和用户本机 Workstation 执行是两条不同链路。
2. 让 Web 平台任务只使用服务器执行档案、服务器凭据、Web 托管 Workstation 和服务器工作区。
3. 让用户本机执行只使用本机 Workstation 配置、本机 CLI 和本机项目目录。
4. 让生成类平台任务完成后默认能在用户中心任务历史下载源码 zip。
5. 健康检查、错误提示和管理端诊断能准确说明是哪一层失败。

## 当前链路口径

### Web 托管 Workstation 执行

```text
用户浏览器
-> Web 后端 same-origin /api/me/jobs
-> 平台任务、任务子项、ai_execution 入库
-> ExecutionOrchestrator 选择 execution profile
-> 解密服务器凭据并派发给 web-workstation
-> web-workstation 执行 workflow step
-> step 按 runner_type 调用 Codex CLI / Claude CLI / API
-> 写服务器工作区
-> package.project 登记 source_project
-> 用户中心任务历史下载
```

关键边界：

- 凭据来源是服务器凭据，不是用户本机配置。
- CLI 来源是 `web-workstation` 容器内 CLI，不是用户电脑 CLI。
- 项目目录来源是服务器工作区，不是用户本机 `project_root`。
- 产物归属是平台任务历史。
- Web 托管 Workstation 健康不等同于本机 Workstation 健康。

### 用户本机 Workstation 执行

```text
用户浏览器
-> runtime-config.js 配置的 workstation 地址
-> 用户本机 local-workstation 后端
-> 用户本机 project_root
-> 本机 LLM / Agent 配置
-> 用户本机 Codex CLI / Claude CLI / API
-> 修改本机项目或返回本机 workflow 结果
```

关键边界：

- 凭据来源是本机 Workstation 配置。
- CLI 来源是用户电脑 PATH 或本机安装位置。
- 项目目录来源是用户本机路径。
- 产物默认不进入平台任务历史。
- 本机链路错误归因应为 `local_workstation`。

## 任务拆分

### 任务 1：文档和术语收口

目标：

- 当前接口文档和专题方案都明确两条执行链路。
- 页面和错误文案避免把“服务器执行”“本机执行”“Web 工作站”混用。

实施点：

- `docs/02-现状/当前前后端接口文档.md` 保持执行链路边界为当前事实入口。
- 本文作为后续改造计划入口。
- 后续 UI 文案统一使用：
  - `Web 托管工作站执行`
  - `本机 Workstation 执行`
  - `服务器凭据健康`
  - `Web 托管 Workstation 健康`
  - `CLI 实际执行健康`

验收标准：

- 读者能从文档直接判断一个错误应该查 Web 后端、Web 托管 Workstation、本机 Workstation 还是上游网关。
- 文档不再出现“生成任务缺 `server_project_ref` 可以静默退回只生成计划文档”的主线口径。

### 任务 2：生成任务产物链路硬约束

目标：

- 生成类平台任务不再静默退回只产出 `plan_markdown`。
- 有服务器工作区的生成任务必须进入项目文件生成与 `package.project`。
- 缺少 `server_project_ref` 的生成类平台任务必须返回明确错误。

实施点：

- 前端继续在 `createAndStartPlatformFlow()` 内为 `single_generate` / `batch_generate` 自动创建服务器工作区。
- 后端对生成类任务启动前增加硬校验：若按当前主线应有 `server_project_ref` 但缺失，返回可诊断错误，而不是退回文本方案链路。
- workflow registry 中保留“纯方案类 workflow”的语义，但必须由明确的方案任务入口触发，不能让主线生成入口误命中。

验收标准：

- 从单资产或批量生成入口创建服务器任务，完成后用户中心出现 `source_project`。
- 如果生成任务没有源码包，错误必须明确说明缺少服务器工作区或打包失败。

### 任务 3：任务创建与下载体验收口

目标：

- 用户创建任务时知道当前进度、弹窗是否可关闭、完成后去哪里下载。
- 下载失败时能定位 artifact 记录、文件缺失还是权限问题。

实施点：

- 执行方式弹窗继续展示阶段：创建服务器工作区、上传服务器资产、创建平台任务、等待确认、启动任务。
- 点击“创建平台任务”前重新复核 Web 后端可达性和平台执行配置；Web 后端不可达时停留在弹窗内展示错误并要求“重试读取”，不进入服务器工作区或平台任务创建链路。
- `web` Docker 镜像必须包含 `/app/mod_template`，服务器工作区创建缺少模板时必须返回明确 503 配置错误，而不是未处理堆栈。
- 任务创建完成后明确引导到用户中心任务历史。
- 用户中心任务详情中按 artifact 类型展示：
  - `source_project`：下载项目源码包。
  - `plan_markdown`：下载方案文档。
- 下载 404 需要展示更明确文案：artifact 不存在、artifact 不可下载、artifact 文件缺失。

验收标准：

- 用户无需问“下载入口在哪里”。
- `artifact file not found` 不再作为唯一可见反馈。

### 任务 4：健康检查语义拆分

目标：

- 不再把“服务器凭据健康”误当成“Web 工作站真实执行健康”。
- 增加“CLI 实际执行健康”，验证服务器执行配置能被真实 CLI 子进程消费。

实施点：

- 管理端展示拆分：
  - 服务器凭据健康：key/base_url/protocol 可访问上游。
  - Web 托管 Workstation 健康：容器可达、token 正确、capabilities 可读。
  - CLI 实际执行健康：选定 runner_type + api_protocol + model + base_url 能跑最小真实任务。
- 对第三方 OpenAI-compatible 网关，明确 Codex CLI 可能使用 Responses API；Chat Completions 健康通过不代表 Codex CLI 可用。
- CLI 实际执行健康由管理员手动触发，使用最小 prompt，记录最近一次结果、耗时、错误分类和日志指引；默认不做后台高频自动探测。

验收标准：

- 管理员能从页面看出应该检查凭据、容器、CLI 还是第三方网关协议支持。
- 用户本机 CLI 健康不会被展示成服务器执行健康证据。
- 同一个服务器凭据可同时展示 HTTP 健康和 CLI 实际执行健康，二者状态不得互相覆盖。

### 任务 6：本机历史独立设计

目标：

- 用户本机执行记录不进入 Web 平台任务历史。
- 后续如需要本机执行历史，只做用户本地存储，不上传到 Web 平台任务系统。

实施点：

- 本机历史作为本机 Workstation 能力独立设计，可存储在用户本机 runtime、localStorage 或 IndexedDB，具体方案另行确认。
- 本机历史只记录本机执行摘要、时间、项目路径、结果状态和本机日志引用，不写入 Web `platform_jobs`。
- Web 用户中心继续只展示 Web 托管 Workstation 产生的平台任务。

验收标准：

- Web 平台任务历史不会混入本机 BYOK、本机 CLI 或本机 workflow 快照。
- 若后续实现本机历史，页面必须明确标注“仅保存在本机”。

### 任务 5：runner/protocol 强校验与错误归因

目标：

- 防止 `claude_cli + openai_compatible`、`codex_cli + anthropic_compatible` 这类组合进入真实 CLI 子进程。
- 保留上游原始错误信息，外层同时提供用户可读结论。

实施点：

- 继续保持路由层和 runner config 构造层的兼容校验。
- `origin` / `runtime_surface` 维持分层：
  - `web`
  - `web_workstation`
  - `local_workstation`
  - `upstream`
- 上游错误记录保留 HTTP 状态、provider error code、raw error 摘要和日志指引。

验收标准：

- runner/protocol 不兼容时，错误在启动或 step 构造阶段失败，不进入 CLI。
- 上游 401、429、HTML 非 JSON、空 body 等错误能被归为 `upstream`。

## 建议执行顺序

1. 先做文档与 UI 术语收口。
2. 再做后端生成任务缺 `server_project_ref` 的硬失败。
3. 接着完善下载错误体验。
4. 增加 CLI 实际执行健康检查，但采用管理员手动触发和最小 prompt，控制成本与频率。
5. 本机历史作为独立后续能力，不阻塞 Web 平台任务链路收口。

## 风险与约束

- 后端硬失败会暴露仍未自动注入 `server_project_ref` 的入口，需要同步修前端调用点。
- CLI 实际执行健康检查可能消耗模型额度，必须限定最小 prompt、频率和管理员触发条件。
- 第三方网关兼容性不统一，健康检查只能证明当前检查路径可用，不能替代真实 runner 执行结果。
- 文案必须足够清楚，但不能把普通用户暴露在过多内部实现细节中。

## 完成标准

- [x] Web 托管 Workstation 与用户本机 Workstation 在文档、UI 和错误诊断中可区分。
- [x] 生成类服务器任务缺少 `server_project_ref` 时硬失败，不再静默退回只生成 `plan_markdown`。
- [x] 前端创建 Web 托管工作站任务时继续自动创建服务器工作区并注入 `server_project_ref`。
- [x] 下载失败能给出结构化原因：产物记录不存在、产物不可下载、产物文件缺失。
- [x] 管理端能区分服务器凭据 HTTP 健康、Web 托管 Workstation 健康和 CLI 实际执行健康。
- [x] 用户中心平台任务历史明确只展示 Web 托管工作站任务，不读取本机执行记录。

## 本轮落地记录

- 后端 `JobApplicationService` 对 `single_generate` / `batch_generate` 的每个 item 强制校验 `server_project_ref`。
- 用户中心 artifact 下载接口改为结构化错误 detail，前端错误解析支持递归读取 `detail.message`。
- 管理端新增 `POST /api/admin/platform/server-credentials/{credential_id}/cli-health-check`，按凭据绑定的 execution profile 实际调用 CLI 最小文本任务；结果不覆盖 HTTP 凭据健康状态。
- 管理端服务器凭据页新增“CLI 实测”按钮，并在凭据卡片内展示最近一次本地页面状态。
- 前端执行方式弹窗、设置页、用户中心和创建流程文案统一为“本机 Workstation 执行”和“Web 托管工作站”。
- 前端执行方式弹窗在提交 Web 托管任务前会重新读取平台执行配置和用户偏好；若 Web 后端不可达，会把错误留在弹窗内并禁用创建按钮，避免继续调用服务器工作区创建接口。
- `web` 镜像补齐 `mod_template`，`/api/me/server-workspaces` 在模板缺失时返回 503 配置错误，避免用户看到后端未处理堆栈。
- 本机执行记录仍不进入 Web 平台任务历史；后续如需“本机历史”，应作为仅本地存储的独立能力设计。
