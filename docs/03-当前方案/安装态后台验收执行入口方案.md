# 安装态后台验收执行入口方案

> 文档定位：定义 production desktop binary 的无 UI 验收入口、协议、安全边界和证据要求。
>
> 不包含：真实游戏 UI 自动化、Web Project API、任务级 candidate 流水或用户的玩法结论。
>
> 权威入口：[`当前方案`](./当前方案.md)；可执行合同见 `.trellis/spec/backend/`。
>
> 最后更新：2026-08-24

## 1. 问题与结论

生产安装包不携带 `e2e` WebDriver plugin，`ats-web` 也只提供 health/catalog，不能执行
Project、Truth、Run、Graph 或 Artifact。旧 GUI E2E 会重建 source debug binary，既会占用桌面，
也不能证明已安装 release candidate。

解决方式是在同一个 production desktop binary 中提供本地 `--headless-jsonl` Shell transport：

```text
candidate E2E driver
        |
        | versioned JSONL over redirected stdin/stdout
        v
production desktop binary --headless-jsonl
        |
        v
shared Shell service functions
        |
        +--> ProjectSession / project lock / task supervisor
        +--> Stage2Composition / Feature registry
        +--> existing repositories and adapters
        |
        v
Run / Graph / Artifact / project files
```

它不是第二套 Runtime，也不是测试专用业务实现。Tauri IPC 与 headless transport 只适配宿主输入输出，
共同调用同一组 Shell service functions。

## 2. 进程入口

```text
no arguments                 -> start desktop UI
--write-build-info <path>    -> write exact BuildInfo and exit
--headless-jsonl             -> run local JSONL session without UI
any unknown argument         -> exit code 2 without starting UI
```

`--headless-jsonl` 存在于 baseline 和 ML production binaries，不依赖 `e2e` feature，不打开端口，
也不启动 WebView。每个响应都携带当前 binary 的 `BuildInfo`；同一 session 中 BuildInfo 不得变化。

## 3. 协议

请求和响应均为一行一个 JSON object，协议版本当前为 `1`。

```json
{"schemaVersion":1,"requestId":"driver-000001","command":{"name":"health"}}
```

带输入的命令使用独立 `input`：

```json
{
  "schemaVersion": 1,
  "requestId": "driver-000002",
  "command": {
    "name": "get_run",
    "input": {"runId": "run-example"}
  }
}
```

每个响应都包含 `schemaVersion`、`requestId`、`build` 和 `ok`。成功响应只包含 typed
`result`；失败响应只包含 `ActionableFailure`。包络和每个 command input 都拒绝未知字段。
请求单行最大 4 MiB，`requestId` 最大 128 个安全 ASCII 字符。decode、schema 或输入错误不得
回显 parser text、原请求、路径、Prompt 或 secret。

## 4. 命令范围

协议覆盖 installed fresh closure 所需的 Shell 操作：

- health、masked settings snapshot/patch、Feature catalog；
- Project create/open/current/close；
- Truth status/import；
- generic Feature submit；
- Run list/get；
- Execution Graph list/get/resume；
- Item list/get/save；
- Composition Draft list/get/update/confirm；
- Resource list/select；Resource prepare 继续通过 generic Feature submit；
- succeeded-source 单 Item human feedback；
- graceful shutdown。

Feature submit 只返回 `RunId`。驱动端通过 `get_run` 和 `get_execution_graph` 观察 persisted state，
不根据固定前端超时推断失败。Node client 默认无限等待 terminal state；调用方若需要 deadline，必须显式给出。

## 5. 生命周期与并发

```text
create/open project
       |
       v
ProjectSession owns OS lock + repositories + task handles
       |
       +--> submit returns RunId while worker continues
       +--> later JSONL requests poll persisted Run/Graph
       |
EOF / close / shutdown
       v
cancel-and-drain -> release project lock -> process exits
```

一个 JSONL 进程拥有一个 `ActiveProject`。命令按输入顺序 dispatch；模型请求仍进入桌面
composition root 的唯一 FIFO。headless transport 不得增加另一层 transport retry、semantic retry、
Run 状态机或工程事务。

## 6. 安全与隐私

- transport 仅使用父子进程 stdio，不监听 TCP，也没有远程认证面；
- stdout 只允许协议 JSONL；本地诊断写 stderr 且有界；
- settings 响应只提供 masked secret 和 configured boolean；
- human feedback 原文只存在于 driver request、pipe 和 worker memory，不进入 response、Run、Graph、
  checkpoint、Artifact 或日志；
- 不返回 Provider body、Prompt、raw completion 或任意 parser/compiler text；
- source path 只进入已有 Resource/Feature contract，不能绕过 Pack asset identity。

## 7. 多游戏边界

headless transport 不认识 STS2 Character、Card、Godot 或 ZIP。不同游戏仍通过各自 Pack、Truth importer、
Game Adapter 和 Pipeline Provider 决定生成、验证、构建与打包链路。协议只传递注册 Feature payload 和
稳定 Workspace/Run/Graph identity，因此新增游戏不需要复制自动化 transport。

## 8. 验证与 candidate 规则

代码级验证必须覆盖：

1. production binary 的真实子进程 JSONL handshake；
2. unknown argument 不启动 UI；
3. unknown command/input field 被拒绝；
4. Project create 产生 succeeded Run，close/shutdown 后锁可重新获取；
5. 每个响应 BuildInfo 稳定，settings/失败响应无 secret 或原请求；
6. Tauri IPC focused regression 与 headless service 共同通过；
7. candidate 安装后由安装目录 binary 完成 health、fresh closure 和证据审计。

源码 debug smoke 只能证明 transport 与共享服务，不能冒充 installed candidate closure。任何 production
代码变化都会使旧 candidate 失效；必须重新提交、构建、安装并使用全新的 Truth、Project、Draft、
Item、Resource、Run、Graph 和 Artifact。

## 9. 不纳入范围

- 自动操作或判断真实 STS2 UI；
- 把 `e2e` WebDriver plugin 打进 production bundle；
- 给 `ats-web` 临时复制 Project execution；
- 保存人工反馈原文或完整自动化会话 transcript；
- 使用旧 candidate/证据、人工改名或 source integration test 冒充安装态验收。

## 10. 完成条件

- release binary 可在后台完成 candidate-specific fresh closure；
- UI 与 headless 共享 ProjectSession、Stage2Composition、typed failures 和 repositories；
- Run/Graph/Artifact、锁、取消、事务和脱敏合同与桌面路径一致；
- 新 candidate 的 installed BuildInfo、fresh evidence 和零残留审计通过；
- 真实游戏玩法及 human feedback 修正结果仍由用户明确确认。
