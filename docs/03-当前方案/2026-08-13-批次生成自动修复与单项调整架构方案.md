# 批次生成自动修复与单项调整架构方案

> 文档定位：定义批次 Mod 生成中的多 Item 自动技术修复，以及生成后由用户针对单个 Item 提出调整要求的产品与架构边界。
>
> 关联方案：[`统一生成反馈闭环`](./2026-08-12-统一生成反馈闭环架构方案.md)。
>
> 当前状态：核心实现已于 2026-08-13 落地，机器门禁与新 candidate/真实游戏验收仍待完成。
>
> 变更性质：破坏性合同升级。实施后必须构建新 candidate，并使用全新 Run、Graph 和 Artifact 重新验收。

## 1. 背景与问题

安装态 O8 Character closure 使用 1 个 Character、9 个 Card 和 1 个 Relic 完成了 23/23 生成节点，但完整工程验证发现 11/11 生成源码均存在真实 STS2/BaseLib API 编译错误。

现有反馈闭环已经证明两项基础能力成立：

- 输出合同错误可以转成 typed feedback，并只重调失败 Item；
- 成功 checkpoint、串行 FIFO、Graph 恢复和 whole-closure 原子发布边界有效。

本次失败同时暴露两个剩余缺口：

1. 完整编译发生在所有 Item 生成后，明显的 API 幻觉发现过晚。
2. registered validation repair 只接受全部错误唯一归属于一个 Item；多个 Item 同时失败时直接暂停为 `validation.not_repairable`。

此外，现有产品入口没有清楚区分：

- 系统为“能否正常运行”负责的技术修复；
- 用户为“是否符合预期”提供的创作调整。

本方案补齐上述边界，但不把 Graph、诊断、修复预算和内部队列暴露给普通用户。

## 2. 目标

系统必须做到：

- 自动发现并修复批次中一个或多个 Item 的生成内容错误；
- 保持模型请求严格串行，保留已成功 Item，不扩大无关重生成；
- 每次修复后重新证明完整 Mod 可以编译、构建、打包和原子发布；
- 只把通过技术验证的结果交给用户预览；
- 允许用户针对一个具体 Item 输入调整要求，并只重新生成该 Item；
- 将内部复杂度限制在 Runtime、Feature、Adapter 和诊断证据中。

用户只需要判断：

```text
生成结果是否正常？       <- 系统负责证明
生成结果是否符合预期？   <- 用户通过预览和单项调整表达
```

## 3. 非目标

本方案不提供：

- 面向普通用户的 Graph、Run、错误码、文件路径或 repair budget 编辑器；
- 生成后对整个批次生效的无边界自由 Prompt；
- 本地字符串补丁、宽松解析或对错误生成结果的兼容性接纳；
- 多 Item 并发模型请求；
- 自动更换模型、Provider、endpoint 或 response format；
- 对本地环境、Truth、锁、存储、工具链或发布事务错误调用模型；
- 未通过 whole-closure 验证的预览发布、部分 Artifact 或部分工程提交。

## 4. 核心原则

### 4.1 系统负责技术正确性

输出格式、API、编译、资源、构建、PCK、ZIP 和 Artifact 错误由系统诊断和自动修复。用户不需要为 `CS0246`、缺失 namespace 或错误 role 提供提示词。

### 4.2 用户负责创作预期

用户调整只表达想要的效果，例如：

```text
降低这张卡的基础伤害，升级后增加一层燃烧。
这个遗物效果太复杂，希望更适合新手。
强化这个角色的金币消耗主题。
```

调整要求必须绑定一个具体 Item 和用户当前看到的 definition 版本。

### 4.3 复杂度不泄漏

内部可以存在诊断分组、修复队列、checkpoint CAS、反馈轮次和安全停止；普通界面只显示生成、检查、自动调整和预览状态。

### 4.4 错误数据永不兼容

人工调整和机器反馈都只能驱动重新生成。任何结果仍需通过相同的 strict output contract、Truth/API 检查和 whole-closure validation。

## 5. 端到端流程

```text
用户描述整套 Mod
        |
        v
结构化 Draft / Item graph
        |
        v
用户确认结构和资源
        |
        v
+--------------------------------------+
| 逐 Item 串行生成                      |
|                                      |
| generate -> strict output contract   |
|          -> Item 快速检查             |
|          -> 必要时自动重调当前 Item   |
+--------------------------------------+
        |
        v
+--------------------------------------+
| Whole-closure validation             |
| compile / references / resources     |
| build / PCK / ZIP / Artifact gate    |
+--------------------------------------+
        |
        +---- passed ----------------------+
        |                                  |
        |                                  v
        |                            用户预览结果
        |                                  |
        |                     +------------+------------+
        |                     |                         |
        |                   接受                    调整单个 Item
        |                     |                         |
        |                   发布              单项重新生成和完整复验
        |
        +---- generated-content rejected
                         |
                         v
                  自动建立多 Item 修复队列
                         |
                         v
                  逐项修复和快速检查
                         |
                         v
                  重新执行完整 closure
```

## 6. 两级验证

### 6.1 Item 快速检查

每个 Item 通过输出合同后、写入成功 checkpoint 前后，由 Pack 声明可用的局部检查。检查至少覆盖：

- generated role 数量、类型、路径和 merge shape；
- localization flat string object 和必需 key；
- Resource/reference binding 与 pinned definition 一致性；
- Truth 中可确定查询的 namespace、type 和 member；
- Pack 能安全声明的 Item 局部源码约束。

快速检查的目标是尽早拒绝明显错误，不替代真实编译。Truth 无法证明的 API 不得因快速检查缺失而被当作正确。

### 6.2 Whole-closure 验证

所有 Item checkpoint 完成后，仍必须运行完整验证：

- 真实 STS2/BaseLib 编译；
- 跨 Item 类型和引用；
- Character、Card、Relic、Pool 与存档身份；
- Resource 文件和 Godot PCK；
- build/package 输出；
- Artifact manifest、文件 hash 和原子发布条件。

只有完整验证通过，Graph 才能进入 `commit_prepared`。

## 7. 多 Item 自动修复

### 7.1 诊断归属

现有单值 `repair_owner()` 升级为确定性的诊断分组：

```text
ValidationIssue[]
        |
        +-- Generated/A.cs -> Item A
        +-- Generated/B.cs -> Item B
        +-- Generated/C.cs -> Item C
        |
        v
RepairTarget[]
```

只有满足以下条件的 issue 才能进入模型修复：

- severity 为 error；
- repairability 为 `generated_content`；
- relative path 精确匹配一个非 shared generated file；
- 文件对一个 Item 具有唯一所有权；
- pinned Truth、Pack、definition 和 Resource 身份仍有效。

shared merge 文件、所有权不唯一、环境和系统错误继续安全暂停。

### 7.2 修复顺序

修复队列按 ResolvedItemGraph 的稳定依赖顺序排列，并保持单飞：

```text
Character -> dependent Cards -> Relic -> remaining Items
```

具体顺序由 Feature 根据 dependency graph 编译，不能依赖文件枚举顺序或 UI 排序。

每次只处理一个 Item：

1. 读取该 Item 当前有效 checkpoint。
2. 装配该 Item 的 typed machine feedback。
3. 请求返回该 Item 的完整声明 roles。
4. 重走 strict decode、Resource 解析和 Item 快速检查。
5. CAS 替换该 Item checkpoint。
6. 继续队列中的下一个 Item。

完成当前队列后重新执行 whole-closure validation。新一轮诊断必须重新分组，不复用已经过期的 issue。

### 7.3 反馈与预算

多 Item 修复继续使用 Graph 级 semantic request budget，不放大为“每个 Item 各 N 轮”。每次实际模型修复调用消耗一次预算。

`until_passed` 仍受以下绝对停止条件约束：

- 整个 Graph 最多 20 个 semantic requests；
- 相同诊断指纹和相同 candidate/checkpoint 重复；
- replacement bytes 未变化；
- Truth 不足或所有权不唯一；
- local environment、storage、lock、configuration 或 publication failure；
- cancellation、project close 或 shutdown。

预算和停止原因属于内部状态，普通用户界面不要求理解或配置。高级诊断可以只读展示。

## 8. 单 Item 用户调整

### 8.1 调整合同

生成后的用户调整必须精确绑定：

```text
ItemAdjustment
+-- itemId
+-- expectedDefinitionHash
+-- instruction
+-- instructionSha256
+-- createdAt
```

- `itemId` 确定作用对象；
- `expectedDefinitionHash` 防止把旧意见应用到已经变化的 Item；
- `instruction` 是有界自然语言，建议最多 4,000 字符；
- hash 和时间用于恢复、审计和幂等判断。

用户从某个 Character、Card 或 Relic 的预览入口点击“调整”，系统自动确定范围。界面不再要求用户选择文件、诊断或依赖节点。

### 8.2 调整执行

```text
选中 Item
    |
输入调整要求
    |
校验 itemId + expectedDefinitionHash
    |
只重新生成该 Item 的完整 roles
    |
Item 快速检查
    |
Whole-closure validation
    |
更新可预览结果
```

其他成功 Item 不重新请求模型，不修改 checkpoint。

成功结果的 Artifact 和 Graph 是不可变证据。用户从 `succeeded` 结果发起调整时，后端复制
当前已验证 checkpoints，派生新的 Graph、父 Run 和 Artifact version，仅激活目标 Item；源
Graph、Run 和 Artifact 保持不变。只有尚未进入 `commit_prepared` 的 paused Graph 才允许在
同一 Graph 上通过 revision CAS 继续调整。

### 8.3 结构性调整

如果用户要求会改变组合结构，例如：

- 删除或新增 Item；
- 改变 ItemType；
- 新增 pinned dependency；
- 改变 Resource profile；
- 改变 starting deck 或 pool 的结构关系；

系统不得在源码修复阶段偷偷级联修改。Shell 应提示该调整需要重新规划相关内容，并回到局部 Draft planning/review 流程。

## 9. 用户体验

### 9.1 默认状态

普通界面只展示：

```text
正在生成
正在检查
正在自动调整
可以预览
```

可以显示总体进度，但不显示 `item.007.single`、Graph revision、HTTP attempt 或 semantic round。

### 9.2 自动恢复耗尽

系统无法继续时显示可行动的产品信息：

```text
本次结果暂时未能通过运行检查。

[重新尝试]  [返回修改需求]
```

可选折叠详情只显示经过归纳的内容：

```text
原因类别：生成内容与当前游戏 API 不匹配
影响范围：角色及部分卡牌
检查结果：完整编译未通过
```

原始 completion 永不展示或持久化；脱敏后的 typed validation issues 作为诊断证据持久化，避免 staging 清理后只剩笼统 failure code。

### 9.3 单项调整入口

每个结果预览项只需要一个明确入口：

```text
灼热火花

[预览] [调整]

调整要求
+------------------------------------+
| 降低基础伤害，升级后增加燃烧。     |
+------------------------------------+

[重新生成此项]
```

不提供作用于整个已生成批次的自由调整输入框。

## 10. 内部状态

Runtime 需要表达 provider-neutral 的修复批次状态。建议使用新的破坏性 schema，而不是向 v3 追加含糊的可选字段：

```text
RepairCampaign
+-- validationFingerprint
+-- targets[]
|   +-- itemId
|   +-- checkpointHash
|   +-- diagnosticFingerprints[]
|   +-- status
+-- currentTarget
+-- completedTargets[]
+-- semanticRequestCount
+-- safetyStop
+-- operatorAdjustment?   // 始终只绑定一个 Item
```

`RepairCampaign` 是 Graph 内部的恢复状态，不是新 Feature，也不进入 Feature catalog。

必须持久化：

- 脱敏 typed diagnostics；
- 稳定 Item ownership；
- 当前 checkpoint hash；
- 修复队列与完成位置；
- semantic request count；
- 单 Item 用户调整及其 hash；
- no-progress 和安全停止证据。

不得持久化：

- raw model completion；
- Provider body；
- parser 原始异常文本；
- 未通过合同的候选文件；
- 多代候选作为隐式 fallback。

## 11. 模块职责

| 模块 | 新增职责 | 不负责 |
| --- | --- | --- |
| `ats-runtime` | RepairCampaign 通用状态、CAS、resume、budget 和安全停止 | ItemType、Prompt 文案、游戏 API |
| `ats-features::generation_feedback` | typed machine feedback、单 Item adjustment envelope、no-progress 判定 | HTTP retry、文件事务 |
| `ats-features::composition_generate` | 多 Item 归属、依赖排序、修复队列、局部/完整验证调度 | Provider 特例、宽松修复 |
| `ats-adapters` | FIFO、HTTP retry、typed validation、原子存储 | semantic repairability、用户范围 |
| Game Pack / Truth | API 查询、局部检查声明、generated role ownership | Graph 调度、UI 状态 |
| Tauri / React | 简化状态、单 Item 预览和调整入口、折叠诊断 | 修复算法、错误字符串控制流 |

## 12. 状态与提交边界

```text
producing
   |
   v
checking_item
   |
   v
validating_closure
   |
   +-- generated-content issues -> repairing_campaign
   |                                  |
   |                                  +-> validating_closure
   |
   +-- passed -> commit_prepared -> committing -> succeeded
   |
   +-- unsafe/exhausted -> paused
```

不变量：

- Pack 声明当前 Item 的 source ownership，Truth 独占 API/type/namespace/lifecycle 事实；Plan
  只提供业务意图与验收指导，不得提升为可执行技术合同；
- generated role 与 Pack file spec 必须按 exact role ID 关联，禁止依赖两个集合的位置顺序；
- worker terminal failure 若仍持有本 Run 的 Graph claim，ProjectSession 必须幂等释放；不得
  覆盖 Feature 已形成的 pause、success、cancel 或新 Run claim；
- `commit_prepared` 前可以在同一 Graph 进行技术修复或用户单项调整；
- `commit_prepared` 后只允许前滚，不再调用模型；
- 已成功结果的用户调整必须派生新 Graph/Run/Artifact version，不重开或覆盖源证据；
- 所有发布仍是 whole-closure 原子事务；
- Crash/Resume 不重跑已成功且仍有效的 checkpoint；
- campaign 部分完成后，Resume 先用当前 Item checkpoints 本地对齐 finalize，再继续 cursor；
  该对齐不消耗模型请求，也不能被误判为 checkpoint corruption；
- adjustment 的 expected definition/checkpoint 不匹配时必须拒绝并要求刷新预览。

## 13. 验证要求

### 单元和属性测试

- 多个 generated file 精确分组到多个 Item；
- shared、ambiguous、local 和 non-repairable issue 不进入模型；
- 修复顺序由 DAG 决定且稳定；
- 一个 Item 修复不改变其他 checkpoint；
- stale `expectedDefinitionHash` 被拒绝；
- 单项 adjustment 不扩散到其他 Item；
- Graph 总预算、20 次绝对上限和 no-progress 停止；
- typed diagnostics 可恢复且不包含敏感路径或 raw output。

### Graph 场景

```text
three Items fail compile
-> three owned repair targets
-> serial complete-role replacements
-> full closure passes
-> one atomic publication
```

```text
user adjusts Card B
-> only Card B model request
-> Card A/Character checkpoints unchanged
-> full closure passes
-> preview updates
```

```text
repair campaign crashes after target 2/5
-> Resume creates new parent Run
-> targets 1..2 remain complete
-> finalize reconciles locally
-> target 3 continues
-> commit once
```

还必须覆盖 cancellation、project close、Provider exhaustion、stale adjustment、budget exhaustion、repeated diagnostics、storage conflict、zero staging/transaction residue 和 project lock reacquisition。

### 最终门禁

- workspace tests、check、clippy；
- frontend tests、TypeScript、production build；
- desktop feature matrix、DAG 和精确 12-Feature catalog；
- isolated GUI E2E；
- release verification；
- 新 candidate 安装态 fresh multi-Item repair closure；
- 真实 STS2/BaseLib compile、Godot PCK、ZIP 和 Artifact/hash；
- 用户真实游戏和单 Item 调整验收。

## 14. 实施顺序

1. 定义多 Item ownership、RepairCampaign 和持久化 validation evidence 合同。
2. 破坏性升级 ExecutionGraph/Composition Generate schema，并同步 stable specs。
3. 将单 owner repair 重构为依赖有序的串行 repair campaign。
4. 接入 Pack-driven Item 快速检查，但保留完整编译为最终权威。
5. 增加单 Item `ItemAdjustment` request、stale guard 和完整复验。
6. 将 Shell 收敛为简化状态、结果预览和单项调整入口。
7. 完成 focused、workspace、GUI 和 release 门禁。
8. 进入 O9：构建并安装新 candidate，使用全新证据完成 fresh closure 和真实游戏验收。

## 15. 完成条件

只有同时满足以下条件，本方案才算落地：

- 多 Item 编译失败可自动分组、串行修复并通过完整 closure；
- 技术错误默认不要求用户提供提示词；
- 用户调整只作用于一个明确 Item 和一个明确版本；
- 其他成功 Item 不被无理由重新生成；
- 普通界面不暴露 Graph、错误码、文件、budget 或内部队列；
- typed diagnostics 在 staging 清理后仍可审计；
- strict validation、全闭包原子发布和安全停止语义没有被削弱；
- 新 candidate、fresh Provider closure 和真实游戏验收全部通过。

最终原则是：**系统隐藏修复复杂度并负责结果可运行，用户只对具体内容表达自己的预期。**
