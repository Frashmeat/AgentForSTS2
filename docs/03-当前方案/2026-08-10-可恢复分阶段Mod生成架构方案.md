# 可恢复分阶段 Mod 生成架构方案

> 文档定位：定义大型、多节点和长输出 Mod 生成的跨游戏本地编排、检查点、恢复和原子发布方案；不记录具体 O8 验证流水。
>
> 事实依据：当前 Stage 2 Cargo DAG、`composition.plan` 单次长请求实现、2026-08-10 安装态 `deepseek-v4-flash/json_object` 长输出传输失败证据，以及用户确认的通用化方向。
>
> 权威入口：阶段入口见 [`当前方案`](./当前方案.md)，当前事实见 [`当前进度说明`](../02-现状/当前进度说明.md)，任务状态见 `.trellis/tasks/08-05-sts2-character-cross-item-composition/`。
>
> 最后更新：2026-08-10

## 1. 决策摘要

大型 Mod 生成采用“Runtime 通用执行图 + Feature 分阶段编排 + Pack 声明游戏差异 + Adapter 可靠传输/持久化”的结构，不再要求 Provider 在一个长连接中一次返回完整多节点闭包。

```text
小型、有界输出 --------------------------> 现有 Single Request

大型、多节点或跨媒体输出
        |
        v
本地确定性 Blueprint
        |
        v
串行短节点请求 + 持久化 checkpoint
        |
        v
本地绑定 identity / pinned references
        |
        v
完整 graph validation
        |
        v
原子创建正式 Draft / 发布最终结果
```

本方案不能消除模型 Provider 依赖，但将故障影响从“整次任务全部作废”收敛为“当前节点暂停且可恢复”。Character 是首个落地场景，后续 Deck、Boss、Event、Quest、多文件 Mod 和跨媒体生成复用同一基础设施。

## 2. 原始问题与根因

实施前的 `composition.plan` 在一个逻辑请求中要求返回完整 `rootItemId + nodes[]`。STS2 Prototype 为 11 个节点；一次真实安装态请求持续约 21 分 24 秒，经过共享 FIFO 和 300/600 秒退避后仍以 `model.transport_failed` 终止，没有 Draft、Item、Artifact 或 Package。

```text
Character Studio
      |
      v
前置校验 -> FIFO -> 一个大型 HTTP 请求 -> 完整 JSON -> 整图验证 -> Draft
                            |
                            X 任意时刻传输失败
                            |
                            +-> 全部模型工作丢失，重新请求整图
```

现有机制已经解决：

- 所有桌面模型请求共享 FIFO 单飞队列。
- 一个逻辑请求内部有界重试，并支持配置化请求间隔。
- `json_schema` / `json_object` 由 typed config 显式选择。
- 返回后执行 exact type/count/reference/root-closure validation。

该版本当时尚未解决：

- 单次输出随节点数增长，连接时间和响应体持续增大。
- 已经正确生成的部分节点没有 durable checkpoint。
- 一个节点失败会让整图重新生成。
- 进程退出后无法从已验证节点恢复。
- 继续增加整体等待时间无法缩短单次长连接。

当前工作树已经用 durable execution graph 和逐节点 checkpoint 解决上述本地可恢复性缺口。Provider 仍可能使单个节点失败，但成功节点不再随本次失败丢失；graph paused 后由用户显式 resume 创建新父 Run。

## 3. 目标与不纳入范围

### 目标

- 通用支持跨游戏的大型、多节点、长输出和跨媒体生成。
- 本地确定图结构、节点身份、依赖和最终 reference binding。
- 每个节点独立请求、验证和持久化；失败后只允许用户显式重试，默认严格串行。
- 进程退出或上游失败后复用已验证 checkpoint。
- 不完整执行不得创建正式 Draft、Item current pointer 或 published project files。
- 最终仍复用完整 graph validator、whole-closure generation 和原子 publication。
- 保留 Run/Artifact、Truth、Pack、Resource 和 definition hash 的可追溯性。

### 不纳入范围

- 不提供离线本地模型推理。
- 不用宽松 JSON 截取、字段猜测或不完整响应修补制造成功。
- 不自动切换模型或 `response_format`。
- 不默认并发模型节点请求。
- 不把任意脚本或工作流实现放进 Game Pack。
- 不让中间 checkpoint 出现在 Item Library 或 CompositionDraft review 中。
- 不强制单个 Card/Relic 等小请求经过 DAG。

## 5. 通用执行图合同

`ExecutionGraphRecord v1` 是执行证据和恢复真源，不是业务 Draft。Runtime 只验证通用结构，Feature 负责解释其中的 versioned blueprint/checkpoint payload。

```text
ExecutionGraphRecord
|
+-- schemaVersion
+-- executionGraphId
+-- ownerFeatureId
+-- requestSnapshotHash
+-- revision
+-- status
+-- activeRunId, optional
+-- previousRunId, optional
+-- createdAt / updatedAt
+-- blueprint: VersionedPayload + SHA-256
+-- nodes: ordered map
|   |
|   +-- nodeId
|   +-- roleId
|   +-- dependsOn[]
|   +-- status
|   +-- logicalAttempts[]
|   +-- requestSnapshotHash
|   +-- checkpoint: VersionedPayload + SHA-256, optional
|   +-- safeFailure, optional
|
+-- commitIntent, optional
|   +-- draftId
|   +-- canonicalDraft: VersionedPayload
|   +-- draftPayloadSha256
|   +-- validatedContentDigest
+-- finalResultRef, optional
```

Runtime 不解码 `roleId`、blueprint 或 checkpoint 的业务含义，只保证：

- ID、依赖边和状态合法。
- DAG 无环且依赖目标存在。
- 只有依赖全部成功的节点可进入运行态。
- checkpoint 与成功状态同时存在且 hash 可复算。
- 同一 execution graph 最多存在一个 `activeRunId` claim。
- `commitIntent` 只在全部节点与整图验证成功后出现，并固定完整 canonical Draft payload、Draft payload hash 和 immutable validated-content digest。
- revision CAS 失败不覆盖新状态。
- 成功执行必须有 final result reference。

Runtime 允许的执行状态至少区分：

```text
created -> running -> pause_requested -> paused
                  \-> cancel_requested -> cancelled
running -> commit_prepared -> succeeded
                           \-> commit_blocked -> cancelled
running -> paused                    (retryable node failure / interrupted)
```

节点的 `logicalAttempts[]` 记录跨父 Run 的逻辑尝试；一个逻辑尝试内部的 HTTP attempts 仍只属于 Adapter。成功 checkpoint 必须是 Feature 对模型响应完成 strict decode、typed validation 和规范化重构后的 domain payload，禁止保存完整 Prompt、Provider response body、原始 completion、stack trace、credential 或未脱敏错误文本。

执行图使用项目内原子文件仓库，例如：

```text
.ats/execution-graphs-v1/<executionGraphId>.json
```

临时文件只允许同目录 staging + atomic rename。损坏、重复节点、非法边或 hash 不匹配必须阻止该 graph 的结构恢复，不得猜测或跳过。Runtime/Adapter 的结构恢复不解释 Feature payload schema；未知 blueprint/checkpoint schema 在 Feature resume 前返回 typed failure，只阻止该 graph 恢复，不阻止项目和既有 Draft/Item 打开。

## 6. Run 与恢复语义

一个用户业务动作仍对应一个公开 Feature Run。节点 checkpoint 记录在执行图中，不为每个节点新增 Character/游戏专用 Feature，也不扩张当前公开 12-Feature catalog。

`composition.plan` 的持久化 request 需要加入后端生成的 tagged execution identity；调用方不能自定义内部 ID：

```text
execution:
  start:
    executionGraphId
  resume:
    executionGraphId
    expectedRevision
    previousRunId
```

Shell 在 Run 创建前生成 `ExecutionGraphId` 和候选 `RunId`。初次执行使用 repository `createClaimed(graph, runId)`；恢复使用 `claim(executionGraphId, expectedRevision, newRunId, previousRunId)`。只有 claim 成功后才持久化并启动新 Run，claim 冲突直接返回 typed conflict，不留下一个伪 Running Run。

如果 claim 成功后 Run repository create 失败，Shell 必须在返回前以 revision-CAS 补偿为 paused；补偿也失败时，ProjectSession structural recovery 根据缺失/非运行 active Run 将 graph 收敛为 paused。任何时候同一 graph 都只能有一个 active Run。

```text
首次执行：
Run A (composition.plan, running)
        |
        +--> ExecutionGraph E / revision 1..N
        |
        X 进程退出

重新打开工程：
Run A -> run.interrupted，保持终态证据
ExecutionGraph E -> paused，保留成功 checkpoints

用户恢复：
Run B (composition.plan, new Run ID)
        |
        +--> 引用同一个 ExecutionGraph E
        +--> 只继续未完成节点
```

不得把已失败或 interrupted 的 Run 改回 running。每次恢复创建新 Run，并在 request/result provenance 中记录 execution graph ID、起始 revision 和前一 Run ID。最终成功 Run 引用 execution graph ID/hash、Draft ID/hash 和最终 graph hash；历史失败 Run 继续可审计。

如果 graph 已经 succeeded、但原父 Run 在写入成功终态前崩溃，原 Run 仍由 reconciliation 标记 interrupted。后续 resume 不重新 claim 或执行模型节点，而是复核 graph final reference 与 Draft provenance 后创建一个新的幂等成功 Run。

### Draft / ExecutionGraph / Run 提交协议

`CompositionDraft` 合同需要升级并持久化 `sourceExecutionGraphId` 与 `validatedContentDigest`。最终 Draft 使用如下可恢复提交顺序：

```text
1. Feature 构造完整 canonical Draft payload/bytes
   + draftId
   + sourceExecutionGraphId
   + validatedContentDigest
   + 固定 createdAt / updatedAt
   + draftPayloadSha256
              |
              v
2. Graph CAS: running -> commit_prepared
   固定 CommitIntent(
     draftId,
     canonicalDraft VersionedPayload,
     draftPayloadSha256,
     validatedContentDigest)
              |
              v
3. DraftRepository.createOrMatch(...)
   不存在：create-new
   已存在且 provenance + bytes hash 完全一致：idempotent match
   已存在但任一值不同：typed commit conflict，绝不覆盖
              |
              v
4. Graph CAS: commit_prepared -> succeeded(finalResultRef)
              |
              v
5. Parent Run -> succeeded
```

`validatedContentDigest` 的 hash 域固定为不可变验证内容：owner Feature ID、request snapshot hash、blueprint schema/hash，以及按 node ID 排序的成功节点 `nodeId/roleId/dependsOn/checkpoint schema/checkpoint hash` 和本地最终化结果。它明确排除 execution revision/status、active/previous Run ID、attempt/timestamp/failure、commit intent、final result reference 等执行态元数据，因此在 `commit_prepared -> succeeded` 后不会漂移，也不包含自身形成递归 hash。

`commitIntent.canonicalDraft` 是 Feature strict validation 后重新构造的正式 Draft domain payload，不是 Prompt 或 Provider 原始响应。所有时间戳在 intent CAS 前固定；恢复只能使用 intent 中的精确 payload bytes 调用 `createOrMatch`，不得重新生成时间戳或从 hash 猜测内容。

Crash recovery 必须覆盖：

- Graph 已 `commit_prepared`、Draft 尚未创建：使用 intent 内完整 canonical Draft payload 创建。
- Draft 已创建、Graph 尚未 succeeded：`createOrMatch` 复核后 roll forward。
- Graph 已 succeeded、Run 尚未 succeeded：旧 Run interrupted；新 resume Run 复核后幂等成功。
- Draft ID 已存在但 provenance/hash 不匹配：graph 进入正式 `commit_blocked`，父 Run failed，返回 typed `composition.commit.conflict`，不猜测成功。

`commit_prepared` 是 roll-forward-only 状态：structural recovery 清除 stale `activeRunId` 但不得将其降回普通 paused；resume claim 可以原子 claim 该状态，但只允许执行 `createOrMatch + graph/Run roll forward`，不得重跑模型节点、修改 checkpoint、生成新 Draft ID 或改写 intent。`commit_prepared` 不允许 Pause/Cancel。

`commit_blocked` 保留 immutable intent 与冲突证据，不允许普通 retry/resume 改写。用户只可检查 typed conflict，或显式 Cancel 该 graph 后以新 execution graph 重新计划；Cancel 不删除或修改既有 Draft、intent、Run 或其他证据。

## 7. Blueprint 与 Pack 合同

现有 `compositionProfiles` 继续声明 preset/custom 参数和节点上限。`pack.composition-plan-guidance` 升级到严格 v2，为同一 Item 类型的不同逻辑角色提供稳定 node group ID，并让 reference rules 指向明确 group，而不是仅比较总数。

概念结构：

```text
composition
|
+-- nodeGroups[]
|   +-- id
|   +-- itemType
|   +-- count { base, parameterId?, multiplier }
|   +-- dependsOnGroupIds[]
|   +-- generationKind = model_item
|
+-- coordination
|   +-- suiteBrief { enabled, guidance[] }
|
+-- bindingRules[]
|   +-- sourceGroupId
|   +-- slotId
|   +-- targetGroupIds[]
|   +-- measure = bindings | total_quantity
|   +-- quantityPolicy
|       +-- constant { value }
|       +-- brief_distribution { totalParameterId, minPerTarget, maxPerTarget }
|
+-- guidance[]
```

严格规则：

- `nodeGroups[].id` 在一个 composition 内唯一；每个 Item 节点只属于一个 group。
- `dependsOnGroupIds`、`sourceGroupId` 和 `targetGroupIds` 必须引用已声明 group；重复 target group 在 Pack load 时失败。
- target union 按 group ID、再按组内 node ordinal 稳定排序和去重；因为 group 不重叠，同一 Item 不得通过多个 group 重复进入同一 slot。
- count 解析为零的 group 不创建 Item 节点。绑定指向零节点 group 时，只有解析后的 measure 为零且对应 reference slot 允许零项才合法，否则 Preflight 失败。
- 同一 `sourceGroupId + slotId + measure` 只能有一条规则，不允许靠多条规则隐式累加。
- `bindings` 精确限定目标节点集合；`total_quantity` 必须指向同一集合并闭合 quantity。
- `brief_distribution` 由 Suite Brief 返回每个稳定目标 node ID 的数量；Feature 验证每项 min/max、目标全集、无重复且总和精确等于 `totalParameterId`。它是经过 checkpoint 固定的受控语义值，不是模型创作 reference identity/hash。
- 未启用 Suite Brief 的 composition 不得使用 `brief_distribution`。

Pack 只声明角色、数量来源、允许依赖、binding 目标和游戏指导；`ats-features` 编译稳定 Item ID、节点实例、执行顺序和 typed schema。Pack 不声明 HTTP 重试、文件路径、线程、任意命令或 Provider 配置。

Pack node groups 只描述业务 Item 节点。Feature 为执行图增加固定的通用本地阶段，避免把工作流代码放进 Pack：

```text
coordination.brief                    (可选 model coordination node)
item.generate:<groupId>:<ordinal>     (Pack group 编译的 model item node)
graph.finalize                        (local reference binding)
graph.validate                        (local full validator)
draft.commit                          (local durable commit protocol)
```

这些执行 role 是跨游戏 Feature 合同，不包含 `character/starter/common/rare` 常量。

Character Prototype 的确定性 Blueprint：

```text
Character x1
|
+-- starting_deck ----> starter Card x3，quantity 总和 10
+-- cards ------------> starter x3 + common x3 + uncommon x2 + rare x1
+-- starting_relics --> starter Relic x1
+-- relics -----------> starter Relic x1

全部 Card/Relic --owner_character identity--> 预分配的 Character Item ID
```

## 8. 分阶段执行流程

```text
[Preflight]
 Pack / Truth / Profile / Resource / request validation
       |
       v
[Compile Blueprint]
 本地确定 node IDs、roles、counts、dependencies
       |
       v
[Suite Brief, when declared]
 Character 使用小型 typed 请求固定玩法主题、节点职责和数量分配
       |
       v
[Node Loop, concurrency = 1]
 依赖 ready -> FIFO -> model -> typed validate -> checkpoint
       |
       v
[Root Finalization]
 本地附加 identity/pinned references 和 definition hashes
       |
       v
[Full Graph Validation]
 exact counts / types / quantities / closure / readiness
       |
       v
[Commit Prepared]
 固定 canonical Draft payload / payload hash / validated-content digest
       |
       v
[Draft createOrMatch + Graph/Run roll forward]
```

模型可以生成 canonical fields、localization 和 behavior intent，但不能创作以下事实：

- Item/current identity。
- Pack、Truth、Resource provenance。
- definition hash。
- node dependency edge。
- pinned target hash。
- Resource selection。

这些字段由本地根据 pinned request、Pack 和已验证 checkpoint 确定性附加。

## 9. 队列与重试策略

执行图和 HTTP 队列承担不同职责：

```text
ExecutionGraph
    决定：下一个合法节点、暂停/恢复、最终是否完整

ModelRequestQueue
    决定：何时允许发出下一次 HTTP attempt
```

默认策略：

- 节点模型请求并发度固定为 1。
- 每个节点逻辑请求获取一个共享 FIFO 席位，并持有到该节点成功、耗尽或取消。
- 节点结束后释放席位；下一个节点重新排队，接受全局最小间隔。
- HTTP transport retry 仍由 Adapter 处理，并尊重 typed config 和 `Retry-After`。
- Feature 不增加第二层自动 retry loop；JSON decode、typed validation 或业务校验失败后，节点进入 failed、graph paused。
- 用户显式 `retry/resume` 创建新父 Run，并为目标节点追加一个 logical attempt；无关成功 checkpoint 不重新请求。
- 取消在 queued/running 状态均可观察；queued 取消不得发 HTTP。
- 不自动切换模型、endpoint 或 response format。

未来可在 Runtime 合同中保留 `maxConcurrency`，但本阶段只接受值 1，不实现并发执行。

## 10. 失败与恢复矩阵

| 失败 | 处理 | 正式 Draft/Item/工程影响 |
| --- | --- | --- |
| Preflight 不满足 | 创建模型节点前 typed fail | 无 |
| HTTP retryable failure | Adapter 有界重试；耗尽后节点失败、graph paused | 无 |
| 输出无法解码或 typed validation 失败 | 不自动重试；节点失败、graph paused，失败响应不进入 checkpoint | 无 |
| 单节点失败后人工重试 | 新 Run claim 同一 graph，为该节点追加 logical attempt | 无 |
| 应用退出/崩溃 | 旧 Run interrupted；running 节点恢复为 paused/failed-interrupted | 无 |
| checkpoint hash/schema 损坏 | 阻止该 execution graph 恢复并返回 typed storage failure；既有已发布工程仍可读取 | 无猜测写入 |
| 最终 graph validation 失败 | graph 保留，可定位失败节点；不创建 Draft | 无 |
| Draft create 冲突 | `createOrMatch` 只接受完全相同 provenance/bytes hash；否则 typed conflict | 既有状态不变 |
| 后续 whole-closure generation 失败 | 复用现有 rollback transaction | 已发布状态不变 |

### ProjectSession 恢复顺序

恢复拆成结构层与业务层，不能要求 ProjectSession 解码 Feature payload：

```text
1. project publication journal recovery
2. execution graph structural recovery
   - 文件/schema envelope/hash/DAG/CAS
   - running node 与缺失 active Run 收敛为 paused
3. Run reconciliation
   - 未终态旧 Run -> run.interrupted
4. session exposure
5. 用户 resume 时由 owning Feature
   - 加载 pinned Pack/contribution
   - 解码 blueprint/checkpoint
   - 复核 Draft commit intent/final reference
```

未知 Feature payload schema、Pack 不匹配或 checkpoint domain validation 失败只阻止该 graph resume，并返回 typed actionable failure；不得阻止用户打开既有正式项目内容。

## 11. UI 与用户流程

Composition Studio 只显示后端返回的 typed graph state：

```text
计划：Character Prototype
进度：7 / 12 stages

[完成] Suite brief
[完成] Starter Card 1
[完成] Starter Card 2
[失败] Starter Card 3   [重试]
[等待] Reward Cards
[等待] Character root
```

- Tauri 返回独立 `ExecutionGraphView`，只包含 graph ID/revision、节点 role/ordinal、进度、状态、logical attempt 数、安全 failure 和当前允许的 actions；内部 blueprint/checkpoint payload 不进入 IPC。
- 节点证据固定包含 logical attempt、`modelRequestSha256`、规范化 checkpoint hash、允许保留的 model/usage 摘要和 terminal safe failure；禁止 Prompt、Provider body 和原始 completion。
- 最终 Plan result 绑定 execution graph ID/hash、Draft ID/hash 和 validated-content digest，不再只依赖单个整图 `modelRequestSha256`。
- `暂停`：先 CAS `running -> pause_requested`，成功后才发送 `execution_paused` control reason；不再调度新节点，当前 HTTP 请求结束。
- `恢复`：创建新父 Run，复用同一 execution graph。
- `重试节点`：仅对失败节点及依赖其内容的本地最终化结果失效，不重做无关 checkpoint。
- `取消计划`：先 CAS `running/paused -> cancel_requested/cancelled`，再发送 `execution_cancelled` control reason；取消后的 graph 不可恢复，如需重新开始则创建新 execution graph。
- 只有完整 Draft 创建后才进入现有 Draft review、Resource Workbench 和确认流程。

React 不根据前端数组推导可运行节点，不在刷新后自行恢复任务，也不把本地轮询错误当作后端终态。

### Pause / Cancel / Shutdown 终态

Runtime 必须给 execution control reason 建立稳定 typed 合同，不能继续把所有控制都折叠成同一个 cancellation：

| 原因 | Graph | 当前节点 | 父 Run |
| --- | --- | --- | --- |
| 用户 Pause | `paused` | 未形成成功 checkpoint 的输出丢弃，保留 interrupted logical-attempt evidence，节点回到 pending/failed-interrupted | `cancelled`，reason=`execution_paused` |
| 用户 Cancel | `cancelled` | `cancelled`，不保存模型输出 | `cancelled`，reason=`execution_cancelled` |
| Graceful App shutdown / ProjectClose / ProjectSwitch | `paused` | in-flight attempt 按原 control reason 标 cancelled，不保存未完成输出，节点回到 pending | `cancelled`，保留现有 `AppShutdown` / `ProjectClose` / `ProjectSwitch` reason |
| Abrupt crash / process stop | open 时 structural recovery 后 `paused` | running attempt 标 interrupted，无成功 checkpoint 时回到 pending | reconciliation 后 `run.interrupted` |

控制竞争使用 graph revision CAS：第一个成功的 `pause_requested` 或 `cancel_requested` 决定当前控制结果，后续使用旧 revision 的请求返回 typed conflict。已经 paused 的 graph 允许用户随后显式 Cancel。模型响应与 Pause 竞争时，checkpoint CAS 先成功则 Pause 必须用新 revision 重试；Pause CAS 先成功则响应不得提交 checkpoint。底层 cancellation token 继续遵循 first-cancellation-wins。

Graceful App shutdown、ProjectClose 和 ProjectSwitch 使用各自现有 cancellation reason：Shell 先把普通 running graph CAS 为 `pause_requested`，再发送原 control reason，worker 收敛为 paused，父 Run cancelled。Abrupt crash 没有完成该终态写入，才由下一次 open 标记 graph/attempt interrupted 并通过 Run reconciliation 产生 `run.interrupted`。`commit_prepared` 不响应 pause；正常关闭只能尝试完成 roll forward，未完成时保持 intent，下一次 open/resume 继续提交。

## 13. 完成标准

- 单节点上游失败不会丢失其他已验证节点。
- 关闭并重开应用后，可以从 durable checkpoint 继续，旧 Run 不被复活。
- start/resume claim 保证同一 graph 最多一个 active Run；并发 loser 不产生伪 Running Run。
- 所有节点请求默认串行，并继续受共享 FIFO 和全局间隔控制。
- Feature 不执行自动语义重试；decode/typed failure 暂停 graph，只有用户显式操作才创建新的 logical attempt。
- 中间 checkpoint 不进入 Draft、Item repository current pointer、Artifact 或工程 published files。
- Checkpoint 只保存规范化 domain payload；持久化文件和 IPC 均不含 Prompt、Provider body 或原始 completion。
- 完整 graph validation 通过后通过 commit intent + `createOrMatch` 只创建一个正式 CompositionDraft；三个 crash window 均能幂等 roll forward 或 typed conflict。
- Character Prototype/Standard/Custom 的节点数量和引用合同仍由 Pack 证明。
- Pack v2 对 node group、target union、quantity、零节点和 local/model stage 的行为有严格可执行 schema，不依赖游戏类型硬编码。
- STS2 之外的 synthetic Pack fixture 能使用同一执行图和 staged coordinator，不存在 STS2/Character 分支。
- Runtime、Adapter、Shell 不出现游戏类型、Profile 数量或游戏 Prompt。
- Pause、Cancel 和 Shutdown 产生不同 graph/node/Run 终态，并通过 revision CAS 解决竞争。
- Stable specs、架构总览、错误处理、前端合同和当前事实与代码在同一实施任务中同步。
- 新 candidate 和全部真实验收证据不复用历史结果。

## 17. Whole-closure Generate 的同图恢复扩展

`rc-20260810T093305Z-cd38919f727e` 已证明分阶段 Plan 不能单独解决最终生成稳定性：第一次
`composition.generate` 在首个 Character Plan 截断；第二次该 Plan 成功后，Character Single
typed output invalid。旧实现虽然通过共享 FIFO 严格串行，但所有 Plan/Single proposal 只存在于
父 Run 内存中，任何节点失败都会让下一次 Generate 从第一个 Item 开始。

当前代码将同一 Runtime graph 扩展到 whole-closure Generate，不增加 Feature 或游戏分支：

```text
ResolvedItemGraph (exact root hash / pinned closure)
        |
        v
item.000.plan ---- checkpoint(typed Plan + child Run)
        |
        v
item.000.single -- checkpoint(canonical bundle + safe provenance + child Run)
        |
        v
item.001.plan -> item.001.single -> ...
        |
        v
composition.finalize
  restore exact proposals without ModelClient
  -> merge / Primitive / project-write validation
        |
        v
commit_prepared(publication intent)
        |
        v
isolated validation -> Build -> Package -> project transaction -> one Artifact
        |
        v
graph succeeded -> parent Run succeeded
```

关键边界：

- `composition.generate` request/result 和 Artifact extension 升级为 v2，并绑定
  `executionGraphId`；initial request 不允许调用方 author `execution`。
- graph 节点数固定为 `2 * resolvedItems + 1`，依赖链本身保证默认串行；共享 FIFO 继续负责
  HTTP attempt 调度，两者职责不重叠。
- Single checkpoint 保存 strict decode 后的 role-keyed canonical contents，而不是 Prompt、HTTP
  body 或 raw completion envelope；恢复时重新验证 definition hash、Pack role contract、精确
  selected Resource versions 和 project writes。
- checkpoint CAS 后 child Run 使用精确 ID/bytes create-or-match。进程在二者之间退出时，可由
  checkpoint 补齐 child Run，不覆盖不同证据。
- Plan/Single 语义失败保留原始 `model.*` family 并暂停当前节点；显式 Resume 创建新父 Run，
  只执行 Pending 节点。`commit_prepared` 失败只释放 active claim，不回退模型 checkpoint。
- generic `resume_execution_graph` 按 persisted owner Feature 分派；React 只看 guarded View 与
  returned Run `featureId`，不解码 checkpoint 或自行推导 DAG。
- succeeded graph reconciliation 只解码 final result 并成功一个新父 Run，模型、验证、Build、
  Package、工程事务和 Artifact 调用均为零。
