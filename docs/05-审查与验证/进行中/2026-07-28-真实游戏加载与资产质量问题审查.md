## 3. P0：首战能量行为失效

### 3.1 生成结果

`E2EEnergySeedRelic.cs` 使用：

```csharp
public override async Task BeforeCombatStart()
{
    Flash();
    await PlayerCmd.GainEnergy(1m, Owner);
}
```

该代码可编译且 hook 会发火，但不能实现“首回合多 1 点可用能量”。

### 3.2 根因

1. `CombatManager.StartCombatInternal()` 先在 `CombatManager.cs:219` 调用 `Hook.BeforeCombatStart(...)`。
2. 首个玩家回合的 `SetupPlayerTurn()` 随后在 `CombatManager.cs:385-394` 执行 `ResetEnergy()` 和 `AfterEnergyReset`。
3. 因此 `BeforeCombatStart()` 增加的能量被回合开始的能量重置覆盖。
4. 官方 `Lantern` 的真实实现使用 `AfterSideTurnStart(CombatSide, CombatState)`，在能量重置之后限定玩家阵营和首回合，再调用 `PlayerCmd.GainEnergy(...)`。

这是**时序语义错误**，不是 API 或编译错误；现有 compile gate 无法发现。

### 3.3 错误来源

- `crates/ats-core/templates/sts2/relic.md:32-35` 直接提供了 `BeforeCombatStart + GainEnergy` 的错误示例。
- `runtime/knowledge/resources/sts2/relic.md` 与模板已漂移：它删除了该能量示例，但也没有提供官方的正确首回合能量配方。
- 原始 API 列表只证明 hook 存在，不证明它适合某个行为意图。

### 3.4 修复验收标准

- 生成代码不再用 `BeforeCombatStart()` 实现首回合获得能量。
- 根据当前官方行为使用 `AfterSideTurnStart(...)` 或经同等时序证据确认的实现，同时限定 Owner 阵营和首回合。
- 自动化门禁能拒绝 `BeforeCombatStart + GainEnergy` 这一已知反模式。
- 用户在真实游戏内人工确认：首回合能量比基础值多 1，后续回合不重复触发。

### 3.5 P0-1 自动修复状态（2026-07-29）

已完成代码与自动化层修复：

- 稳定 relic 模板不再包含 `BeforeCombatStart + GainEnergy` 行为配方，规划阶段也不再在无源码证据时猜测 hook。
- 资产 codegen 会用本次 `requirements` 检索当前反编译源，注入官方相似实现的有界方法体，并沿 override 名称检索生命周期调用方。
- 当前能量需求的真实源码静态评分以 `Lantern.cs` 为最高相关相似实现，`CombatManager.cs` 是 `Hook.AfterSideTurnStart` 的生命周期调用方；自动 fixture 固定验证 Owner side、首回合 guard、`ResetEnergy` 和 hook 顺序片段均进入 prompt。
- 每次成功的结构化资产生成新增 `artifacts/<asset>/evidence.md`，保留实际 knowledge manifest 快照、source mode、需求、symbol、路径/行号、证据用途和注入 facts。
- 新增通用 `forbidden_call_in_method` 规则执行器；STS2 规则在正式写盘和 compile gate 前拒绝 `BeforeCombatStart` 方法体内调用 `PlayerCmd.GainEnergy`，并指向 `SetupPlayerTurn.ResetEnergy` 时序。
- 针对性测试覆盖正确后置 hook、错误组合、注释/字符串、不同方法、表达式方法、写盘前拒绝和 compile validator 未调用。

尚未完成：新 LLM 候选生成、候选 compile gate/build/package 和用户真实游戏行为复验。以上自动修复不等于首回合能量已经在游戏中复验通过。

## 4. P0：背景去除通过但视觉质量失败

### 4.1 文件事实

三张运行时 PNG 均为 `1024×1024`，且有完全相同的 SHA-256：

```text
2F34CD82B9F213F1A08DFC0C7F10C354C53B9A3306D0C0A28EF922C11140269B
```

每张图的 alpha 统计：

| 指标 | 值 |
| --- | ---: |
| alpha = 0 | 587,736 |
| alpha = 255 | 460,840 |
| 中间 alpha | 0 |
| 透明但 RGB 非黑 | 587,736 |
| 非透明包围盒 | `(0, 0) - (1023, 1023)` |

这些数据不能单独证明所有边缘都错，但与源图的棋盘/复杂浅色背景、不透明像素触及四边和用户看到的噪点一致。

### 4.2 根因

- `SimpleBgRemover` 只会把 RGB 三通道都不低于 `235`、且通道差不超过 `20` 的浅灰/白像素设为透明。
- 文生图返回了棋盘格/复杂浅色背景；启发式只删除了其中一部分，剩余格子仍为不透明前景。
- `asset_generate` 把“背景处理函数返回 `Ok`且写盘成功”当作可交付，没有 alpha、边界、连通域、棋盘残留或尺寸语义的质量门禁。
- `asset_bundle.rs:431-436` 将同一组字节复制到 normal、outline 和 big 的所有目标路径，没有真正的资源派生。

### 4.3 修复验收标准

- 图片处理不得仅以“有 PNG 输出”判定成功；必须输出可解释的质量指标和通过/拒绝结论。
- 明显棋盘背景、边缘噪点、前景无意义地触及全部图像边缘时，任务不得标记为可交付成功。
- normal、outline、big 必须按资源语义生成/派生和独立验证，不得无条件复制同一字节。
- 自动化覆盖 Good/Base/Bad 图：真透明主体、纯白背景回退、棋盘/复杂背景拒绝或 ML 处理。
- 用户在真实游戏中人工确认普通图标、outline 显示场景和大图无噪点、棋盘格、黑边、裁切或异常缩放。

### 4.4 P0-2 自动修复状态（2026-07-29）

已完成代码与自动化层修复：

- 新增通用 PNG 质量报告，明确记录尺寸、alpha/前景比例、连通域、边界接触、浅色中性残留、判断阈值、问题码和通过/拒绝结论。
- 默认门禁要求透明像素不少于 5%、前景不少于 1%、最大前景连通域占比不少于 60%、边界前景不高于 30%、边界浅色中性残留不高于 15%。棋盘 fixture 会以 `likely_background_residue` / `fragmented_foreground` 在代码生成和 compile gate 前被拒绝。
- 背景处理解码/执行失败不再静默使用原图；原图只作为诊断文件保留。质量拒绝时同时保留 raw、rembg 和 `image-quality.json`。
- 通用角色派生器按声明执行 cover resize 和 alpha-outline；当前 STS2 relic 声明为 normal `128×128`、outline `128×128`（空心白色 alpha 轮廓，半径 4）和 big `1024×1024`。三者字节必须互不相同，事务写入前还会分别验证尺寸以及 normal/big 质量或 outline alpha 语义。
- 正式资源仍进入原有事务；compile gate 失败会回滚项目内图片，诊断文件继续保留。

尚未完成：真实 LLM/image generation 新候选、候选 compile gate/build/package、文件级候选审查和用户真实游戏视觉复验。自动 fixture 通过不等于真实生成图片已经通过游戏内验收。

探针同时发现并修复两个缓存缺陷：仓库原 u2netp SHA-256 常量错误；下载实现整包缓冲且没有超时、续传或 Runtime 哈希门禁。当前实现使用流式落盘、连接/停滞/总超时、匹配 `Content-Range` 的断点续传，并固定校验 u2netp、ONNX Runtime ZIP 和 DLL。

当前机器的系统 `MSVCP140.dll` / `VCRUNTIME140.dll` 为 `14.00`，与 `_1.dll` 的 `14.44` 不一致，导致 ONNX Runtime 返回 Win32 1114。探针目录放置 Visual Studio 已安装的 14.38 x64 CRT 后推理成功，根因得到验证。正式实现不打包 CRT；加载异常会转为 `PrewarmStatus::Failed` 并提示安装或修复 Microsoft Visual C++ 2015-2022 Redistributable (x64)。安装版 prewarm 和新候选仍待系统前置条件处理后复验。

修复时应以当前游戏 manifest schema 和 BaseLib 3.3.8 实际要求为准，更新 scaffold/模板与对应验证，不应只修此次临时产物。

## 8. 模板、知识与多游戏边界（已决策）

后续讨论否决了“每个功能建立持久化行为契约 SSOT”的方案。该方案本质上是对某次源码解释的语义缓存，会新增契约选择、版本迁移和错误结论集中扩散的风险；对多游戏目标也会形成过重的中间层。

已确认的最终边界是：

- AgentTheSpire 是通用的资源获取、知识检索、生成、验证、构建与打包流水线。
- 游戏差异以 Game Pack 中的真相源、专属资源和声明数据表达，不为每个游戏复制一套厚 Adapter。
- 游戏行为生成每次从当前版本真相源检索证据，并记录本次 Evidence Record；不持久化功能答案作为跨任务权威。
- 模板只保留稳定工程结构；通用验证引擎读取 Game Pack 中的 schema、稳定约束和少量已知错误规则。
- 真实游戏行为与视觉验收继续由用户人工完成。

权威决策见 [ADR 0004 — 通用 Mod 生产流水线与 Game Pack 边界](../../04-决策/0004-generic-mod-pipeline-and-game-pack.md)。本审查后续只跟踪能量 hook、图片质量、资源派生和 manifest 修复，不再作为多游戏架构决策入口。
