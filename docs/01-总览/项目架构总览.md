## 项目定位

AgentTheSpire 是 AI 驱动的 Mod 生产工具。当前首要目标游戏是《杀戮尖塔 2》，核心链路为：

```text
自然语言需求
  → 知识检索与规划
  → LLM/图像生成
  → 结构与编译验证
  → 构建和打包
  → 真实游戏人工验收
```

## Workspace

```text
.
├─ Cargo.toml
├─ crates/
│  ├─ ats-core/       领域逻辑、Prompt、STS2 模板
│  ├─ ats-web/        axum HTTP 与静态资源壳
│  └─ ats-cli/        构建、部署、日志和停止命令
├─ src-tauri/         Tauri v2 桌面壳与 IPC commands
├─ src/               React 19 + TypeScript 共享前端
├─ runtime/           运行配置、知识库和运行产物入口
└─ scripts/           CI、E2E 和辅助脚本
```

Cargo workspace 使用 Rust edition 2024，并禁止 `unsafe_code`。`ats-core` 不依赖具体 UI 或传输框架，桌面/Web/CLI 只负责装配和 IO 边界。

## 核心模块

`ats-core` 当前导出以下主要能力：

| 范围 | 主要模块 | 职责 |

## 桌面壳

`src-tauri` 以 Tauri IPC 暴露 core 能力，不在桌面进程内启动 HTTP 服务。主要托管：

- 当前配置快照及保存后的热替换。
- app data 路径和 recent projects。
- `ActiveProject -> Arc<ProjectSession>`，统一持有当前工程、操作系统文件锁、共享 Run repository 和活动 task scope。
- image processing prewarm 状态。
- project、run、knowledge、planning、codegen、LLM、settings 和 plan artifact commands。

启动期非致命预热通过后台任务执行，窗口不等待 ML 模型或缓存准备完成。

工程 Run 的生命周期由桌面 composition 层统一管理：

```text
ActiveProject
  lifecycle mutex
  current: Arc<ProjectSession>
             |
             +-- ProjectFolder / OS exclusive lock
             +-- Arc<FileRunRepository>
             +-- RunTaskScope
             |     run-id -> CancellationToken + JoinHandle
             +-- state: open | closing

submit
  -> 在同一 task-scope 临界区检查 accepting 并注册 SpawnedRun

close / switch / app ExitRequested
  -> enter closing
  -> reject new submissions
  -> cancel every project Run
  -> wait for stream / file rollback / image worker / process tree cleanup
  -> drained: release OS lock
  -> 30s timeout: keep closing + task handles + OS lock
```

Tauri 应用退出通过 `RunEvent::ExitRequested.prevent_exit()` 先排空活动工程；排空成功后内部放行一次 `app.exit(code)`，避免退出事件递归。异常进程终止留下的 Pending/Running Run 在下次 `ProjectSession::open` 返回前统一 reconciliation 为 `failed + run.interrupted`。全局 ML prewarm 不读写工程，因此不注册到 ProjectSession。

Core 根级 `failure` 模块定义唯一的 `ActionableFailure` schema 和 typed normalizer。`RunRecord.failure` 直接保存该类型；Tauri 只用透明 `CommandFailure` newtype 将相同 JSON object 作为 command reject value 返回，不复制领域字段，也不把未知错误的 `Display` 文本暴露给前端。

## Web 与 CLI 壳

`ats-web` 当前是轻量 Web 入口，装配 health、knowledge、planning、codegen、LLM 和静态前端。它不是完整 SaaS 平台，也没有开放端口所需的完整应用鉴权，因此默认只应绑定本机或放在外部鉴权代理之后。

`ats-cli` 提供自动化和运维入口。壳层不得复制 core 中的任务、构建或错误分类逻辑。

## 共享前端

前端使用 React 19、TypeScript 5.6、Vite 6、Zustand 5 和 HashRouter。主要页面包括 Dashboard、Mod Editor、Batch Generation、Log Analysis、System、Settings 和 DevTools。

`src/services/api.ts` 根据构建期 `__IS_TAURI__` 选择：

- `tauriApi.ts`：通过 Tauri `invoke` 调用桌面 commands，并作为 API 类型权威。
- `webApi.ts`：通过 HTTP 调用 `ats-web`，必须满足与 `tauriApi.ts` 相同的导出签名。

页面组件只消费统一 API，不自行维护桌面/Web 两套业务流程。

所有 Tauri `invoke` 经过 `invokeCommand` 和严格 runtime guard。React 错误 state 使用 `ActionableFailure | null`，统一由 `ActionableErrorNotice` 展示安全 message、恢复动作提示和可选 diagnostic ID；字符串或畸形 reject 固定降级为本地 `core.unclassified`，原值不进入 UI。

```text
typed Core error
  -> FailureNormalizer
  -> ActionableFailure
       +-> RunRecord.failure
       +-> CommandFailure (transparent Tauri reject)
              -> invokeCommand runtime guard
              -> ActionableErrorNotice
```

## 工程数据

桌面端不依赖数据库，每个 Mod 工程是可复制、可归档的自包含目录。核心内容包括：

```text
<project>/
├─ project.json
├─ plan.json
├─ items/
├─ artifacts/<artifact-id>/runs/<run-id>/
│  ├─ artifact-manifest.json
│  └─ files/
├─ history/                 # schema v2 RunRecord
├─ Generated/
└─ .ats/
   ├─ lock
   └─ diagnostics/<run-id>/
```

`RunRecord v2` 是执行状态、timeline、failure 和 result 的唯一事实；独立 Run lifecycle audit 已删除。成功产物先以不可变 `ArtifactManifest` 和文件哈希发布，再通过 repository CAS 完成 Run；失败诊断进入 `.ats/diagnostics/<run-id>/`，不能污染正式工程文件或成功 Artifact Store。图片 ArtifactManifest schema v2 还保存实际 processor、model SHA、ONNX Runtime、fallback 原因和编译期 BuildInfo；图片质量报告与 processor provenance 是两个独立事实。

候选构建身份由 `ats-core/build.rs` 从受控环境和实际 Cargo feature 嵌入，health、capabilities 与图片 provenance 读取同一个 `BuildInfo`。`build.ps1 -Variant Baseline|Ml` 使用 `artifacts/build/<variant>/<build-id>/target` 隔离 Cargo/Tauri 输出，再把本次 bundle 复制到 `artifacts/release/<build-id>/<variant>` 并生成 SHA-256 manifest；脏工作区、variant/feature 不一致和复用 build ID 都在构建前拒绝。

## Mod 生产边界

长期目标是“一条通用 Mod 生产流水线 + 多个 Game Pack”：

- 通用引擎实现获取、索引、生成、验证、构建、打包和追踪机制。
- Game Pack 声明游戏真相源、专属资源、工程骨架、资源规格、验证规则和交付布局。
- STS2 的 C#、Godot、BaseLib、DLL/PCK 与具体 hook 属于 STS2 Game Pack 内容，不进入通用领域接口。

Game Pack Stage 1 已完成：工程通过 `game_id` 绑定受控 Pack，生成任务固定经过验证的 Truth Snapshot；STS2 的 guidance、模板、manifest、资源规格、验证规则、build recipe 和 package layout 已迁移到 `game_packs/sts2/`，通用 Core 只保留可复用执行器。当前仍只有 STS2 一个完整样本，workstation 发现 UI 和有限 `Sts2CodeFactsProvider` 是否继续声明化，等待第二个真实游戏需求后再决定。完整边界和实施依据见[通用 Mod 流水线与 Game Pack 边界](../03-当前方案/通用Mod流水线与Game-Pack边界.md)与[Stage 1 职责清单](../03-当前方案/2026-07-30-Game-Pack-Stage-1职责清单与迁移设计.md)。
