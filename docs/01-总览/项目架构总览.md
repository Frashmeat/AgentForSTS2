# 项目架构总览

> 文档定位：`rust` 分支跨阶段稳定架构、模块责任和主要执行流入口。
>
> 不包含：当前任务状态、candidate 账本或单个游戏的完整 Pack 细节。
>
> 事实入口：[`当前进度说明`](../02-现状/当前进度说明.md)。
>
> 最后更新：2026-08-24

## 1. 架构原则

AgentTheSpire 是桌面端优先、编译期约束依赖方向的模块化单体。

- Shell 只做交互和 IPC，不绕过 Feature 执行产品逻辑。
- Runtime 只拥有跨游戏稳定机制，不认识具体游戏、语言或工具链。
- Feature 拥有用户工作流、typed request/result、Graph 编排和领域验证。
- Game Pack 声明受控数据、Capability Catalog、Provider/Adapter 身份和游戏差异。
- Truth Snapshot 证明当前游戏、API 和工具链事实。
- Game Adapter 将已验证 Behavior IR 确定性渲染为游戏原生文件。
- Game Pipeline Provider 决定游戏专属 Validate/Build/Package 阶段。
- Workspace 保存可变工程状态和不可变证据；成功必须由 Run/Graph/Artifact 证明。

## 2. 总体结构

```text
React / Tauri IPC / desktop JSONL / CLI / Web catalog
                 |
                 v
        exact 12-Feature Registry
                 |
                 v
        typed Feature Services
          |             |
          |             +--> versioned Recipes -> ModelRequestSnapshot
          |
          +--> Pack v5 + Truth v2 + Item/Resource/Draft
                         |
                         v
              Capability Catalog + registered identities
                         |
               +---------+---------+
               |                   |
               v                   v
       Game Behavior Adapter   Game Pipeline Provider
               |                   |
               +---------+---------+
                         v
             Runtime DAG / Run / Graph / Artifact
                         |
                         v
       filesystem / HTTP / media / compiler / package adapters
```

依赖方向：

```text
Shell -> Feature -> Runtime ports / Game Context / Workspace -> Kernel
Adapter implementations -> Runtime and Game Context contracts
Game-specific crate -> Game Context contracts + Runtime ports
```

Kernel、Runtime、Game Context、Workspace 和 Adapter 不得反向依赖 Feature。Core、Feature 和
React 不得通过 `game_id == ...` 分支实现 STS2 或其他游戏规则。

## 3. Workspace 与 Crate 责任

| Crate/层 | 拥有 | 不拥有 |
| --- | --- | --- |
| `ats-kernel` | 稳定 ID、hash、schema ref、`ActionableFailure`、BuildInfo | IO、产品工作流、游戏分支 |
| `ats-runtime` | RunRecord v3、ArtifactManifest v3、ExecutionGraphRecord v6、DAG/CAS、claim、取消、事务意图、ports | Pack、Prompt 文本、游戏阶段 |
| `ats-game-context` | Pack v5、Truth/Evidence、Capability Catalog、Behavior IR、Provider/Adapter contracts 和 registry | HTTP、文件系统、产品编排 |
| `ats-workspace` | ProjectFolder、OS lock、Item/Draft/Resource、受控 `local.props` | 模型调用、游戏语义 |
| `ats-features` | 12 个 Feature、Recipe、typed request/result、Composition Graph、反馈与调整 | Provider SDK、Tauri/Axum、游戏硬编码 |
| `ats-game-sts2` | STS2 Provider v2、五类 deterministic Behavior Adapter、STS2 validate/build/package 物化 | 通用状态机、Shell |
| `ats-adapters` | Settings、HTTP model/media、repositories、PNG、dotnet、ZIP | Feature 编排、游戏产品流程 |
| `src-tauri` | Desktop composition root、Tauri IPC、production JSONL Shell、ProjectSession、task supervision、shutdown drain | Prompt、游戏规则、Graph 算法副本 |
| React | 用户工作流和受控状态展示 | checkpoint decode、DAG 推导、游戏专属生成逻辑 |
| Web/CLI | health、共享 catalog 和运维入口 | 第二套 project execution；当前 Web 不执行 Project |

`scripts/check-stage2-dependency-dag.mjs` 校验依赖方向。

## 4. Feature Registry

共享 catalog 精确包含：

```text
project.create
mod.plan
composition.plan
composition.retry-node
composition.generate
resource.prepare
mod.generate.single
mod.generate.batch
mod.generate.complex
log.analyze
project.build
project.package
```

- `composition.plan` 产生可审阅 Draft，不写 Item current pointer 或工程文件。
- `composition.retry-node` 只替换一个逻辑 Draft node，并重跑完整 Draft validator。
- `composition.generate` 使用 Typed Behavior IR 和确定性 Adapter 发布整个 closure。
- `mod.generate.single` 仍是独立 Feature，但 Composition 不调用它、不解析它的 contribution、
  checkpoint 或 result。
- Batch 仍复用 standalone Plan/Single；Complex 仍复用 Batch/Build/Package。它们不是
  Composition 的内部实现。

Execution Graph node 是 Feature 内部可恢复步骤，不是 catalog Feature。

## 5. Composition 生产链路

```text
confirmed root ItemDefinition
          |
          v
resolve exact pinned closure
          |
          v
optional item.N.plan
          |
          v
item.N.behavior -> strict BehaviorProposal schema v1
          |
          v
local IR validation -> registered deterministic Game Adapter
          |
          v
item.N.render -> RenderedItemBundle
          |
          v
composition.finalize
          |
          v
provider.validate -> provider.build -> provider.package
          |
          v
one atomic project publication + one immutable Artifact
```

AI 只拥有 Catalog-scoped capability invocation。confirmed localization、Resource 选择、reference、
identity、class/namespace、relative path 和 manifest 均由本地确定性代码产生。

同一 pinned ItemDefinition、Pack、Truth、Catalog、Adapter 和 Behavior IR 必须得到字节级相同的
RenderedItemBundle。合法 IR 若被 Adapter 渲染成不可编译原生文件，是本地 Adapter 缺陷，不进入
模型反馈。

## 6. Pack、Truth、Catalog 与 Adapter

Pack v5 在模型调用前完成：

```text
Pack bytes/schema/SHA
  + exact Truth Snapshot v2
  + Capability Catalog identity/version/SHA
  + Game Adapter identity/version/implementation SHA
  + Pipeline Provider identity/version
  -> exact readiness
```

Pack 只选择随应用注册的 Adapter/Provider，不能携带任意 shell、native plugin 或命令。
`itemTypes` 仍声明 canonical/localization fields、typed references、Resource profiles、
composition profiles 和 Evidence Queries；`behavior` 声明每类 Item 可用 capability 及参数合同。

当前 STS2 Pack 覆盖 Character、Card、Relic、Potion 和 Power。新游戏通过新的 Pack、Truth source、
Game Adapter、Pipeline Provider 和 fixtures 接入，不修改通用 Runtime 状态机。

## 7. 持久化与恢复

```text
<project>/
  project.json
  Generated/
  artifacts/<artifact-id>/runs/<run-id>/artifact-manifest.json
  .ats/lock
  .ats/version
  .ats/runs-v3/<run-id>.json
  .ats/items-v2/<item-id>/definitions/<definition-hash>.json
  .ats/composition-drafts-v2/<draft-id>.json
  .ats/execution-graphs-v5/<execution-graph-id>.json
  .ats/composition-staging/<run-id>/
  .ats/transactions/<run-id>/
```

ExecutionGraphRecord v6 保存 owner/request/Blueprint identity、节点 DAG、active checkpoint、
Behavior/Render provenance、安全 feedback envelope、parent Runs、commit intent、final result 和
revision。

- claim 必须在创建 Running parent Run 前通过 revision CAS。
- checkpoint 只保存 strict-decoded domain payload，不保存 Prompt、raw completion 或 Provider body。
- Behavior checkpoint 绑定 definition、Pack、Truth、Catalog、Adapter、request snapshot 和 IR hash。
- Render checkpoint 绑定完整 bundle 及每个文件 hash。
- Resume 只执行未成功节点；succeeded reconciliation 不调用模型、Adapter 或 Pipeline。
- 每个 Behavior baseline 都可执行一次；`semanticRequestCount` 只审计实际请求，
  `semanticFeedbackCount` 才受 shared allowance 限制。
- output/IR 问题可反馈当前 Item；Adapter/compiler/storage/publication 问题是 typed local failure。
- `commit_prepared` 只在完整 registered validation 成功后创建，之后只允许前滚或稳定阻塞。

ExecutionGraphRecord schema v6 只从当前 `.ats/execution-graphs-v5` repository generation 读取；
更早的 repository generations 保留为历史证据，不读取、不迁移、不删除。schema version 与
repository directory generation 是两个独立合同，不能按数字相等推断路径。

## 8. 单 Item 调整

用户只提供目标 Item 的自然语言调整词：

```text
executionGraphId + expectedRevision
+ itemId + expectedDefinitionHash
+ bounded instruction
```

系统仅重建目标 Behavior/Render checkpoint，然后复验整个 closure。调整后 Behavior hash 未变化、
重复 diagnostic+candidate、轮次耗尽或 unsupported capability 都安全停止。源 Graph、Run 和
Artifact 保持不可变；成功调整产生新的证据版本。

## 9. Publication 与 Artifact

所有 RenderedItemBundle 恢复并复验后，Provider 才能执行 whole-closure Validate/Build/Package。
工程 transaction 使用 prepared/committed journal 和同目录 rename 形成 durable commit decision。
Artifact 在同目录 staging 中完整写入并核验后原子 rename。

Composition result/artifact extension v4 必须保存 Behavior/Render provenance、Graph identity、
definition/model/resource/Pack/Truth/Adapter identities 和输出文件 hashes。失败不得留下伪 final
目录、伪 succeeded Run、partial publication 或 staging/transaction 残留。

## 10. Prompt、Shell 与安全

模型请求由 Recipe、Pack/Catalog、Truth Evidence、Item、Resource、sanitized Project Context、
`llm.custom_prompt` 和 typed output contract 装配为内存中的 ModelRequestSnapshot，并派生可持久化的
ModelRequestCommitment。桌面 composition root
持有唯一 FIFO；timeout/429/5xx 只在 transport 层有界重试，不形成语义修订。

React 只显示 generating、checking、auto-adjusting、needs-attention 和 preview-ready 等产品状态。
Graph node、compiler diagnostic、预算、repair counter、Adapter 内部身份不暴露给普通用户。

`ActionableFailure` 是跨 IPC/UI 的唯一失败形状。Prompt、raw completion、Provider body、secret、
未分类绝对路径和任意 SDK/IO 文本不得进入 Run、Graph、Artifact、IPC 或 release verification。

production desktop binary 额外提供本地 `--headless-jsonl` Shell。它通过重定向 stdin/stdout
执行 versioned typed commands，不打开 WebView 或网络端口，并与 Tauri IPC 共享相同 ProjectSession、
Stage2Composition 和 command service。每个响应绑定当前 BuildInfo；stdout 只允许协议 JSONL，
human feedback 原文不得进入响应或持久化。无参数才启动 UI，未知参数直接失败而不能回落启动 UI。

## 11. 验证边界

代码收口门禁包括 workspace test/check/clippy、desktop feature checks、frontend test/type/build、
DAG、CLI 精确 12-Feature catalog、rustfmt 和 `git diff --check`。

完整 candidate 构建、安装、真实 Provider closure 和真实游戏行为是独立高成本门禁。局部测试不能
替代 fresh candidate；Agent 不操作真实 STS2 UI。
